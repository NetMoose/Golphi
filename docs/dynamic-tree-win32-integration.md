# Интеграция динамического дерева Win32 — этап 4.2

Реализация подготовлена для Windows 11 amd64, CGO_ENABLED=0. Проверки Linux и
cross-build не подтверждают работу GUI. Первый нативный запуск на Windows 11 build 26100 получен: backend-тест завершился
ошибкой при переносе сфокусированного Edit с обратным выделением. Это не PASS;
этап остаётся непринятым. Диагностический повтор подтвердил расхождение Y координат и несоответствие
активного конца кешу. Следующая сборка с исправлением ещё не запускалась на Windows.

Panel использует собственный оконный класс Golphi с WS_CHILD/WS_CLIPCHILDREN,
принимающий WM_COMMAND от вложенных контролов. Вложенные HWND задают клиентскую
систему координат и стандартную обрезку Win32. Контейнер не растёт ради детей.
Прямой перенос использует SetParent и SetWindowPos без пересоздания потомков.
Материализация создаёт скрытые HWND; барьер событий снимается после публикации
полных bindings. Подготовленный Config.Input применяется и при startup.

Снимок Edit переводит UTF-16 в Unicode scalar offsets с проверкой границ
surrogate pair. EM_GETSEL возвращает упорядоченный диапазон, поэтому направление
сохраняется внутренним subclass при EM_SETSEL, клавиатуре, мыши и потере фокуса.
Для поддерживаемого однострочного EDIT (без ES_MULTILINE) направление определяется
по совпадению X caret с одним из двух различных наблюдаемых X концов.
Windows-лог при 96 DPI показал glyph Y=0 и caret Y=2: вертикальное положение
bitmap курсора не определяет конец на единственной строке. Это не обещание
поддержки multiline/bidi. Равные X, несовпадающий X и недоступные наблюдения без
надёжного кеша по-прежнему отвергаются; сырой XY сохраняется в диагностике.
Наблюдённый конец имеет приоритет над кешем. Неизменившийся упорядоченный диапазон
EM_SETSEL не получает новое направление только из аргументов setter.
Восстановление сначала сворачивает диапазон в anchor, затем задаёт нужные концы;
для сфокусированного поля результат повторно читается и сравнивается с запросом.
Ошибка направления не считается успешным восстановлением. При недоступном
text-end действует прежний проверяемый кеш явного изменения диапазона, который
инвалидируется перед изменением ввода/фокуса и не может противоречить доступному
наблюдаемому концу.
Если направление нельзя надёжно прочитать, операция возвращает обычную ошибку
до изменения дерева; недоступное направление не заменяется молча прямым.
Offscreen, bidi, IME и произвольные сторонние сообщения не объявлены проверенными.
Публичного API выделения не добавлено. Фокус вне переносимого поддерева сохраняется;
reattach не использует прежний Focused как запрос захвата фокуса.

Отсоединённые HWND и ресурсы неуспешной попытки остаются в retired до безопасного
внешнего шага Run либо Close. Маршруты событий отключаются раньше освобождения.
Depth включает оконный и Edit callback; вложенная попытка release ничего не
уничтожает. Уничтожение контейнера удаляет всё транзитивное поддерево из maps.
При неуспешном освобождении оставшиеся peers, callback trampoline и DLL остаются
учтёнными; новые обещания retry/успешного освобождения всех ресурсов не вводятся.

## Автоматический нативный запуск

Нужны интерактивный Windows 11 amd64 и исходники с Go либо два переданных тестовых
EXE. Тестовые EXE консольные, без `-H windowsgui`; GUI-примеры собираются с этим
флагом отдельно. Не используйте Wine как подтверждение поддерживаемой матрицы.

Из корня репозитория в PowerShell:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/verify-dynamic-tree-native-windows.ps1
```

Для готовых EXE:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/verify-dynamic-tree-native-windows.ps1 -BackendExe .\golphi-win32.test.exe -UIExe .\golphi-ui.test.exe
```

Скрипт выставляет `GOLPHI_NATIVE_TREE=1`, сохраняет SHA256, ОС, вывод и exit code.
Он запускает ровно `TestNativeDynamicTreeWin32` и
`TestNativeDynamicTreeIntegration`, отвергает SKIP/отсутствие PASS, не трактует
успешную сборку как запуск. Прямой вызов EXE использует LASTEXITCODE; пустой
ExitCode объекта Start-Process не принимается за ноль. Логи находятся в
`artifacts/dynamic-tree-windows/`; прислать весь каталог и указать Windows build,
Go version, масштаб 100%/96 DPI либо фактическое отличие.

Backend-тест проверяет startup reverse Unicode selection, прямой перенос,
detach/reattach, фокус внешней Button, сфокусированное обратное выделение,
неудачный SetParent на уже уничтоженный HWND, поздний отказ создания потомка,
тишину технических событий, реальный WM_COMMAND callback и deferred release.
Он проверяет освобождение native HWND через IsWindow и очистку реестров, а не RSS.
UI-тест проверяет тот же backend через публичное ядро; его состав описан в
исходнике `ui/tree_native_test.go`.

## Ручная часть и граница доказательств

Поставляемый backend EXE содержит отдельный ограниченный 180 секундами тест
`TestNativeDynamicTreeManual`, использующий производственный Driver. Запуск:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/verify-dynamic-tree-native-windows.ps1 -BackendExe .\golphi-win32.test.exe -UIExe .\golphi-ui.test.exe -Manual
```

Сначала подготовьте внешнее приложение: откройте Notepad, узнайте PID в Task
Manager либо командой `(Get-Process notepad | Select-Object -First 1).Id`.
Пользовательский ввод в тестовое поле не требуется. В режиме `-Manual` runner
сначала выполняет две автоматические проверки, затем открывает постоянное окно
`Golphi manual tree: 180 seconds`. Команды ниже вводятся в ту же консоль,
где запущен runner, и завершаются Enter.

1. Рассмотрите верхнюю вложенную Panel. Её oversized Button выходит за правую и
   нижнюю границы внутренней Panel, но видимая часть должна заканчиваться на
   x=240/y=160 в клиентских координатах формы при 96 DPI. Справа остаётся чистое
   место перед подписью, под панелью — чистое пространство. Внешняя Panel
   занимает 220×110, внутренняя 180×70 логических единиц; они не растут.
   Сохраните снимок всего окна как `clipping.png` в каталог логов. Только после
   визуальной проверки введите `clip-pass`; если есть выход за границы — `fail`.
2. Введите `arm 1234`, заменив 1234 PID вашего Notepad. Тест напечатает `ARMED` и
   будет ждать foreground **именно этого PID**, поэтому гонки с закрывающимся
   окном нет. Переключитесь в Notepad обычным Alt+Tab и оставьте его активным.
   Тест выполнит настоящий backend SetParent поля из нижней левой Panel в
   правую; событие фиксируется строкой `AUTO_MOVE`, проверяются неизменный
   foreground HWND и прежние клиентские размеры панелей.
3. Убедитесь, что Notepad остался активен: Golphi не должен появиться поверх или
   забрать ввод. Вернитесь в консоль, прочитайте `AUTO_CHECK`, затем введите
   `focus-pass` и `done`. При неверном результате введите `fail`.

До перехода foreground к указанному PID переноса нет. `done` принимается только
после переноса и двух подтверждений. Закрытие окна до `done`, `fail` или тайм-аут
завершают тест ошибкой. На Windows Terminal запускайте runner прямо в той же
консоли; не перенаправляйте stdin из файла. Отдельный прямой запуск без runner:

```powershell
$env:GOLPHI_NATIVE_TREE_MANUAL = '1'
.\golphi-win32.test.exe -test.v -test.run=^TestNativeDynamicTreeManual$ -test.timeout=210s
```

`manual-operator.log` хранится отдельно от `backend-native.log` и `ui-native.log`.
`AUTO_SETUP`/`AUTO_MOVE`/`AUTO_CHECK` — машинные наблюдения; `USER_CONFIRM` —
подтверждения оператора, не автоматическое доказательство pixel clipping.
Приложить все логи, `clipping.png`, Windows build и масштаб. PASS интерактивного
теста означает завершённый workflow с подтверждениями, а не распознавание
изображения. Запуск только автоматических тестов оставляет ручную часть открытой.

Не закрываются вопросы DPI switching, IME, accessibility, layout, нескольких
форм, направлений bidi и общей политики cleanup/retry.

Источники: Context7 resolve для Win32 завершился transport error; использована
официальная документация Microsoft:
[SetParent](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setparent),
[EM_GETSEL](https://learn.microsoft.com/en-us/windows/win32/controls/em-getsel),
[EM_SETSEL](https://learn.microsoft.com/en-us/windows/win32/controls/em-setsel).

Поколение события фиксируется в оконном callback до обращения к sink и
отвергается при устаревании; оно не заменяется текущим поколением при доставке.
Поддерживаемые EDIT/BUTTON отправляют EN_CHANGE/BN_CLICKED синхронно через
WM_COMMAND. Отдельной очереди отложенных уведомлений адаптер не создаёт. Внешний
Run отбрасывает posted WM_COMMAND с дочерним HWND: такие синтетические сообщения
не несут достоверного исходного поколения и не являются источником уведомлений
стандартных контролов. Настоящий BM_CLICK и отклонение старого внутреннего epoch
проверяются нативным тестом. Поддержка стороннего PostMessage через вложенные
чужие message loops не вводится.

## Диагностический повтор после Windows-отказа 2026-10-29

Первый журнал содержит `selection direction cannot be established unambiguously`
в `TestNativeDynamicTreeWin32` при ApplyTree сфокусированного обратного выделения.
Исходный журнал не сообщает фазу/координаты, поэтому причина пока не установлена.
Ошибка PowerShell после этого — распространение exit code 1 из тестового EXE.

Следующий запуск нужен **без `-Manual`**, с новыми backend/UI EXE из диагностического
архива. Команда runner остаётся той же. В `backend-native.log` появятся
`NATIVE_INPUT` до SetFocus, после SetFocus и после EM_SETSEL перед ApplyTree;
при успехе переноса — также после ApplyTree. Эти строки только читают native
состояние, не вызывают sleep, message pump и не меняют фокус/выделение.

Ошибка теперь указывает `PrepareTree snapshot` либо `Commit snapshot ... before
placement`, Peer/HWND, UTF-16 диапазон, прежние anchor/caret, valid/known кеша,
сырые значения EM_POSFROMCHAR и наблюдённые координаты caret/концов. Это позволит
отличить расхождение координат, недоступный конец, потерю фокуса и недействующий
кеш. Для GetCaretPos диагностический `caretErr` значим только при `caretOK=0`:
Windows может сохранять старый last-error после успешного вызова.

Передайте весь каталог логов, включая environment/SHA256, даже если тест опять
завершится ошибкой. Ручной сценарий пока не нужен: сначала требуется пройти
автоматические проверки. Правило отказа при неоднозначном направлении сохранено;
диагностическая сборка не объявлена исправлением нативной причины.

## Следующая сборка после диагностического лога

Полученный `NATIVE_INPUT` показал: после reverse EM_SETSEL диапазон UTF-16 [1,6],
caret (35,2), low (10,0), high (35,0), кеш [6,1]. Отказ произошёл в
`PrepareTree snapshot` до SetParent. Поэтому исправление отдельно учитывает
вертикальное расхождение однострочного Edit и ошибочный кеш запрошенного
направления. Схема collapse-then-set устраняет повторное присваивание того же
упорядоченного диапазона; гипотеза об оптимизации такого присваивания внутри
Windows ещё требует нового нативного запуска. Фактическое направление после
восстановления теперь обязательно проверяется.

Повторить автоматический runner без `-Manual` и передать логи. Тест дополнен
чередованием прямого и обратного выделения при одном и том же диапазоне [1,6]
и строками `same-ordered-range-after-verified-restore`; проверяются также концы
текста. Успешный cross-build и переносимые regression-тесты не заменяют этот
Windows-запуск. Старые журналы и открытые вопросы сохраняются.

## Выделение клавиатурой и перенос HWND — 2026-10-29

[Изолированная проба](../artifacts/edit-selection-probe-windows-20261029/selection-probe.log.txt)
завершила 24 случая, exit code 0; [SHA256 и окружение](../artifacts/edit-selection-probe-windows-20261029/environment.txt)
совпали с пакетом. На Windows build 26100 / DPI 96 обычный EDIT и EDIT с
обработкой Golphi показали одинаковые результаты. Прямой и обратный EM_SETSEL,
включая collapse-then-set, оставляют каретку у верхней границы для ASCII и
строки с суррогатными парами. EM_GETCARETINDEX возвращает 0 даже при свёрнутой
каретке в ненулевой позиции; EM_SETCARETINDEX видимого изменения не даёт.
В этой конфигурации использовать их как достоверное чтение/восстановление нельзя.

Следующий диагностический эксперимент: оператор создаёт `[2,5]` в `ABCDEF`
через End, Left и три Shift+Left, запускает F8 с фокусом в Edit. Тот же HWND
переносится `place` между панелями без `restoreInput` и EM_SETSEL. Читаем native
состояние до, сразу после и после прохождения опубликованного сообщения через
очередь Windows. Затем оператор нажимает Shift+Right один раз и F9: `[3,5]`
с кареткой на нижней границе проверяет продолжение изменения нужного конца.
Негативный результат сохраняется как наблюдение; PASS означает завершение
диагностики. Это не весь production ApplyTree: он пока вызывает restoreInput.
Код библиотеки, OpenSpec checkbox и остальные открытые вопросы не меняются.

Пакет `artifacts/golphi-edit-keyboard-selection-probe-windows.zip` содержит
русскую инструкцию и `scripts/probe-edit-keyboard-selection-windows.ps1` в
UTF-8 с BOM. После запуска передать оба файла из
`artifacts/edit-keyboard-selection-probe`, в том числе при неуспешном завершении.


## Проба восстановления фокуса после переноса — 2026-10-29

[Клавиатурная проба](../artifacts/edit-keyboard-selection-windows-20261029/keyboard-selection-probe.log.txt)
и [окружение](../artifacts/edit-keyboard-selection-windows-20261029/environment.txt)
соответствуют manifest диагностического пакета коммита `0ffc831`
(SHA256 EXE `592701b7b6f94fbdc67ca0eac2822125cea8526a068c6a44c2512fb40115bcf9`). Начальное обратное выделение `[2,5]`
в `ABCDEF` подтверждено с фокусом Edit и кареткой у нижней границы. После
`place` HWND и диапазон сохраняются, но фокус уходит в старую Panel и остаётся
там после доставки контрольного сообщения. Сбор завершился exit code 0 с
`continuation_performed=false reason=focus-lost-after-move`. Координаты каретки
без фокуса Edit не доказывают сохранение активного конца; продолжение ввода
не было проверено.

По согласованию добавлен режим `-RestoreFocus` к диагностическому runner.
После переноса и чтения immediate ровно один SetFocus возвращает фокус прежнему
HWND Edit. Сразу читаются GetFocus и native-состояние, затем доставляется
контрольное сообщение и проверяется настоящий Shift+Right/F9. EM_SETSEL и
restoreInput не вызываются. Возврат фокуса неудачен — фиксируется отрицательное
наблюдение, без повторного нажатия мышью и восстановления выделения.

Распаковать `artifacts/golphi-edit-focus-restore-probe-windows.zip` в новую папку
и выполнить:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\probe-edit-keyboard-selection-windows.ps1 -RestoreFocus
```

Последовательность: щёлкнуть ABCDEF; End; Left один раз; Shift+Left три раза;
отпустить Shift; F8; после подсказки формы Shift+Right один раз, отпустить
Shift и F9. Не переключать фокус. Передать `keyboard-selection-probe.log` и
`environment.txt` из `artifacts/edit-keyboard-selection-probe`. Русский .ps1
сохранён с UTF-8 BOM. Сборка и статическая проверка не заменяют запуск на Windows;
PASS пробы означает сбор данных. Production-код и задачи приёмки не меняются.
