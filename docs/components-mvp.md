# Компоненты экспериментального MVP

`ui.NewForm()` создаёт логическую форму. `ui.NewEdit(owner)`,
`ui.NewButton(owner)`, `ui.NewLabel(owner)` принимают живую `*ui.Form`:
владелец обязателен, nil и уничтоженный владелец вызывают panic.
Конструкторы не создают native-ресурсов и не присоединяют контрол к Parent.

`form.SetTitle(string)` / `form.Title()` работают с заголовком.
`control.SetText(string)` / `control.Text()` работают с текстом.
`control.Owner()` и `control.Parent()` возвращают `*ui.Form`.
`control.SetParent(*ui.Form) error` меняет только визуальную связь;
`SetParent(nil)` отсоединяет контрол, сохраняя его настройки.
Уничтоженный Parent даёт error, не изменяя прежнее размещение, Owner или
настройки. Повторное назначение того же живого Parent безопасно.

Owner и Parent могут быть разными формами в статическом логическом дереве.
Уничтожение любой из них уничтожает соответствующий контрол и удаляет его
из обеих связей. `Destroy()` немедленно отмечает объект уничтоженным,
каскадно обрабатывает owned-компоненты и визуальных потомков. Пересечение
деревьев не вызывает повторного уничтожения. `Destroyed()` и повторный
`Destroy()` безопасны; прочие операции уничтоженного объекта вызывают panic,
включая `SetParent`, даже несмотря на его возврат error.

Это логическая часть подготовки MVP. Native-создание, Run, события,
обновление живых native-контролов добавляются отдельными этапами.
MVP допускает только статическое дерево до Run: Panel, динамическое
создание, перенос и отсоединение во время Run, несколько окон и полный
контракт произвольных деревьев компонентов не заявлены реализованными.
Статические связи между разными формами не означают поддержку нескольких
native-окон в одном Run. Детали физического освобождения во время callback
относятся к runtime; логическая часть сама native-ресурсами не владеет.

## Фиксированная геометрия

`form.SetClientSize(width, height)` задаёт клиентскую область окна без
декораций. `control.SetBounds(x, y, width, height)` задаёт фиксированное положение
относительно внутренней области Parent и минимальный размер контрола.
Native-тема может увеличить размер контрола, сохраняя его координаты;
SetClientSize по-прежнему задаёт точный размер клиентской области. Все аргументы —
целые logical units; преобразование с учётом начального масштаба выполняет
backend. Одинаковые Bounds не гарантируют одинаковый внешний вид native
контролов на разных ОС.

Размеры должны быть строго положительными, координаты — неотрицательными.
Недопустимые значения вызывают panic, сохраняя прежнюю геометрию. Проверка
уничтожения выполняется первой. Выход за границы Parent, пересечения и
обрезание не исправляются автоматически. Bounds можно подготовить до
назначения Parent; перенос до Run сохраняет те же относительные координаты.

Геометрия настраивается только до Run. Динамическая геометрия, пользовательское
изменение размера окна и переключение DPI между мониторами не поддерживаются
MVP; масштаб фиксируется при запуске. Runtime и native-запрет resizing пока
реализуются отдельным этапом.

Внутренний hook интеграции: Run должен установить `component.started` для
формы и каждого участвующего контрола **до** native-инициализации и больше
не сбрасывать его. Сеттеры также проверяют этот флаг у Owner и Parent.
Тесты моделируют начало Run установкой флага; существование публичного Run
этот hook не подразумевает. До явного вызова сеттеров внутренний `bounds`
нулевой (геометрия ещё не задана); это не обещание публичных размеров по
умолчанию. Примеры должны явно задавать ClientSize и Bounds; политика
обработки незаданной геометрии остаётся задачей runtime.

## События и изменение текста

`button.SetOnClick(func())` и `edit.SetOnChange(func())` назначают единственный
обработчик. Повторное назначение заменяет его, nil отключает. Setter события
уничтоженного компонента вызывает panic, как и другие обычные операции.
Текст можно прочитать из замыкания через `edit.Text()`; новое значение уже
доступно при входе в OnChange. Одинаковый итоговый текст события не создаёт.

До запуска и у отсоединённого контрола подготовка текста остаётся тихой.
Работающий присоединённый Edit уведомляет как об изменении пользователем,
так и через SetText. Синхронный native-сигнал от SetText объединяется с
программным изменением; сравнивается прочитанный обратно итоговый текст,
включая нормализацию backend.

Изменения того же Edit внутри OnChange применяются сразу без рекурсивного
вызова. После возврата обработчика отличающийся от входного текст создаёт
одно отложенное уведомление; возврат к входному значению отменяет повтор.
Ненулевая замена сохраняет накопление и выбирается при следующей доставке.
Nil отменяет и очередь, и накопление текущего вызова. После нового назначения
первое реальное изменение начинает новое сравнение с текстом перед этим
изменением, даже если результат совпал со входом в старый обработчик.
Destroy и логическое отсоединение отменяют ожидающие уведомления; неудачная
смена Parent сохраняет их. Начало остановки запрещает новые вызовы.

На этапе реализации событий эти правила проверены реальным внутренним
контроллером с подставным адаптером runtime. Native Run подключается отдельным
этапом. Его внутренний `eventRuntime` предоставляет `eventsRunning()`,
`enqueueEvent(func())` и `syncText(*component, string) string`. Последний
выполняет native SetText и Text, возвращает эффективное значение, а ошибки
передаёт через panic boundary runtime. Адаптер назначается после создания
native peers. `enqueueEvent` всегда откладывает работу до безопасного оборота
цикла; конкретный порядок с Post и событиями других компонентов не является
публичной гарантией. Native Change/Click направляются в `nativeText`/
`nativeClick`. При остановке/сбое runtime сначала выключает доставку, затем
вызывает `cancelTextNotification()` для каждого компонента и очищает очередь.

Panel, отсоединение предка и динамический reparent во время Run остаются вне
MVP. Тесты логического отсоединения контрола не означают поддержку этих native
сценариев. Взаимные изменения компонентов, справедливость очереди и иные
неописанные сочетания сохраняют открытый статус.

## Run: допуск и native lifecycle

`form.Run() error` вызывают из `main` или его синхронного помощника на startup
OS thread. Импорт `ui` закрепляет этот поток, но не загружает GTK/Win32 и не
создаёт окно. Linux-сборка выбирает GTK4, Windows-сборка — Win32.

Первая проверка Run — уничтожение формы: уничтоженная форма вызывает panic
даже с фонового потока и после завершившегося запуска. Native-действий и
изменения допуска при этом нет. У живой формы неверный поток и уже
израсходованная попытка возвращают error. Отклонённый первый вызов допуска
не расходует. Прошедшая проверки попытка расходуется атомарно и навсегда,
включая отказ Init, создания peer или показа. Повторный Run из обработчика
возвращает error, сохраняя работающий интерфейс. После выхода Run повторный
запуск также недоступен; обычное закрытие само по себе не уничтожает Go-форму.

Run создаёт одно native-окно и его визуальных детей в порядке создания
логических компонентов. Owned-контролы без Parent остаются логическими.
Настройки передаются при создании peers, итоговый native-текст считывается
до включения событий. Сигналы подготовки не вызывают прикладных обработчиков.
Только после полной подготовки и показа включаются события и внутренняя
очередь отложенных уведомлений. Публичный Post добавляется отдельной задачей.

У формы, её owned-контролов и визуальных детей флаг начала Run фиксируется
до Init и не сбрасывается после ошибки или завершения. Геометрические setter
после этого вызывают panic. Незаданную геометрию текущая реализация заменяет
внутренними размерами 400×180 для формы и 120×28 для контрола. Это технический
fallback, **не публичная гарантия размеров**; примеры обязаны задавать размеры.

В течение Run конструкторы вызывают panic до изменения дерева или счётчика
компонентов. SetParent возвращает error, сохраняя связи и настройки; проверка
уничтожения вызывающего компонента остаётся первой. Это ограничение
статического MVP, а не поддержка динамического дерева.

Destroy сразу меняет логическое состояние и отменяет уведомления. Физическое
освобождение peer выполняется на безопасном обороте после возврата callbacks
и очереди либо после выхода native loop. Destroy главной формы и запрос её
закрытия выключают доставку и запрашивают выход. Очистка пытается освободить
все созданные peers и инфраструктуру, собирая ошибки и паники отдельных
операций; успешный выход возвращает nil. Диагностика паники хранит исходное
значение и стек во внутреннем типе; публичный API её разбора не утверждён.

Допуск и интеграция проверяются subprocess-тестами с подставным Driver на
настоящем startup-потоке. Это не подтверждение реального запуска Windows
или полного контракта очистки: расширенные сценарии остановки, отказов и
native smoke относятся к следующим задачам. Прежние открытые вопросы
полной библиотеки остаются открытыми.

## Post

`ui.Post(func()) error` безопасен для вызова из любой goroutine. До `Run` и
во время подготовки native-компонентов он возвращает ошибку без накопления
задач. Приём открывается после успешных Init, создания, начальных свойств,
размещения, чтения текста и Show, когда очередь и пробуждение готовы, до
прикладной доставки и без ожидания первой отрисовки. Ошибка запуска не открывает
приём. `Post(nil)` возвращает ошибку без остановки приложения.

Результат `nil` означает принятие, а не завершение или обещание выполнения.
Функции выполняются последовательно на UI-потоке. Даже вызов с UI-потока всегда
ставит задачу в очередь: вложенная задача начнётся после текущего обработчика
или задачи и после уже ожидающих задач. Последовательно принятые задачи сохраняют
FIFO; порядок конкурентных отправителей и порядок относительно native-событий
и OnChange не определяются.

Обычная и аварийная остановка атомарно закрывают приём и отменяют не начатые
задачи. Гонка с остановкой даёт принятие до границы (с возможной отменой) либо
ошибку без постановки. Выполняющаяся функция не прерывается принудительно.
Очистка не восстанавливает очередь. Обычный Post не имеет владельца: уничтожение
захваченного компонента само по себе задачу не отменяет; перед обращением можно
проверить `Destroyed()`.

Типы ошибок, окончательный получатель Post полной библиотеки, ожидание результата,
индивидуальная отмена и справедливость остаются открытыми вопросами.
