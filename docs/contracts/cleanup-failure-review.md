Это документальное применение выбранной части E0. Runtime, backend, FFI, алгоритм очистки и агрегатор ошибок не реализованы; T-01–T-09 не выполнялись. Q-05 и весь E0 остаются незавершёнными.

## Соответствие договорённостям

| Решение | Проверяемое описание |
|---|---|
| Сбои очистки дополняют первичную диагностику | Сохраняются исходные V/S, все E1/E2 и значения/стеки каждой перехваченной паники W/T |
| Ошибка одной операции не прекращает независимые | После ошибки А предпринимаются попытки очистки независимых Б/В |
| Паника перехватывается отдельно | Граница операции А; W/T сохранены, попытки Б/В продолжаются, тело А не возобновляется |
| Run возвращает собранную диагностику | После выхода из callback и завершения попыток — ненулевая ошибка с первичной паникой, стеком и всеми сбоями; перехваченные паники очистки не выбрасываются повторно |

Сохраняются прекращение прикладной доставки, отмена ожидающих уведомлений и ещё не начатых Post, отказ новых Post. Завершение попыток не обещает освобождения всех ресурсов; порядок зависимых ресурсов не назначен.

## Покрытие сценариев

[Контракт аварийной остановки](application-failure.md) содержит сопоставления всех 13 сценариев: восемь прежних и пять новых. [Контракт Post](post-dispatch.md) сохраняет 18 прежних сценариев и правила принятия, FIFO, отмены и захвата компонента. В двух MODIFIED-требованиях сохранены имена и тексты всех четырёх прежних сценариев.

| Новый сценарий | Трассировка application-failure |
|---|---|
| Handler panic followed by cleanup failures | Ошибка E и паника W после паники обработчика; возврат V/S/E/W/T без повторного выбрасывания |
| Task panic followed by cleanup failures | Несколько ошибок/паник после Post; полный результат Run |
| Multiple cleanup failures preserve primary diagnostics | Смешанные E1/E2/W с сохранением V/S и W/T |
| Error leaves independent cleanup running | Ошибка А, попытки независимых Б/В |
| Panic leaves independent cleanup running | Перехват W на границе А, попытки независимых Б/В |

### openspec/specs/application-failure/spec.md — Scope

Контракт касается паники прикладного обработчика или функции Post, прекращения прикладной доставки, отмены ожидающих уведомлений и всех ещё не начатых задач Post и отклонения новых Post при аварийной остановке. После выхода из callback выполняются попытки очистки; ошибки и перехваченные паники отдельных операций очистки дополняют первоначальную панику, её значение и стек, не препятствуя попыткам очистить остальные независимые ресурсы. После завершения попыток Form.Run() возвращает ненулевую ошибку со всей собранной диагностикой; перехваченные паники очистки повторно наружу не выбрасываются. Открытыми остаются обычная остановка и очистка без первичной паники, самостоятельный Destroy, ошибки запуска, сбои внутренних механизмов вне отдельных операций очистки, порядок очистки зависимых ресурсов и определение зависимостей, повторные попытки и судьба неосвобождённых ресурсов, зависшие операции, тайм-ауты и принудительное прерывание, публичный тип ошибки, API доступа, представление стеков, способ объединения и порядок представления диагностики, повторный Run и состояние после возврата. Остальные вопросы E0, перечисленные в design.md изменения define-cleanup-failure-contract, этим контрактом не разрешаются.

### openspec/specs/post-dispatch/spec.md — Scope

Контракт относится к обычному Post(fn), без владельца. Очистка и диагностика при аварийной остановке, включая сбои отдельных операций очистки после первичной паники, подчиняются расширенному application-failure: первоначальная паника сохраняется, сбои очистки добавляются к диагностике, попытки очистить остальные независимые ресурсы продолжаются, а Form.Run() возвращает всю собранную диагностику после завершения попыток. Открытыми остаются обычная остановка и очистка без первичной паники, порядок очистки зависимых ресурсов и определение зависимостей, публичный тип ошибки, API доступа, представление стеков, способ объединения и порядок представления диагностики, а также остальные вопросы очистки и остановки, оставленные открытыми application-failure. Ожидание результата, индивидуальная отмена, задачи с владельцем, точный получатель метода, типы отказа и перегрузка, порядок относительно native events/OnChange, справедливость, взаимные изменения, bootstrap/закрепление UI-потока, граница готовности Run и проверка потоковых правил остаются открытыми. Остальные вопросы E0, перечисленные в design.md изменения define-cleanup-failure-contract, этим контрактом не разрешаются.

## Организация работы

Ветка feat/define-cleanup-failure-contract создана от актуального develop (7330c37) в существующем checkout без worktree. Использован Subagent Driven Development: контракты подготовлены параллельно, после их review параллельно согласованы непересекающиеся файлы дизайна, реестров и Scope. Git выполняет только координатор; этапы фиксируются commit/push, результат передаётся PR в develop.

Checkbox-задачи OpenSpec извлечены в briefs непосредственно; стандартный helper ожидает заголовки Task N. Указания пользователя о checkout, параллельных независимых задачах и Git у координатора имеют приоритет над стандартными настройками навыка. Продуктовые решения сверх согласованных не принимались.
