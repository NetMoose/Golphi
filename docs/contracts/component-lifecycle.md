# Жизненный цикл компонентов Golphi

Этот документ описывает целевой контракт, принятый в [изменении define-component-contract](../../openspec/changes/define-component-contract/design.md), и проверяемые примеры из [спецификации жизненного цикла](../../openspec/changes/define-component-contract/specs/component-lifecycle/spec.md). Он не подтверждает наличие работающей библиотеки или поддержку операций конкретным backend и не означает завершение E0.

## Две независимые связи

`Owner` определяет владение, `Parent` — визуальное размещение. Успешная смена `Parent` сохраняет `Owner`. Компонент с владельцем можно создать без `Parent`, настроить свойства и обработчики и затем присоединить к контейнеру.

Согласован контракт `SetParent(parent) error`: операция либо полностью завершается, либо возвращает ошибку с сохранением прежнего состояния. При ошибке сохраняются прежний `Parent`, `Owner`, настройки, обработчики и работоспособность прежнего размещения. Временные ресурсы неуспешного переноса освобождаются. Откат одного поля `Parent` без восстановления работоспособного отображения контракту не соответствует.

Успешный `SetParent(nil)` убирает компонент и его визуальное поддерево из отображаемого интерфейса. Владение, настройки, обработчики и внутренние связи поддерева сохраняются для повторного присоединения. Это не уничтожение.

Уничтожение охватывает принадлежащие компоненту объекты и его визуальных потомков независимо от их владельцев. Все уничтожаемые объекты исключаются из обеих связей; пересечение деревьев не приводит к повторному освобождению ресурсов.

## Как читать эскизы

Ниже используется псевдокод, а не компилируемый Go. Конструкторы, их параметры и обработка ошибок, setters свойств, типы обработчиков и способ вызова уничтожения ещё не утверждены. Запись «создать» не задаёт сигнатуру конструктора; во всех примерах рассматривается ветка его успешного завершения. Запись «уничтожить» обозначает принятое поведение, но не утверждает метод `Destroy` или его сигнатуру.

`SetParent(parent) error` и семантика `SetOnClick` приняты; точные типы параметров и полные объявления API этими примерами не устанавливаются. Настройки и обработчики задаются условными операциями, чтобы не принимать решения об их сигнатурах. Владелец самой формы, bootstrap, запуск и завершение приложения здесь не выбираются.

## Эскиз создания формы и настройки без Parent

```text
форма := создать форму                         // эскиз конструктора
панельА := создать панель с Owner = форма, Parent = nil
кнопка := создать кнопку с Owner = форма, Parent = nil
задать кнопке подпись «Сохранить»               // эскиз setter
установить обработчик нажатия H                // тип H не утверждён

ошибка := панельА.SetParent(форма)
если ошибка: сохранить панельА для последующей попытки; закончить пример
ошибка := кнопка.SetParent(панельА)
если ошибка: сохранить кнопку для последующей попытки; закончить пример
```

Перед присоединением кнопки её `Owner = форма`, `Parent = nil`, подпись и H уже подготовлены. Успех меняет только её размещение: `Parent = панельА`, подпись и H используются без повторной настройки. При ошибке первого присоединения `Parent` остаётся `nil`; владелец, подпись и H сохранены для следующей попытки, частичные ресурсы освобождены.

Настройка текста до запуска не вызывает `OnChange`. Аналогично, изменение текста неприсоединённого компонента не вызывает уведомлений, а присоединение не воспроизводит подготовительные изменения. Это правила [контракта событий](../../openspec/changes/define-component-contract/specs/component-events/spec.md), а не обещание конкретного порядка запуска формы.

## Эскиз динамического добавления панели и переноса

Исходное состояние: форма работает, панельА присоединена к ней, кнопка отображается в панелиА. У кнопки `Owner = форма`, подпись «Сохранить» и обработчик H.

```text
панельБ := создать панель с Owner = форма, Parent = nil  // эскиз
настроить свойства панелиБ                             // эскиз
ошибка := панельБ.SetParent(форма)
если ошибка: сохранить панельБ для следующей попытки; закончить пример

ошибка := кнопка.SetParent(панельБ)
если ошибка: кнопка продолжает работать в панелиА
иначе: кнопка размещена в панелиБ
```

При успехе `Parent` кнопки становится панельБ, а `Owner` остаётся формой. Подпись и H сохраняются. При неуспешном переносе отображаемой кнопки возвращается ошибка; `Parent = панельА`, `Owner = форма`, подпись и H неизменны. Прежнее размещение остаётся работоспособным, временные ресурсы переноса освобождены. Пример не определяет причину ошибки или механизм её получения: они зависят от ещё не выбранной реализации.

## Эскиз отсоединения и возврата поддерева

Исходное состояние: панельБ присоединена к форме, содержит кнопку и поле ввода. У панели, кнопки и поля `Owner = форма`; у кнопки и поля `Parent = панельБ`.

```text
ошибка := панельБ.SetParent(nil)
если ошибка: прежнее размещение сохранено; закончить пример

задать полю текст «Подготовлено»                 // эскиз setter
ошибка := панельБ.SetParent(форма)
если ошибка: поддерево остаётся отсоединённым для следующей попытки
```

После успешного отсоединения только `Parent` панели становится `nil`; её дети сохраняют `Parent = панельБ`, свои настройки, обработчики и владельцев. Всё поддерево исчезает из отображаемого интерфейса. Для событий дети тоже отсоединены: цепочка `Parent` больше не достигает формы. Само наличие непосредственного родителя, `Owner` и видимость не определяют присоединённость; работающий runtime является отдельным условием доставки событий.

Изменение текста поля проходит без `OnChange`. Успешное возвращение панели восстанавливает отображение её детей с итоговыми настройками и обработчиками, без воспроизведения подготовительных уведомлений. При ошибке возврата сохраняются `Parent = nil` панели и все внутренние связи, итоговый текст и обработчики; частичные ресурсы попытки освобождены.

Пример не рассматривает уже ожидающее повторное `OnChange` в момент отсоединения: его судьба остаётся открытой. Сохранять ли нативные представления при отсоединении или пересоздавать их позже, также не решено.

## Эскизы уничтожения

**Уничтожение панели с детьми, принадлежащими форме.** Пусть `Owner` панели и кнопки — форма, `Parent` панели — форма, а `Parent` кнопки — панель. Условная операция «уничтожить панель» уничтожает и кнопку как визуального потомка. Обе исключаются из связей владения и визуальной иерархии; в частности, кнопка удаляется из списка компонентов формы. Последующее уничтожение формы не освобождает ресурсы кнопки второй раз.

**Уничтожение владельца отсоединённой панели.** Пусть панель успешно отсоединена: `Parent = nil`, `Owner = форма`, а кнопка остаётся её визуальным ребёнком. Условная операция «уничтожить форму» достигает панели по владению и уничтожает её визуальное поддерево независимо от владельцев потомков. Отсутствие `Parent` у панели не спасает её от каскада. Если объект встречается по обеим связям, его ресурсы освобождаются один раз.

Эти примеры не задают порядок обхода двух деревьев, доступ к уничтоженному объекту или результат повторного явного вызова уничтожения. Гарантия отсутствия двойного освобождения при пересечении связей не является решением вопроса о повторном `Destroy`.

## Таблица ожидаемого состояния для ручной проверки

Имена сценариев переведены; строки следуют порядку сценариев исходной спецификации. «Сохранены» означает сохранение настроек и обработчиков, а не выбранную политику нативного фокуса или выделения.

| № / сценарий | Исходное состояние и действие | Ожидаемые связи и состояние | Ресурсы и наблюдаемое поведение |
|---|---|---|---|
| 1. Перенос между панелями | Кнопка: Owner = форма, Parent = панельА; успешный перенос в панельБ | Owner = форма, Parent = панельБ; настройки и H сохранены | Кнопка размещена в новой панели |
| 2. Подготовка кнопки | Создать с Owner = форма и Parent = nil; задать подпись и H; успешно присоединить | Owner = форма, Parent = панельА; подготовленные подпись и H используются | Повторная настройка после присоединения не нужна |
| 3. Ошибка переноса отображаемого компонента | Кнопка отображается в панелиА; SetParent(панельБ) возвращает ошибку | Owner = форма, Parent = панельА; все настройки и H сохранены | Прежнее размещение работоспособно; частичные ресурсы освобождены |
| 4. Ошибка первого присоединения | Настроенная кнопка с Owner = форма и Parent = nil; SetParent(панельА) возвращает ошибку | Owner = форма, Parent = nil; настройки и H сохранены для повтора | Частичные ресурсы освобождены; присоединения не произошло |
| 5. Отсоединение и возврат панели | Панель с кнопками; успешный SetParent(nil), затем успешный SetParent(форма) | Временно Parent панели = nil; Parent детей всегда = панель; Owner, настройки и обработчики сохранены | Всё поддерево исчезает и вновь отображается; во время отсоединения дети отсоединены и для событий |
| 6. Уничтожение панели с детьми формы | Кнопка: Owner = форма, Parent = панель; уничтожить панель, затем форму | Панель и кнопка уничтожены, удалены из обеих связей; кнопки нет среди компонентов формы | Ресурсы кнопки не освобождаются повторно при уничтожении формы |
| 7. Уничтожение владельца отсоединённого компонента | Панель: Owner = форма, Parent = nil, дети сохраняют Parent = панель; уничтожить форму | Панель и визуальные потомки уничтожены и удалены из обеих связей | Каскад действует без Parent панели, ресурсы каждого объекта освобождаются один раз |

Таблица предназначена для сверки документационного контракта. Проверка реального отката, ресурсов и отображения потребует отдельной реализации и испытаний backend.

## Открытые вопросы

Полный реестр сохраняется в [дизайне изменения](../../openspec/changes/define-component-contract/design.md#open-questions). Ни один из следующих вопросов здесь не закрывается:

- Q-01: module path и проверка существующей лицензии перед изменением лицензионных решений; название Golphi уже принято.
- Q-02/Q-03: технические зависимости, bridge, первый Linux backend, версии Go/toolkit и платформенная матрица.
- Q-04: bootstrap UI-потока, ограничения Run, принятие и отмена Post.
- Q-05: ошибки конструкторов и setters, операции над уничтоженным объектом, повторный Destroy, panic в callback. Возврат ошибки SetParent уже согласован.
- Q-06: сигнатуры событий и источник Program/User; замена обработчика при доставке; отключение обработчика, уничтожение, отсоединение компонента или предка и остановка при ожидающем OnChange; взаимные изменения разных компонентов; порядок относительно Post и нативных событий. Завершение уже вызванного обработчика при его замене не утверждено.
- Иерархия: проверка циклов Owner/Parent, смена Owner, перенос между формами или приложениями, присоединение к ещё не отображаемому контейнеру.
- Нативный жизненный цикл: момент создания, сохранения и уничтожения представлений; сохранение фокуса, выделения и курсора при пересоздании; механизм гарантированного отката SetParent.
- Q-07–Q-14: Close/Hide/завершение, модальность, layout, формат форм, поставка runtime, Qt, расширения и доступность остаются предложениями исходного документа.

Порядок обхода при уничтожении и способ освобождения пересекающихся связей примерами не выбираются. Проверяемость контракта на каждой платформе ещё предстоит доказать.
