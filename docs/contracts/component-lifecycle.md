# Жизненный цикл компонентов Golphi

Этот документ описывает целевой контракт, принятый в [изменении define-component-contract](../../openspec/changes/archive/2026-10-27-define-component-contract/design.md), и проверяемые примеры из [спецификации жизненного цикла](../../openspec/changes/archive/2026-10-27-define-component-contract/specs/component-lifecycle/spec.md). Дополнения об уничтожении приняты в [изменении define-destruction-and-event-failure-contract](../../openspec/changes/archive/2026-10-27-define-destruction-and-event-failure-contract/design.md) и проверяются его [дельтой component-lifecycle](../../openspec/changes/archive/2026-10-27-define-destruction-and-event-failure-contract/specs/component-lifecycle/spec.md). Он не подтверждает наличие работающей библиотеки или поддержку операций конкретным backend и не означает завершение E0.

## Две независимые связи

`Owner` определяет владение, `Parent` — визуальное размещение. Успешная смена `Parent` сохраняет `Owner`. Компонент с владельцем можно создать без `Parent`, настроить свойства и обработчики и затем присоединить к контейнеру.

Согласован контракт `SetParent(parent) error`: операция либо полностью завершается, либо возвращает ошибку с сохранением прежнего состояния. При ошибке сохраняются прежний `Parent`, `Owner`, настройки, обработчики и работоспособность прежнего размещения. Временные ресурсы неуспешного переноса освобождаются. Откат одного поля `Parent` без восстановления работоспособного отображения контракту не соответствует.

Успешный `SetParent(nil)` убирает компонент и его визуальное поддерево из отображаемого интерфейса. Владение, настройки, обработчики и внутренние связи поддерева сохраняются для повторного присоединения. Это не уничтожение.

Уничтожение охватывает принадлежащие компоненту объекты и его визуальных потомков независимо от их владельцев. Все уничтожаемые объекты исключаются из обеих связей; пересечение деревьев не приводит к повторному освобождению ресурсов.

## Как читать эскизы

Ниже используется псевдокод, а не компилируемый Go. Конструкторы, их параметры и обработка ошибок, setters свойств, и типы обработчиков ещё не утверждены. Запись «создать» не задаёт сигнатуру конструктора; во всех примерах рассматривается ветка его успешного завершения. Запись «уничтожить» означает принятый вызов `Destroy()`. Безопасная проверка состояния — `Destroyed() bool`.

`SetParent(parent) error` и семантика `SetOnClick` приняты; точные типы параметров и полные объявления API этими примерами не устанавливаются. Настройки и обработчики задаются условными операциями, чтобы не принимать решения об их сигнатурах. Владелец самой формы, bootstrap, запуск и завершение приложения здесь не выбираются.

## Эскиз создания формы и настройки без Parent

```text
форма := создать форму                         // эскиз конструктора
панельА := создать панель с Owner = форма, Parent = nil
кнопка := создать кнопку с Owner = форма, Parent = nil
задать кнопке подпись «Сохранить»               // эскиз setter
установить обработчик нажатия H                // тип H не утверждён

ошибка := панельА.SetParent(форма)
если ошибка: сохранить панельА для последующей попытки; закончить пример
ошибка := кнопка.SetParent(панельА)
если ошибка: сохранить кнопку для последующей попытки; закончить пример
```

Перед присоединением кнопки её `Owner = форма`, `Parent = nil`, подпись и H уже подготовлены. Успех меняет только её размещение: `Parent = панельА`, подпись и H используются без повторной настройки. При ошибке первого присоединения `Parent` остаётся `nil`; владелец, подпись и H сохранены для следующей попытки, частичные ресурсы освобождены.

Настройка текста до запуска не вызывает `OnChange`. Аналогично, изменение текста неприсоединённого компонента не вызывает уведомлений, а присоединение не воспроизводит подготовительные изменения. Это правила [контракта событий](../../openspec/changes/archive/2026-10-27-define-component-contract/specs/component-events/spec.md), а не обещание конкретного порядка запуска формы.

## Эскиз динамического добавления панели и переноса

Исходное состояние: форма работает, панельА присоединена к ней, кнопка отображается в панелиА. У кнопки `Owner = форма`, подпись «Сохранить» и обработчик H.

```text
панельБ := создать панель с Owner = форма, Parent = nil  // эскиз
настроить свойства панелиБ                             // эскиз
ошибка := панельБ.SetParent(форма)
если ошибка: сохранить панельБ для следующей попытки; закончить пример

ошибка := кнопка.SetParent(панельБ)
если ошибка: кнопка продолжает работать в панелиА
иначе: кнопка размещена в панелиБ
```

При успехе `Parent` кнопки становится панельБ, а `Owner` остаётся формой. Подпись и H сохраняются. При неуспешном переносе отображаемой кнопки возвращается ошибка; `Parent = панельА`, `Owner = форма`, подпись и H неизменны. Прежнее размещение остаётся работоспособным, временные ресурсы переноса освобождены. Пример не определяет причину ошибки или механизм её получения: они зависят от ещё не выбранной реализации.

## Эскиз отсоединения и возврата поддерева

Исходное состояние: панельБ присоединена к форме, содержит кнопку и поле ввода. У панели, кнопки и поля `Owner = форма`; у кнопки и поля `Parent = панельБ`.

```text
ошибка := панельБ.SetParent(nil)
если ошибка: прежнее размещение сохранено; закончить пример

задать полю текст «Подготовлено»                 // эскиз setter
ошибка := панельБ.SetParent(форма)
если ошибка: поддерево остаётся отсоединённым для следующей попытки
```

После успешного отсоединения только `Parent` панели становится `nil`; её дети сохраняют `Parent = панельБ`, свои настройки, обработчики и владельцев. Всё поддерево исчезает из отображаемого интерфейса. Для событий дети тоже отсоединены: цепочка `Parent` больше не достигает формы. Само наличие непосредственного родителя, `Owner` и видимость не определяют присоединённость; работающий runtime является отдельным условием доставки событий.

Изменение текста поля проходит без `OnChange`. Успешное возвращение панели восстанавливает отображение её детей с итоговыми настройками и обработчиками, без воспроизведения подготовительных уведомлений. При ошибке возврата сохраняются `Parent = nil` панели и все внутренние связи, итоговый текст и обработчики; частичные ресурсы попытки освобождены.

Успешное отсоединение отменяет уже ожидающие `OnChange` всего отсоединяемого поддерева; повторное присоединение их не восстанавливает. При ошибке `SetParent` ожидающие уведомления сохраняются с прежним состоянием. Новое накопление после отсоединения и повторного присоединения в том же callback остаётся открытым вопросом. Сохранять ли нативные представления при отсоединении или пересоздавать их позже, также не решено.

## Эскизы уничтожения

**Уничтожение панели с детьми, принадлежащими форме.** Пусть `Owner` панели и кнопки — форма, `Parent` панели — форма, а `Parent` кнопки — панель. Условная операция «уничтожить панель» уничтожает и кнопку как визуального потомка. Обе исключаются из связей владения и визуальной иерархии; в частности, кнопка удаляется из списка компонентов формы. Последующее уничтожение формы не освобождает ресурсы кнопки второй раз.

**Уничтожение владельца отсоединённой панели.** Пусть панель успешно отсоединена: `Parent = nil`, `Owner = форма`, а кнопка остаётся её визуальным ребёнком. Условная операция «уничтожить форму» достигает панели по владению и уничтожает её визуальное поддерево независимо от владельцев потомков. Отсутствие `Parent` у панели не спасает её от каскада. Если объект встречается по обеим связям, его ресурсы освобождаются один раз.

### Немедленное логическое уничтожение

`Destroy()` немедленно делает компонент логически уничтоженным. `Destroyed() bool` безопасно возвращает `true` после этого перехода. Повторный `Destroy()` безопасен и ничего не меняет, в том числе пока физическое освобождение отложено; повторное освобождение не начинается. Все обычные операции над уничтоженным компонентом вызывают `panic`: это относится к getters, setters и `SetParent`, хотя последний возвращает `error` для ошибок переноса живого компонента. Возврат `error` не заменяет `panic` при использовании уничтоженного объекта. Исключения — `Destroy()` и `Destroyed()`.

Если необходимо для безопасного выхода из callback, физическое освобождение ресурсов допускается отложить до выхода из него. Логическое уничтожение при этом уже произошло. Уже выполняющийся обработчик продолжает работу, если сам не вызывает `panic`; наличие ещё не освобождённых ресурсов не разрешает обычные обращения к объекту.

```text
обработчик кнопки:
    кнопка.Destroy()
    утверждать: кнопка.Destroyed() == true
    кнопка.Destroy()                    // безопасный повтор до освобождения
    продолжить независимую работу       // обработчик не прерывается уничтожением
    выйти из callback                   // при необходимости ресурсы освобождаются теперь
```

Если оставшаяся часть обработчика вместо независимой работы читает обычное свойство кнопки, меняет его или вызывает `SetParent`, операция вызывает `panic`. Паника прикладного обработчика подчиняется [контракту application-failure](application-failure.md): запуск новых прикладных обработчиков и задач Post прекращается, новые Post отклоняются, ожидающие прикладные уведомления и ещё не начатые задачи Post отменяются. После выхода из callback выполняется очистка; после завершения её попыток `Form.Run()` возвращает ненулевую ошибку с исходным значением паники, стеком и всеми собранными сбоями очистки. [Текущая дельта очистки](../../openspec/changes/define-cleanup-failure-contract/specs/application-failure/spec.md) сохраняет все ошибки и значения/стеки перехваченных паник очистки, требует продолжать попытки независимых операций и не выбрасывать перехваченные паники повторно. Прикладная доставка не возобновляется; завершение попыток не гарантирует освобождения всех ресурсов. Это расширение относится к очистке после первичной паники обработчика или Post; самостоятельный Destroy и очистка без такой паники остаются открытыми.

Та же семантика действует для каждого компонента каскада по `Owner` и `Parent`. Если обработчик кнопки вызывает `панель.Destroy()` и кнопка уничтожается как визуальный потомок, её `Destroyed()` уже возвращает `true`, повторный `Destroy()` безопасен, обычное обращение вызывает `panic`. Пересечение деревьев по-прежнему не приводит к повторному освобождению; порядок обхода не выбирается.

## Таблица ожидаемого состояния для ручной проверки

Имена сценариев переведены; строки 1–7 следуют порядку сценариев исходной спецификации, строки 8–12 — порядку новых сценариев дельты component-lifecycle. Английское имя в новых строках обеспечивает прямое сопоставление со спецификацией. «Сохранены» означает сохранение настроек и обработчиков, а не выбранную политику нативного фокуса или выделения.

| № / сценарий | Исходное состояние и действие | Ожидаемые связи и состояние | Ресурсы и наблюдаемое поведение |
|---|---|---|---|
| 1. Перенос между панелями | Кнопка: Owner = форма, Parent = панельА; успешный перенос в панельБ | Owner = форма, Parent = панельБ; настройки и H сохранены | Кнопка размещена в новой панели |
| 2. Подготовка кнопки | Создать с Owner = форма и Parent = nil; задать подпись и H; успешно присоединить | Owner = форма, Parent = панельА; подготовленные подпись и H используются | Повторная настройка после присоединения не нужна |
| 3. Ошибка переноса отображаемого компонента | Кнопка отображается в панелиА; SetParent(панельБ) возвращает ошибку | Owner = форма, Parent = панельА; все настройки и H сохранены | Прежнее размещение работоспособно; частичные ресурсы освобождены |
| 4. Ошибка первого присоединения | Настроенная кнопка с Owner = форма и Parent = nil; SetParent(панельА) возвращает ошибку | Owner = форма, Parent = nil; настройки и H сохранены для повтора | Частичные ресурсы освобождены; присоединения не произошло |
| 5. Отсоединение и возврат панели | Панель с кнопками; успешный SetParent(nil), затем успешный SetParent(форма) | Временно Parent панели = nil; Parent детей всегда = панель; Owner, настройки и обработчики сохранены | Всё поддерево исчезает и вновь отображается; во время отсоединения дети отсоединены и для событий |
| 6. Уничтожение панели с детьми формы | Кнопка: Owner = форма, Parent = панель; уничтожить панель, затем форму | Панель и кнопка уничтожены, удалены из обеих связей; кнопки нет среди компонентов формы | Ресурсы кнопки не освобождаются повторно при уничтожении формы |
| 7. Уничтожение владельца отсоединённого компонента | Панель: Owner = форма, Parent = nil, дети сохраняют Parent = панель; уничтожить форму | Панель и визуальные потомки уничтожены и удалены из обеих связей | Каскад действует без Parent панели, ресурсы каждого объекта освобождаются один раз |
| 8. Повтор до физического освобождения (Destroy twice before physical release) | Вызвать Destroy(), пока освобождение отложено проверить Destroyed() и повторить Destroy() | Компонент немедленно логически уничтожен; Destroyed() = true; повтор ничего не меняет | Повторное освобождение не инициируется |
| 9. Обращение после уничтожения (Access after destruction) | После Destroy() отдельно вызвать обычный getter, setter или SetParent | Каждый вызов вызывает panic | Возвращаемый SetParent error не заменяет panic |
| 10. Самоуничтожение в обработчике (Self destruction during a handler) | Обработчик вызывает Destroy() своего компонента и продолжает без обычных обращений к нему | Destroyed() уже = true; обработчик продолжает работу | Физическое освобождение при необходимости происходит после выхода из callback |
| 11. Обращение из оставшейся части обработчика (Access from the remaining handler body) | После Destroy() текущий обработчик вызывает обычную операцию компонента | Операция вызывает panic | Паника обрабатывается контрактом application-failure |
| 12. Уничтожение панели из обработчика ребёнка (Destroying the panel from a child handler) | Обработчик кнопки уничтожает панель; кнопка уничтожается каскадно | Кнопка логически уничтожена; Destroyed() и повторный Destroy() безопасны; обычное обращение вызывает panic | Пересечение Owner/Parent не приводит к повторному освобождению |

Таблица предназначена для сверки документационного контракта. Проверка реального отката, ресурсов и отображения потребует отдельной реализации и испытаний backend.

## Открытые вопросы

Актуальный остаток вопросов об очистке перечислен в [дизайне очистки](../../openspec/changes/define-cleanup-failure-contract/design.md#open-questions), а вопросы Post — в [дизайне изменения Post](../../openspec/changes/archive/2026-10-27-define-post-dispatch-contract/design.md#open-questions); [исторический реестр](../../openspec/changes/archive/2026-10-27-define-destruction-and-event-failure-contract/design.md#open-questions) сохраняет контекст решений о компонентах. Ниже перечислены оставшиеся вопросы; принятые правила Destroy/Destroyed, panic при обращении к уничтоженному объекту и выбранная политика сбоев очистки закрывают только часть Q-05. Q-04/Q-05/Q-06 и весь E0 не закрываются:

- Q-01: module path и проверка существующей лицензии перед изменением лицензионных решений; название Golphi уже принято.
- Q-02/Q-03: технические зависимости, bridge, первый Linux backend, версии Go/toolkit и платформенная матрица.
- Q-04: bootstrap и закрепление UI-потока, точная граница готовности при запуске Run, ограничения Run и проверка нарушения потоковых правил; судьба задач и закрытие приёма при обычной остановке, режим после возврата Run и повторный Run; ожидание результата, индивидуальная отмена, задачи с владельцем, получатель Post, точные ошибки отказа и ёмкость/перегрузка очереди. Принятие, очередь и отмена ещё не начатых задач при аварийной остановке описаны в [контракте Post](post-dispatch.md). Обычный Post не связан с владельцем: уничтожение захваченного компонента само по себе не отменяет задачу; Destroyed() безопасен, обычное обращение вызывает panic по общей политике аварийной остановки.
- Q-05: ошибки конструкторов и setters живых компонентов; публичный тип диагностической ошибки, API доступа, форматирование, представление стеков, способ объединения и порядок представления собранных сбоев. Порядок очистки зависимых ресурсов и определение зависимостей, повторные попытки и судьба неосвобождённых ресурсов, зависшие операции, тайм-ауты и принудительное прерывание остаются открытыми. Очистка без первичной паники, самостоятельный Destroy, ошибки запуска и сбои внутренних механизмов вне отдельных операций очистки также не определены. Возврат ошибки SetParent живого компонента, Destroy/Destroyed, обычные операции уничтоженного объекта, аварийная остановка при panic обработчика или Post и сохранение первичной причины со всеми собранными сбоями очистки уже согласованы.
- Q-06: сигнатуры событий и источник Program/User; обычная остановка при ожидающем OnChange; новое накопление после отсоединения и повторного присоединения в том же callback; взаимные изменения разных компонентов; порядок относительно Post и нативных событий. Замена обработчика без nil сохраняет текущий вызов и ожидающее уведомление с выбором получателя при доставке; отключение отменяет очередь и накопление, уничтожение отменяет все не начатые уведомления уничтоженных компонентов, успешное отсоединение отменяет OnChange поддерева. Эти принятые правила подробнее определены в [дельте component-events](../../openspec/changes/archive/2026-10-27-define-destruction-and-event-failure-contract/specs/component-events/spec.md); прочие сочетания остаются открытыми.
- Иерархия: проверка циклов Owner/Parent, смена Owner, перенос между формами или приложениями, присоединение к ещё не отображаемому контейнеру.
- Нативный жизненный цикл: момент создания, сохранения и конкретный механизм уничтожения представлений в пределах принятого разделения логического уничтожения и допустимой отсрочки освобождения; сохранение фокуса, выделения и курсора при пересоздании; механизм гарантированного отката SetParent.
- Q-07–Q-14: Close/Hide/завершение, модальность, layout, формат форм, поставка runtime, Qt, расширения и доступность остаются предложениями исходного документа.

Порядок обхода при уничтожении и способ освобождения пересекающихся связей примерами не выбираются. Проверяемость контракта на каждой платформе ещё предстоит доказать.
