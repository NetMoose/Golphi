# Передача задач Post на UI-поток Golphi

Документ фиксирует целевой контракт из [дельты post-dispatch](../../openspec/changes/archive/2026-10-27-define-post-dispatch-contract/specs/post-dispatch/spec.md), [дельты application-failure](../../openspec/changes/archive/2026-10-27-define-post-dispatch-contract/specs/application-failure/spec.md) и [дизайна изменения](../../openspec/changes/archive/2026-10-27-define-post-dispatch-contract/design.md). Это проектные трассировки для ручной проверки документации, а не подтверждение реализации runtime, очереди, backend или FFI. Они не закрывают E0 и не являются runtime-тестами T-01–T-09.

## Принятие и граница работы

`Post(fn) error` обозначает отправку функции без аргументов и результата. Получатель метода пока не выбран. `nil` подтверждает принятие в очередь, а не завершение; последующая аварийная остановка может отменить ещё не начатую задачу. Ошибка означает отказ без постановки и выполнения.

| Условия и действие | Наблюдаемый результат |
|---|---|
| Работающий runtime принимает допустимую функцию | `Post` возвращает `nil`; принятие само по себе не подтверждает выполнение |
| Runtime отклоняет задачу | Ошибка; функция не попадает в очередь и не выполняется |
| В работающем приложении вызывается `Post(nil)` | Сразу ошибка; нет задачи в очереди и аварийной остановки |
| `Post` вызывается до запуска `Form.Run()` | Ошибка; задача не накапливается для будущего запуска |
| `Post` вызывается после начала аварийной остановки | Ошибка без постановки |
| Принятая задача ещё не началась, затем начинается аварийная остановка | Задача отменена; ранее возвращённый `nil` остаётся подтверждением принятия |

Приём разрешён только во время работы приложения. Точная граница готовности при bootstrap не определяется первым входом в тело `Run`. Ни ёмкость очереди, ни перегрузка, ни дополнительные гарантии принимаемости или задержки здесь не устанавливаются.

## UI-поток и отсутствие рекурсии

`Post` безопасен для вызова из любой goroutine. Дошедшие до выполнения функции исполняются последовательно на UI-потоке, без одновременного выполнения другой функции `Post`, и могут обращаться к живым компонентам по обычным правилам UI-кода.

| Трассировка | Проверяемая последовательность |
|---|---|
| Фоновый отправитель обновляет живой компонент | Фоновая goroutine отправляет задачу → задача принята → при отсутствии отмены начинается на UI-потоке → обращается к живому компоненту → завершается |
| Отправка из обработчика события | Обработчик вызывает `Post(Б)` → Б поставлена в очередь без непосредственного вызова → обработчик продолжает работу и завершается → лишь затем Б может начаться |
| Отправка из выполняющейся задачи | А вызывает `Post(В)` → В поставлена в очередь без рекурсии → А продолжает работу и завершается → лишь затем В может начаться |

Постановка обязательна и с UI-потока. Для фонового отправителя не обещается, что выполнение начнётся только после возврата самого `Post`: ограничение относится к завершению текущего UI-обработчика или задачи. Механизм закрепления потока и пробуждения не выбран.

## FIFO и конкурентные отправители

| Трассировка | Условия | Результат |
|---|---|---|
| Последовательные отправки | А, Б, В приняты последовательно; отмены нет | Выполняются А → Б → В |
| Вложенная отправка за ожидающей работой | А выполняется; Б уже ожидает; А отправляет В; отмены нет | В добавляется в конец за Б; А завершается → выполняется и завершается Б → выполняется и завершается В; рекурсии нет |
| Два конкурентных отправителя | Две goroutine отправляют без дополнительного упорядочивания; обе задачи приняты и не отменены | Обе выполняются последовательно на UI-потоке; заранее первая не определена |
| Паника первой из конкурентно принятых задач | Обе приняты; первая выполняемая функция паникует; вторая ещё не началась | Вторая отменена и не выполняется; требование выполнения обеих применимо только без отмены |

FIFO ограничен очередью `Post`. Порядок относительно native events/`OnChange`, приоритет, квант обработки и справедливость не заданы.

## Аварийная остановка и гонка принятия

Паника прикладного обработчика или функции `Post` обнаруживается на границе прикладного вызова. С этого момента новые прикладные обработчики и задачи не запускаются, все ожидающие прикладные уведомления и ещё не начатые задачи `Post` отменяются, новые `Post` отклоняются.

| Трассировка | Проверяемая последовательность |
|---|---|
| Паника обработчика с ожидающими задачами | Обработчик паникует → обнаружение паники → все ещё не начатые задачи отменены → новые `Post` возвращают ошибку |
| Паника задачи с ожидающей работой | А вызывает `panic(V)`; ожидают Б и уведомление компонента → обнаружение на границе А → Б и уведомление отменены; новые обработчики и задачи не запускаются; новые `Post` отклонены |
| Принятие выигрывает гонку | `Post` принят до остановки и возвращает `nil` → функция ещё не началась → остановка отменяет её |
| Остановка выигрывает гонку | Остановка начинается до принятия конкурентного `Post` → тот возвращает ошибку без постановки и выполнения |

Гонка имеет один из двух наблюдаемых исходов, без состояния «ошибка, но задача поставлена». Это требование согласованности, а не выбор mutex, atomic или канала. Принудительное прерывание произвольной уже выполняющейся функции не обещается.

После обнаружения паники необходимые внутренние действия для выхода из прикладного вызова и callback продолжаются. Очистка выполняется после выхода из callback, без новых прикладных обработчиков и задач. Если очистка проходит без собственного сбоя, `Form.Run()` возвращает ненулевую ошибку с исходным V и стеком паники, а не только строкой сообщения. Полная политика и трассировки — в [контракте аварийной остановки](application-failure.md); расширение на `Post` задано указанной дельтой. Ошибки очистки, восстановление UI, повторный запуск и тип диагностики этим не выбираются.

## Захват уничтоженного компонента

Обычный `Post` не связан с владельцем. Захват компонента замыканием не создаёт владения, а уничтожение само по себе не отменяет задачу. Логическое уничтожение и допустимые операции определены [контрактом жизненного цикла](component-lifecycle.md).

| Трассировка | Проверяемая последовательность |
|---|---|
| Проверка перед обращением | Задача принята → захваченный компонент уничтожен → при отсутствии иной отмены задача запускается → `Destroyed()` безопасно возвращает `true` → задача пропускает обычные обращения; аварии нет |
| Обращение без проверки | Задача запускается и вызывает обычный метод уже уничтоженного компонента → возникает паника → на границе функции `Post` начинается та же аварийная остановка, что при панике обработчика |

Отложенное физическое освобождение не делает обычное обращение допустимым. Специальный API задач с владельцем и автоматическая отмена по владельцу остаются открытыми.

## Покрытие каждого сценария post-dispatch

Имена сценариев сохранены буквально для сопоставления с дельтой.

| Сценарий | Проверяемая трассировка выше |
|---|---|
| Accepted task | Принятие: допустимая функция, `nil` означает принятие |
| Rejected task | Принятие: ошибка, нет очереди и выполнения |
| Acceptance followed by failure | Принятие: авария до начала отменяет принятую задачу |
| Nil while running | Принятие: `Post(nil)` без аварии |
| Before Run | Принятие: отказ без накопления до `Run` |
| After failure shutdown begins | Принятие: отказ после начала остановки |
| Background caller updates a live component | UI-поток: фоновый отправитель обновляет живой компонент |
| Posting from an event handler | UI-поток: отправка из обработчика без вложенного вызова |
| Posting from a running task | UI-поток: отправка из задачи без рекурсии |
| Sequential submissions | FIFO: последовательные А → Б → В без отмены |
| Nested submission behind queued work | FIFO: А отправляет В за ожидающей Б |
| Concurrent submitters | FIFO: обе принятые функции выполняются только при отсутствии отмены; соседняя строка проверяет панику первой |
| Handler panic with queued tasks | Остановка: паника обработчика отменяет ожидающие задачи |
| Task panic with queued tasks | Остановка: паника задачи отменяет задачи и уведомления |
| Acceptance wins the race | Гонка: `nil`, затем отмена ещё не начатой функции |
| Shutdown wins the race | Гонка: ошибка без постановки |
| Guarded access after destruction | Захват: безопасный `Destroyed()` и пропуск работы |
| Unguarded access after destruction | Захват: обычный метод вызывает панику и остановку |

## Открытые вопросы и границы

Обычная остановка остаётся открытой: судьба уже принятых задач, момент закрытия приёма, `Close`/`Hide`, условия выхода, состояние после возврата `Run` и возможность повторного `Run` здесь не определяются. Правила аварийной остановки не переносятся на неё автоматически.

Также открыты ожидание результата и индивидуальная отмена; задачи с владельцем; точный получатель `Post` и публичные типы ошибок; ёмкость и перегрузка очереди; порядок относительно native events/`OnChange`, взаимные изменения компонентов, справедливость и бесконечные последовательности; bootstrap и закрепление UI-потока, граница готовности и ограничения `Run`; ошибки/паники очистки и их приоритет относительно исходной паники; внутренние сбои и алгоритмы FFI/backend.

Остальные вопросы событий, иерархии компонентов и Q-01–Q-14 сохраняются в [полном реестре изменения](../../openspec/changes/archive/2026-10-27-define-post-dispatch-contract/design.md#open-questions). Этот документ фиксирует только выбранную часть Q-04/Q-05/Q-06 и не завершает весь E0.
