# Аварийная остановка приложения Golphi

Документ фиксирует целевой контракт из [спецификации application-failure](../../openspec/changes/archive/2026-10-27-define-destruction-and-event-failure-contract/specs/application-failure/spec.md) и [дизайна исходного изменения](../../openspec/changes/archive/2026-10-27-define-destruction-and-event-failure-contract/design.md), расширенный [дельтой application-failure](../../openspec/changes/define-post-dispatch-contract/specs/application-failure/spec.md), [контрактом post-dispatch](../../openspec/changes/define-post-dispatch-contract/specs/post-dispatch/spec.md) и [дизайном Post](../../openspec/changes/define-post-dispatch-contract/design.md). Это проверяемое описание будущего поведения, а не подтверждение реализации runtime, FFI или конкретного backend. Оно не означает завершение E0.

## Граница сбоя и последовательность остановки

Golphi перехватывает панику на границе вызова прикладного обработчика событий или функции Post и начинает аварийную остановку приложения. Сразу после обнаружения паники новые прикладные обработчики и задачи Post не запускаются; все ожидающие прикладные уведомления приложения и все ещё не начатые задачи Post отменяются, включая уведомления других компонентов. Новые вызовы Post отклоняются с ошибкой без постановки задачи в очередь и без её выполнения.

Необходимые внутренние действия для выхода из текущего прикладного вызова и callback продолжаются. После выхода из callback выполняется очистка ресурсов приложения, без возобновления прикладных событий и запуска задач Post. После очистки без дополнительного сбоя `Form.Run()` возвращает ненулевую ошибку с исходным значением паники и её стеком. Обычная работа UI и повторный вызов упавшего обработчика не возобновляются.

```text
panic в прикладном обработчике или функции Post
    → обнаружение на границе прикладного вызова
    → запрет новых обработчиков и задач Post, отказ новых Post
    → отмена ожидающих уведомлений и ещё не начатых задач Post
    → необходимый внутренний выход из прикладного вызова и callback
    → очистка ресурсов приложения после выхода из callback
    → ненулевая ошибка Form.Run() с исходным значением паники и стеком
```

Это порядок наблюдаемых этапов, а не алгоритм перехвата, диспетчеризации или перехода через FFI. Последний этап предполагает очистку без собственного сбоя. Сохранение исходного значения означает, что диагностика не подменяет его одной строкой сообщения. Публичный тип ошибки, её форматирование, представление стека и API доступа к данным не выбираются.

## Трассировка паники при ожидающих уведомлениях

Исходно приложение работает: обработчик компонента А выполняется внутри callback, а у компонентов Б и В ожидают прикладные уведомления, а в очереди — ещё не начатые задачи Post. Обозначение `panic(V)` — псевдокод для паники с исходным значением V; сигнатуры обработчиков примером не устанавливаются. Очистка в этой трассировке проходит без дополнительной ошибки или паники.

| Шаг | Действие | Ожидаемое поведение |
|---|---|---|
| 1 | Прикладной обработчик А вызывает `panic(V)` | Сбой достигает границы перехвата прикладного обработчика |
| 2 | Golphi обнаруживает панику | Начинается остановка; новые прикладные обработчики и задачи Post больше не запускаются, новые Post отклоняются с ошибкой |
| 3 | У Б и В остаются не начатые уведомления | Эти уведомления, как и остальные ожидающие прикладные уведомления приложения и все ещё не начатые задачи Post, отменяются |
| 4 | Нужны внутренние действия для выхода из callback | Они выполняются; прикладные обработчики Б, В и других компонентов не вызываются |
| 5 | Выполнен выход из callback | Затем выполняется очистка ресурсов приложения; прикладные события не возобновляются |
| 6 | Очистка завершена без дополнительного сбоя | `Form.Run()` возвращает ненулевую ошибку, сохраняющую исходное V и стек паники |

Запрет распространяется на прикладные события всего приложения, а не только на событие или компонент А. Задачи Post отменяются по отдельному явному правилу, без их отождествления с прикладными уведомлениями. Ранее возвращённый Post результат nil подтверждает принятие, но не гарантирует выполнение при последующей аварии. Гонка принятия с остановкой имеет один из двух исходов: принятие до остановки с nil и последующая отмена ещё не начатой задачи либо отказ с ошибкой без постановки. Принудительное прерывание произвольной выполняющейся функции этим не обещается.

## Трассировка обращения к уничтоженному компоненту

Обычные операции уничтоженного компонента вызывают панику по [контракту жизненного цикла](component-lifecycle.md). Если такое обращение происходит в прикладном обработчике, применяется та же остановка приложения.

| Шаг | Действие | Ожидаемое поведение |
|---|---|---|
| 1 | Компонент уже логически уничтожен; выполняется прикладной обработчик | Физическое освобождение ресурса не определяет допустимость обращения |
| 2 | Обработчик обращается к компоненту обычным методом | Возникает паника ошибочного использования API |
| 3 | Паника достигает границы прикладного обработчика | Golphi перехватывает её, запрещает новые прикладные обработчики и задачи Post, отклоняет новые Post и отменяет ожидающие прикладные уведомления приложения и ещё не начатые задачи Post |
| 4 | Выполняется необходимый внутренний выход из callback | После выхода начинается очистка, без возобновления прикладных событий |
| 5 | Очистка проходит без дополнительного сбоя | `Form.Run()` возвращает ошибку с исходным значением этой паники и её стеком |

Безопасные `Destroy()` и `Destroyed() bool` не относятся к обычным операциям, вызывающим панику при обращении к уничтоженному объекту. Пример не выбирает значение паники ошибочного использования или публичный тип диагностической ошибки.

## Трассировка паники функции Post

Принятая функция Post А выполняется на UI-потоке; у компонентов ожидают прикладные уведомления, а в очереди — задачи Post Б и В. Обозначение `panic(V)` не выбирает публичный тип диагностики. Очистка в этой трассировке проходит без дополнительной ошибки или паники.

| Шаг | Действие | Ожидаемое поведение |
|---|---|---|
| 1 | Функция Post А вызывает `panic(V)` | Паника достигает границы вызова функции Post |
| 2 | Golphi обнаруживает панику | Начинается аварийная остановка; новые прикладные обработчики и задачи Post не запускаются |
| 3 | Остаются ожидающие уведомления и ещё не начатые задачи Б и В | Все такие уведомления и задачи приложения отменяются; новые Post отклоняются с ошибкой без постановки и выполнения |
| 4 | Требуются внутренние действия для выхода из прикладного вызова и callback | Эти действия продолжаются без новых прикладных обработчиков и задач Post |
| 5 | Выполнен выход из callback | Затем выполняется очистка ресурсов без возобновления прикладных событий и задач Post |
| 6 | Очистка завершена без дополнительного сбоя | `Form.Run()` возвращает ненулевую ошибку с исходным V и стеком паники, а не только текстом сообщения |

## Трассировка обращения к уничтоженному компоненту из Post

Обычный Post не связан с владельцем: захват компонента замыканием и последующее уничтожение компонента сами по себе задачу не отменяют.

| Шаг | Действие | Ожидаемое поведение |
|---|---|---|
| 1 | Компонент уничтожен до выполнения принятой функции Post | Уничтожение само по себе не отменяет задачу |
| 2 | Функция начинает выполнение и обращается к компоненту обычным методом | Возникает паника ошибочного использования API |
| 3 | Паника достигает границы функции Post | Применяются шаги 2–5 трассировки паники Post: запрет новых вызовов, отмена ожидающих уведомлений и задач, отказ новых Post, внутренний выход и последующая очистка |
| 4 | Очистка после выхода из callback проходит без дополнительного сбоя | `Form.Run()` возвращает ненулевую ошибку с исходным значением этой паники и её стеком |

Безопасная проверка `Destroyed()` может вернуть true, после чего задача пропускает обычные обращения без аварийной остановки. Она не является автоматической отменой задачи; значение паники обычного метода и тип ошибки Run остаются невыбранными.

## Соответствие сценариям спецификации

| Сценарий application-failure | Проверяемая трассировка |
|---|---|
| Panic with other component notifications pending | Первая таблица, шаги 1–3: остановка доставки, отмена уведомлений Б и В, запрет новых обработчиков |
| Invalid access from a handler | Вторая таблица: обычное обращение к уничтоженному компоненту приводит к той же остановке |
| Internal work during shutdown | Первая таблица, шаги 4–5: необходимый внутренний выход, затем очистка без прикладных обработчиков |
| Diagnostic return after successful cleanup | Первая таблица, шаг 6: ненулевая ошибка `Form.Run()` сохраняет V и стек после успешной очистки |
| Post panic stops all application delivery | Трассировка паники Post, шаги 1–3; шаги 4–6 связывают остановку с очисткой и возвратом Run |
| Destroyed component access from Post | Трассировка обращения из Post, шаги 1–4: паника обычного метода, общая остановка, очистка и исходная диагностика |
| Internal work after task panic | Трассировка паники Post, шаги 4–5; шаг 6 применим при успешной очистке |
| Task panic diagnostic return | Трассировка паники Post, шаг 6: после успешной очистки Run сохраняет исходное V и стек |

Таблицы предназначены для ручной проверки документационного контракта. Проверка реального перехвата, выхода из callback, очистки и диагностики потребует отдельной реализации и испытаний backend.

## Открытые вопросы и границы контракта

Контракт касается паники прикладного обработчика событий или функции Post. Он не определяет сбои внутренних механизмов или обычную остановку приложения. Следующие вопросы остаются открытыми:

- Обычная остановка: судьба уже принятых задач Post и момент закрытия приёма; режим после возврата Run и повторный Run. Порядок Post относительно native events/OnChange, bootstrap и точная граница готовности во время запуска Run, закрепление UI-потока и ограничения Run (оставшаяся часть Q-04).
- Ожидание результата и индивидуальная отмена Post; специальный API задач с владельцем; получатель Post, точные ошибки отказа, ёмкость очереди и перегрузка.
- Ошибки и паники самой очистки, их приоритет и объединение с первоначальной паникой. Приведённые трассировки не обещают результата при таком дополнительном сбое.
- Публичный тип диагностической ошибки, её форматирование, способ доступа к исходному значению и представление стека; конкретный алгоритм FFI и перехвата.
- Обычная остановка, `Close`/`Hide`, модальность и вложенные циклы; ошибки конструкторов и setters живых компонентов; остальные несогласованные части Q-05/Q-06.

Исторический [реестр открытых вопросов исходного изменения](../../openspec/changes/archive/2026-10-27-define-destruction-and-event-failure-contract/design.md#open-questions) сохраняет контекст Q-01–Q-14; актуальные границы выбранной части Post и остаток вопросов перечислены в [дизайне Post](../../openspec/changes/define-post-dispatch-contract/design.md#open-questions). Контракт не выбирает способ восстановления UI после паники или автоматический лимит событий.
