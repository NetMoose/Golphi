## 1. Назначение и статус решений

Цель проекта — создать самостоятельный GUI-фреймворк для Go с компонентной моделью, близкой по удобству разработки к Delphi VCL: формы, контролы, свойства, события, обработчики на Go и визуальное проектирование интерфейса.

Прикладной программист использует единый Go API. Фреймворк создаёт нативные элементы через Win32, GTK или Qt и скрывает различия toolkit там, где определён общий контракт поведения. Для обычной сборки приложения не требуется устанавливать сторонний C/C++-компилятор.

Пользователь прямо подтвердил намерение создать собственный независимый фреймворк. Конкретные зависимости, интерфейсы, порядок реализации backend и состав первой версии пока являются предложениями.

В документе используются три статуса:

| Статус | Значение |
|---|---|
| **Требование пользователя** | Прямо следует из запроса и уточнений пользователя |
| **Желаемая возможность** | Сформулирована пользователем как целевой идеал; срок реализации не согласован |
| **Предлагаемое решение** | Архитектурная рекомендация, требующая проверки и дальнейшего согласования |

Фактические ограничения Go, GTK, Qt и FFI сопровождаются ссылками на первичные источники. Формулировки поведения в разделах 3–16 описывают **предлагаемую спецификацию**, кроме явно выделенных принятых контрактов разделов 5–8. Узкий реестр принятых решений приведён в разделе 18; остальные архитектурные предложения остаются Proposed. Ни один из этих статусов не означает уже реализованную возможность.

Название Golphi и ориентир на VCL приняты пользователем: иной API допустим при продемонстрированных удобстве и логичности; полная совместимость с VCL не обещается. Согласованы часть E0 и узкий MVP раздела 1.1, а не весь этап.

Предлагаемая трактовка независимости: проект владеет публичным API, моделью компонентов, семантикой событий, layout, форматом форм и инструментами. Системные GUI-библиотеки и заменяемый механизм FFI могут оставаться внешними техническими зависимостями. Требование написать весь низкоуровневый код исключительно на Go пользователем отдельно не установлено.

### 1.1. Принятый узкий MVP и фактическая реализация

В репозитории уже есть экспериментальные `ui`, Win32/GTK4 backend и [единый пример](../examples/hello/main.go). Это не завершение E0, полного E1 или всех T-01–T-09. Принятый срез описан в [дизайне архивного изменения](../openspec/changes/archive/2026-10-28-implement-native-ui-mvp/design.md), [текущем API](components-mvp.md), [инструкции сборки](mvp-build.md) и [отчёте проверок](mvp-validation.md). Общие предложения ниже применяются к будущей полной библиотеке; при расхождении MVP руководствуется этим узким принятым срезом.

MVP: одна форма и статические Edit/Button/Label, прямые Win32/GTK4-вызовы, без публичного Application. `ui.NewForm()`, `ui.NewEdit(owner)`, `ui.NewButton(owner)`, `ui.NewLabel(owner)` создают логические объекты с Parent=nil. `SetParent(parent) error`, `SetTitle(string)`, `Text() string`, `SetText(string)`, `Destroy()`, `Destroyed() bool`, `button.SetOnClick(func())`, `edit.SetOnChange(func())`, `ui.Post(func()) error`, `form.Run() error` — экспериментальная поверхность, не стабильный API расширения.

Импорт ui закрепляет startup thread без native-загрузки; main последовательно строит дерево и вызывает Run на этом потоке. Процесс допускает одну попытку после предварительных проверок, включая неуспешный startup. Уничтоженная форма вызывает panic раньше проверок потока/допуска. Starting закрыт для Post; после подготовки backend, peers, свойств, геометрии, очереди и пробуждения единый Running открывает приём до прикладных событий, без ожидания paint. Обычное закрытие главной формы не отменяется: приём закрывается, не начатые Post/уведомления отменяются, текущий вызов завершается; очистка выполняется на UI-потоке. Run возвращает nil при успехе либо исходную ошибку запуска и все сбои очистки; первичная прикладная паника сохраняет прежний контракт. Значения/стеки паник сохраняются, независимая очистка продолжается. Стабильные публичные типы, формат диагностики и общий порядок зависимой очистки не выбраны.

До Run задаются `form.SetClientSize(width, height)` и `control.SetBounds(x, y, width, height)` в целых логических единицах: размеры > 0, координаты >= 0; неверные значения вызывают panic. Клиентская область точна, координаты фиксированы относительно Parent, размеры контролов минимальны и могут увеличиваться до нативного минимума темы, сохраняя native-вид. Автоматического устранения пересечений нет. На GTK4/X11 для запроса Edit 368×28 измерено 368×29, Button 160×32 — 160×34; Label 368×32 и клиентская область 400×180 точны. Это согласованное уточнение пользователя, не обещание одинаковых физических пикселей.

Фактическая Windows-машина уточнена пользователем: **Windows 11 Pro/amd64, build 26100, 100% (96 DPI)**; Windows 10 не проверена. Native-проба и обе автоматические native suites Windows пройдены; ручные сценарии общего примера подтверждены пользователем на Windows и Linux, узкий MVP принят. Матрица и свидетельства — в [отчёте проверок](mvp-validation.md). Qt, Auto, Panel, динамическая материализация, несколько окон, layout/resizing/DPI, формы и дизайнер остаются вне MVP.

Пять MVP-дельт синхронизированы с основными спецификациями, включая Scope трёх существовавших контрактов; исходное изменение архивировано 28 октября 2026 года. [Снимок Scope до синхронизации](mvp-scope-sync.md) сохранён как история переходного состояния. Исторические контракты и прежние архивы не переписываются.

## 2. Требования пользователя

### 2.1. Основные требования

| ID | Требование | Как будет проверяться |
|---|---|---|
| R-01 | Собственный независимый фреймворк | Публичная модель компонентов и поведение определяются проектом; существующий GUI-фреймворк не становится его скрытым основным ядром |
| R-02 | Прикладной API и обработчики событий на Go | Пример приложения содержит Go-компоненты и Go-функции, без использования типов GTK/Qt/Win32 в обычной логике формы |
| R-03 | Поддержка Windows и Linux | Один исходный код приложения собирается и работает в объявленной матрице обеих ОС |
| R-04 | Создание интерфейса через нативные API/toolkit | Backend создаёт реальные Win32-, GTK- или Qt-компоненты согласно своему контракту |
| R-05 | Формы, контролы, свойства и события | Пользователь может создать форму, разместить элементы и подключить обработчики |
| R-06 | Удобный запуск главной формы через `Run` | В публичном API предусмотрен сценарий создания формы и последующего вызова `Form.Run()` |
| R-07 | Сборка приложения без GCC и других сторонних компиляторов | Приложение собирается установленным Go toolchain без C/C++-компилятора; конкретный механизм предлагается в разделе 12 |

Перечень Win32, GTK и Qt задаёт целевое направление поддержки. Очерёдность появления этих backend не согласована. Готовые платформенные библиотеки должны быть совместимы с ОС и архитектурой запуска.

Пользователь ожидает подготовленные платформенные библиотеки. Предлагаемая поставка обычного Go-модуля вместе с готовым native runtime, а также прямые вызовы системных библиотек там, где отдельный мост не нужен, описываются как архитектурный вариант выполнения этого требования.

### 2.2. Желаемые возможности целевого продукта

| ID | Возможность | Уточнение |
|---|---|---|
| W-01 | Автоматический выбор платформенной реализации | ОС обычного Go executable задаётся при сборке; выбор доступного GTK/Qt внутри Linux-приложения можно выполнять при запуске |
| W-02 | Статическая линковка либо библиотеки рядом с executable | Go-часть и нативный runtime рассматриваются отдельно; полностью статическая компоновка GTK/Qt пока не доказана |
| W-03 | Визуальный редактор форм | Размещение компонентов, редактирование свойств и соответствий событий методам |
| W-04 | Сохраняемое описание формы | Файл содержит компоненты, свойства, структуру и привязки событий |
| W-05 | Редактор написан на Go поверх собственной библиотеки | Редактор становится полноценным приложением и практической проверкой фреймворка |

### 2.3. Уточнение термина «нативный»

Предлагаемое значение: Windows backend создаёт Win32 controls; Linux backend использует реальные виджеты выбранного GTK или Qt. Отдельный системный оконный handle у каждого компонента не является общим обещанием: Qt Widgets, например, использует собственную отрисовку через QStyle. [S4]

Для составных компонентов и компонентов с собственной отрисовкой потребуется отдельное описание того, какие части остаются нативными и какие обязанности выполняет фреймворк.

## 3. Границы первой версии

**Предлагаемая начальная матрица:**

| Параметр | Первый прототип | Целевое расширение |
|---|---|---|
| Windows | amd64, Win32 backend | Другие архитектуры и версии ОС после проверки |
| Linux | amd64, glibc, один выбранный GTK4 baseline | arm64, дополнительные окружения; musl — отдельное решение |
| Linux display | Проверка X11 и Wayland там, где их поддерживает выбранный runtime | Расширение проверенной матрицы |
| Qt | Учитывается при проектировании общего контракта | Отдельный backend через предварительно собранный мост |
| Формы | Программное создание | Загрузка описания и генерация Go |
| Дизайнер | Требования и модель метаданных | Минимальный редактор после проверки runtime |

Минимальные версии Windows, Go, GTK4, glibc и дистрибутивов нужно зафиксировать до объявления поддержки. Таблица не является заявлением о готовой совместимости.

Первый прототип ограничивается одним приложением с формой, полем ввода, кнопкой, подписью, простой колонкой и динамически создаваемой группой контролов. Он проверяет архитектуру, а не полноту набора компонентов.

Расширенный набор таблиц, деревьев, rich text, печати, docking и рисуемых компонентов планируется после базового runtime. Отсутствие этих функций в первом прототипе не исключает их из направления развития.

## 4. Модель архитектуры

### 4.1. Три уровня представления

| Уровень | Содержимое | Время жизни |
|---|---|---|
| **Описание формы** | Типы, постоянные ID, имена, начальные свойства, layout, ресурсы, привязки событий | Файл проекта и редактируемая модель дизайнера |
| **Экземпляр компонента Go** | Текущие свойства, связи Owner/Parent, обработчики и состояние жизненного цикла | Один экземпляр формы в приложении |
| **Нативное представление, peer** | HWND, GObject/QObject и другие ресурсы toolkit | От материализации до уничтожения на UI-потоке |

Шаблон формы может создавать несколько независимых экземпляров. Нативный handle не используется как постоянный ID в файле. Go-компонент существует до создания своего peer.

Описание формы хранит сохраняемые настройки. Текущее нажатие кнопки, активный callback, указатель на native object и другие временные данные туда не попадают.

### 4.2. Поток зависимостей

~~~mermaid
flowchart TD
    D["Дизайнер на Go"] --> F["Описание формы"]
    F --> G["Генератор и загрузчик"]
    G --> C["Go-компоненты"]
    A["Прикладная логика Go"] --> C
    D --> C
    C --> K["Свойства, события, lifecycle и layout"]
    K --> W["Win32 backend"]
    K --> T["GTK backend"]
    K --> Q["Qt backend"]
    W --> WA["Windows API"]
    T --> TA["GTK C API"]
    Q --> B["Собственный C ABI bridge"]
    B --> QA["Qt Widgets"]
~~~

Все стрелки показывают логические зависимости. Диаграмма не означает, что каждый компонент или вся библиотека должны поставляться отдельным бинарным файлом.

### 4.3. Состояние компонента

Управляемые свойства, такие как текст и доступность кнопки, имеют единый путь изменения в ядре. Backend сообщает о пользовательском вводе и фактическом состоянии платформы; ядро согласует значение и публикует событие.

Для свойств, которыми совместно управляют приложение и ОС, разделяются запрос и наблюдение. Например, желаемый размер окна отличается от фактического размера клиентской области. Фокус и фактическое масштабирование также поступают от платформы.

Не вводится обязательный цикл постоянного сравнения двух деревьев. Описание формы создаёт обычные Go-компоненты, которые затем изменяются методами.

### 4.4. Предварительное разделение пакетов

| Пакет или инструмент | Ответственность |
|---|---|
| `ui` | Публичные компоненты, события, приложение, общие типы layout |
| `internal/backend` | Внутренний контракт backend |
| `internal/backend/win32` | Win32 controls, сообщения, интеграция цикла событий |
| `internal/backend/gtk4` | GTK/GLib/GObject, сигналы, загрузка функций |
| `internal/backend/qt` | Будущий адаптер собственного Qt bridge |
| `form` | Схема, проверка, загрузка и описание компонентов |
| `cmd/uigen` | Генератор Go-кода |
| `cmd/designer` | Редактор форм |

Окончательная структура пакетов определяется при реализации с учётом запрета циклических зависимостей. Разделение ответственности важнее количества директорий.

## 5. Публичный Go API

### 5.1. Принципы

- Конструкторы и структуры Options задают начальные значения.
- Методы изменяют живой компонент.
- Обработчики являются типизированными Go-функциями или методами.
- Компоненты расширяются преимущественно композицией.
- Обычный переносимый API не содержит HWND, GtkWidget, QObject, unsafe.Pointer, native enums или типов purego.
- Специальные платформенные расширения при необходимости оформляются отдельно от переносимого API.
- Строковое обращение к свойствам допускается для инспектора и сериализации; оно не становится основным способом написания прикладного кода.

### 5.2. Эскиз будущей полной библиотеки

Работающий MVP использует [examples/hello](../examples/hello/main.go) и API раздела 1.1. Следующий исторический эскиз полной библиотеки иллюстрирует использование согласованных связей Owner/Parent и одного обработчика. Пакет `example.org/golphi/ui`, конструкторы, Options, сигнатуры callback и остальные ещё не согласованные методы — эскизы, не утверждённый публичный API и не проверенный компилятором пример. Аргумент конструктора здесь обозначает Owner, а не автоматическое присоединение.

~~~go
// Эскиз: имена конструкторов и полные сигнатуры ещё не утверждены.
form := app.NewForm(ui.FormOptions{Title: "Пример"})
panel := ui.NewPanel(form) // Owner = form, Parent = nil
button := ui.NewButton(form) // Owner = form, Parent = nil
button.SetText("Поздороваться")
button.SetOnClick(func(e ui.ClickEvent) {
    // Прикладная логика.
})
if err := panel.SetParent(form); err != nil {
    // Parent панели остаётся nil; возможна повторная попытка.
    return
}
if err := button.SetParent(panel); err != nil {
    // Parent кнопки остаётся nil; настройки и обработчик сохранены.
    return
}
if err := form.Run(); err != nil {
    // Политика ошибок Run ещё требует согласования.
    return
}
~~~

Создание с Owner без Parent, настройка и последующий `SetParent(parent) error` приняты; автоматическое присоединение конструктором не предполагается. Порядок элементов, перестановка и окончательные фабрики остаются открытыми.

Проектные примеры этапа 2: [жизненный цикл](contracts/component-lifecycle.md) содержит подготовку кнопки, перенос, ошибки, отсоединение и уничтожение; [события](contracts/component-events.md) — замену обработчика, тихую подготовку, отсоединённую панель и обе трассировки повторного `OnChange`.

### 5.3. Ошибки публичных методов

Вне принятого MVP раздела 1.1 и ранее принятых контрактов общая политика ошибок полной библиотеки ещё не утверждена. Предлагается:

- ошибки загрузки runtime и запуска возвращать из `Run`;
- ошибки чтения и проверки формы возвращать как обычные Go errors с путём к проблемному узлу;
- нарушение жизненного цикла, например обращение к уничтоженному объекту, выявлять явно;
- не скрывать неподдерживаемую возможность молчаливым изменением поведения.

Перед замораживанием API необходимо решить, какие setters возвращают error, какие ошибки считаются ошибками программиста и как приложение получает ошибки, возникшие во время работы цикла событий. В эскизе выше возврат ошибок setters намеренно не специфицирован.

Сигнатуры конструкторов и сообщение ошибок динамического создания также входят в этот контракт: успешное создание логического объекта не должно скрывать последующий сбой его материализации.

## 6. Запуск и UI-поток

### 6.1. Один runtime приложения

`Application` владеет выбранным backend, диспетчером задач и основным циклом событий. `Form.Run()` запускает соответствующее приложение с этой формой как главной.

Дополнительные формы используют тот же runtime. Отдельный вызов `Run` для каждого окна не создаёт независимые GUI-циклы.

Предлагаемые состояния приложения: `New`, `Starting`, `Running`, `Stopping`, `Stopped`, `Failed`. Экземпляр одноразовый: после завершения или ошибки запуска повторный `Run` не поддерживается в первом прототипе.

### 6.2. Порядок запуска

1. Проверить логическую модель и конфигурацию.
2. Подготовить требуемый UI-поток.
3. Выбрать backend и проверить доступность нужного runtime.
4. Инициализировать backend.
5. Создать peers и применить начальные свойства.
6. Выполнить измерение и layout.
7. Показать главную форму и начать обслуживание событий.
8. При завершении остановить приём новой работы и освободить ресурсы на UI-потоке.

Некоторым операциям может потребоваться уже обслуживаемый нативный context. Точный порядок показа и сигнализации готовности проверяется в адаптере; пользовательский код не должен зависеть от частично созданного дерева.

При ошибке на этапе материализации все успешно созданные peers освобождаются. Приложение переходит в `Failed`; ошибка включает стадию и компонент, если он известен.

В состоянии `Running` новые компоненты создаются и материализуются на UI-потоке. Ошибка добавления компонента или группы освобождает частично созданные peers и не оставляет частично присоединённое дерево. Для `SetParent` действует принятый откат из раздела 8; правила передачи остальных ошибок вызывающему коду и окончательные сигнатуры фабрик остаются вопросами E0; частный отказ добавления компонента не приравнивается автоматически к сбою всего приложения.

### 6.3. Контракт потоков

Большинство GTK widgets привязаны к главному потоку GTK; Qt GUI-классы и основной event loop также имеют требования к main thread. [S2], [S5]

Предлагается более простой общий контракт: после запуска создание, изменение, чтение изменяемого состояния и уничтожение UI-компонентов выполняются на UI-потоке. До запуска логическое дерево строится последовательно вызывающим кодом.

`Run` вызывается из `main`. Конкретный bootstrap должен гарантировать правильный поток с начала нативной инициализации. `runtime.LockOSThread` закрепляет текущую goroutine за текущим потоком; вызов в произвольной goroutine не переносит её на startup thread. Документация Go отдельно описывает закрепление startup thread через `init`. Для MVP закрепление startup thread через init принято; общий bootstrap полной библиотеки вне MVP остаётся предложением. [S6]

Принята только узкая гарантия доставки: `Post(fn) error` безопасен из любой goroutine; принятые функции, дошедшие до выполнения, выполняются последовательно на UI-потоке и могут обращаться к живым компонентам по обычным правилам UI-кода. Это не утверждает весь предложенный выше контракт потоков, bootstrap, ограничения `Run` или проверку нарушения потоковых правил. Точная граница готовности во время запуска `Run` полной библиотеки вне MVP остаётся открытой; первый вход в тело `Run` сам по себе её не определяет.

### 6.4. Доставка фоновой работы

Принято: `Post(fn) error` принимает функцию без аргументов и результата. `nil` означает принятие в очередь, а не завершение и не гарантию выполнения при последующей аварии. Ошибка означает отказ без постановки и выполнения. `Post(nil)` сразу возвращает ошибку без аварийной остановки. Задачи принимаются только во время работы приложения; до запуска `Form.Run()` они отклоняются и не накапливаются. В MVP выбран пакетный ui.Post; окончательный получатель полной библиотеки (app/form/package), точные типы ошибок, ёмкость и политика перегрузки очереди не выбраны.

Каждая принятая функция ставится в очередь, включая вызов с UI-потока; непосредственного вызова внутри `Post` нет. Отправленная из обработчика или задачи функция не начинается до завершения текущего вызова. Для фонового отправителя не обещается, что выполнение обязательно начнётся лишь после возврата `Post`. Механизм очереди и пробуждения event loop остаётся предложением реализации; длительные вычисления и I/O предлагается выполнять в goroutine.

Последовательно принятые задачи выполняются FIFO, если не отменены. Вложенный `Post` добавляет задачу в конец: выполняется А, ожидает Б, А отправляет В — завершение А → Б → В без рекурсии. Порядок конкурентных отправителей заранее не обещается; обе принятые задачи выполнятся последовательно лишь при отсутствии отмены. Порядок относительно native events/`OnChange`, квант обработки и справедливость не определены.

При обнаружении паники обработчика или функции `Post` приём закрывается, все ещё не начатые задачи отменяются, новые `Post` отклоняются с ошибкой. Гонка с остановкой имеет однозначный исход: принятие до остановки с `nil` и последующая отмена ещё не начатой задачи либо отказ с ошибкой без постановки. Принудительное прерывание произвольной выполняющейся функции не обещается. Общая очистка и диагностика описаны в разделе 7.4.

Обычный `Post` не связан с владельцем: захват компонента замыканием не создаёт связи владения, а уничтожение компонента само по себе задачу не отменяет. Функция может безопасно проверить `Destroyed()` и пропустить обычные обращения. Обычный метод уничтоженного объекта вызывает панику; при достижении границы функции `Post` применяется общая аварийная остановка.

Обычная остановка, режим после возврата Run и запрет повторной попытки для MVP приняты в разделе 1.1; их общий контракт вне MVP, ожидание результата, индивидуальная отмена и специальный API задач с владельцем остаются открытыми. Синхронный `Invoke` остаётся предложением вне первого среза; его повторный вход и ожидание требуют отдельного решения. Подробные трассировки — в [контракте Post](contracts/post-dispatch.md).

## 7. Свойства и события

### 7.1. Принятый контракт текста

Визуальный компонент присоединён, если цепочка его `Parent` достигает формы. Ненулевого непосредственного Parent недостаточно: поле внутри отсоединённой панели также отсоединено. Owner и видимость не определяют присоединённость; работающий runtime — отдельное условие доставки.

| Условие | Поведение |
|---|---|
| Работающий присоединённый компонент; реальное изменение текста пользователем или через `SetText` | `OnChange` вызывается; до вызова `Text()` уже возвращает новое значение |
| Присваивание текущего текста | `OnChange` не возникает |
| Подготовка до запуска или изменение отсоединённого компонента | Текст обновляется без `OnChange`, даже если обработчик уже назначен |
| Последующее присоединение | Отображается подготовленный текст; подготовительные уведомления не воспроизводятся |

Предлагается нормализовать дубли нативных уведомлений в ядре. Алгоритм нормализации, сигнатуры событий и представление источника `Program/User` ещё не утверждены. Контракт текста не утверждает автоматически поведение всех прочих свойств и событий.

### 7.2. Один заменяемый обработчик

Принято: у каждого события в основном API не более одного прикладного обработчика. `SetOnClick(handler)` заменяет прежний обработчик, `SetOnClick(nil)` отключает его; то же правило действует для других событий. Предложение нескольких подписок и `Disconnect` заменено этим решением. Внутренние соединения backend им не определяются.

Если А заменён на Б между событиями, следующее событие вызывает только Б. При замене уже выполняющегося обработчика текущий вызов продолжается как обычно; последующая доставка выбирает обработчик, установленный на момент доставки. Замена ненулевого `OnChange` другим ненулевым сохраняет ожидающее уведомление и накопление, не сбрасывая базу сравнения.

### 7.3. Изменения внутри собственного OnChange

Изменения текста внутри собственного `OnChange` применяются сразу без вложенного вызова. Пока уведомление не отменено, после завершения обработчика итоговый текст сравнивается с текстом **на входе в этот обработчик**, а не до первоначального события; после отключения используется новая база по правилу ниже. Различие даёт одно отложенное повторное уведомление с итоговым текстом, равенство — ни одного. При неизменном обработчике и непрерывно живом, работающем, присоединённом компоненте А → Б → В даёт одно повторное уведомление для В, а А → Б → А — ни одного. Рекурсия и очередь всех промежуточных значений отвергнуты.

Приняты следующие области отмены:

| Причина | Ожидающие уведомления и текущий вызов |
|---|---|
| Логическое уничтожение | Все ещё не начатые прикладные уведомления каждого уничтоженного компонента отменены, включая каскад; текущий обработчик продолжается, но обычные обращения к уничтоженному объекту вызывают `panic` |
| Успешное отсоединение компонента или предка | Ожидающие `OnChange` всего отсоединённого поддерева отменены без восстановления при присоединении; отдельное правило прерывания текущего вызова этим не вводится |
| Ошибка `SetParent` | Уведомления сохраняются вместе с прежним состоянием |
| Замена ненулевого `OnChange` другим ненулевым | Уведомление и накопление сохранены, текущий вызов завершается как обычно; при доставке выбирается текущий обработчик |
| `SetOnChange(nil)` | Отменены и ожидающее уведомление, и изменения, накопленные внутри текущего обработчика; текущий вызов продолжается |

Назначение обработчика после `nil` не восстанавливает отменённое уведомление и само не создаёт события. Прежняя база сравнения сбрасывается. Первое реальное изменение после назначения нового обработчика создаёт новое основание для уведомления с базой — текстом непосредственно до этого изменения. Внутри текущего callback сохраняются объединение и отложенная доставка без рекурсии.

Обязательная трассировка: вход с А → `SetOnChange(nil)` → текст Б → назначение нового обработчика → текст А → выход. Новая база — Б; после выхода новый обработчик получает один отложенный `OnChange` с А, хотя итог совпал со входом в старый вызов. Без нового изменения после назначения уведомления нет. Замена без `nil` базу не сбрасывает.

Хранение признака доставки, входного текста или поколения накопления — предложения реализации. Новое накопление после отсоединения и повторного присоединения в том же callback остаётся открытым: отсоединение не приравнивается к сбросу через `nil`. Обычная остановка вне MVP, взаимные изменения разных компонентов, очередь относительно `Post` и нативных событий, справедливость и диагностика бесконечных изменений остаются открытыми; автоматический лимит не принят. Подробные трассировки приведены в [контракте событий](contracts/component-events.md).

### 7.4. Отменяемые события и сбои обработчиков

Отменяемые события предлагается отделять от уведомлений. Их сигнатуры, политика отмены, модальные диалоги и вложенные циклы событий требуют отдельного решения. Аналогия с VCL не утверждает синхронный API. Предложение не вызывать пользовательский код под внутренним mutex сохраняется.

Принято: Golphi перехватывает панику на границе вызова прикладного обработчика событий или функции `Post` и начинает аварийную остановку приложения. Сразу после обнаружения сбоя новые прикладные обработчики и задачи `Post` не запускаются, все ожидающие прикладные уведомления приложения и все ещё не начатые задачи `Post` отменяются; новые `Post` отклоняются с ошибкой без постановки и выполнения. Необходимые внутренние действия для выхода из текущего прикладного вызова и callback продолжаются; после выхода выполняется очистка ресурсов без возобновления прикладных событий и задач `Post`. После завершения попыток очистки `Form.Run()` возвращает ненулевую ошибку с первоначальной паникой, её значением и стеком и всеми собранными сбоями очистки. Ошибки очистки дополняют исходную диагностику; для каждой перехваченной паники очистки сохраняются её значение и стек. Перехваченные паники очистки повторно наружу не выбрасываются. Первоначальная причина не подменяется последним сбоем или одной строкой сообщения, а набор ошибок очистки не ограничивается первой ошибкой.

Ошибка отдельной операции очистки не прекращает попытки очистить остальные независимые ресурсы. Паника очистки перехватывается на границе отдельной операции с сохранением её значения и стека; затем продолжаются попытки остальных независимых операций, а не тело упавшей операции. Запрет новых прикладных обработчиков и задач, отмена ожидающих и отказ новых `Post` сохраняются во время очистки и после её сбоя. Завершение попыток не гарантирует освобождения всех ресурсов. Порядок очистки зависимых ресурсов и определение зависимостей не выбраны.

Паника обычного обращения к уничтоженному объекту внутри обработчика или функции `Post` приводит к той же остановке. Обычная работа UI и повтор упавшего вызова не возобновляются. Открыты публичный тип ошибки, форматирование, представление стеков, API доступа, способ объединения и порядок представления собранных сбоев; повторные попытки и судьба неосвобождённых ресурсов; зависшие операции, тайм-ауты и принудительное прерывание. Обычная остановка и очистка без первоначальной паники и ошибки запуска для MVP определены в разделе 1.1; самостоятельный `Destroy`, сбои внутренних механизмов вне отдельных операций очистки и общий контракт полной библиотеки этим контрактом не определены. Для MVP приняты прямые native-вызовы и перехват на границе callback; общий механизм полной библиотеки вне MVP остаётся открытым. См. [контракт аварийной остановки](contracts/application-failure.md), [контракт Post](contracts/post-dispatch.md) и [дизайн очистки](../openspec/changes/archive/2026-10-27-define-cleanup-failure-contract/design.md). Эти решения закрывают лишь часть Q-05/Q-06, не весь E0.

## 8. Владение и уничтожение

### 8.1. Независимые Owner и Parent

Принято: Owner определяет владение, Parent — визуальное размещение. Это две независимые связи. Смена Parent сохраняет Owner; визуальный компонент можно создать с Owner без Parent, настроить свойства и обработчики, затем присоединить.

`SetParent(parent) error` либо завершает перенос, либо возвращает ошибку и сохраняет прежние Parent, Owner, все настройки, обработчики и работоспособность прежнего размещения. Частичные ресурсы неуспешного переноса освобождаются. При ошибке первого присоединения Parent остаётся nil. Восстановить только поле Parent недостаточно: прежнее отображение должно оставаться работоспособным.

Успешный `SetParent(nil)` убирает компонент и его визуальное поддерево из отображаемого интерфейса, сохраняя Owner, настройки, обработчики и связи Parent внутри поддерева. Поддерево можно присоединить повторно. Это отсоединение, не уничтожение.

При уничтожении каскад охватывает принадлежащие компоненты и визуальных потомков независимо от их Owner. Уничтожение панели уничтожает кнопку с Owner = форма; кнопка исключается также из компонентов формы, поэтому последующее уничтожение формы не освобождает её ресурсы повторно. Уничтожение владельца отсоединённой панели уничтожает панель и её визуальных потомков. Уничтожаемые объекты исключаются из обеих связей без повторного освобождения при пересечении деревьев.

Порядок обхода, проверка циклов, смена Owner, перенос между формами/приложениями и присоединение к ещё не отображаемому контейнеру остаются открытыми. Подготовка нового peer до фиксации связи — предложение реализации; момент создания, сохранения или пересоздания native peers, сохранение фокуса/выделения/курсора и механизм гарантированного отката не выбраны.

### 8.2. Разные операции

| Операция | Статус и значение |
|---|---|
| `SetParent(nil)` | Принято: отсоединяет с сохранением компонента и поддерева |
| Hide | Предложение: скрывает форму или контрол с сохранением экземпляра и ресурсов |
| Close | Предложение: запрашивает отменяемое закрытие формы |
| `Destroy()` | Приняты каскад раздела 8.1, немедленное логическое уничтожение и безопасный повтор; обычные операции уничтоженного объекта вызывают `panic` |
| Завершение приложения | Аварийная остановка при панике обработчика или функции Post принята в разделе 7.4; для MVP закрытие главной формы принято в разделе 1.1; общий порядок вне MVP открыт |

Для MVP закрытие главной формы завершает приложение; действие после Close и условие выхода полной библиотеки вне MVP остаются открытыми. Закрытие главной формы с завершением приложения и уничтожение вспомогательной формы — предварительные варианты.

`Destroy()` немедленно делает компонент логически уничтоженным. `Destroyed() bool` безопасен и после этого возвращает `true`. Повторный `Destroy()` ничего не меняет, включая период до физического освобождения, и не инициирует повторного освобождения. Обычные операции уничтоженного объекта — getters, setters и `SetParent` — вызывают `panic`; возвращаемый `error` у `SetParent` этого не заменяет. Исключения — безопасные `Destroy()` и `Destroyed()`.

Физическое освобождение при необходимости допускается отложить до выхода из callback; логическое уничтожение уже произошло. Уже выполняющийся обработчик продолжает работу, если сам не вызывает `panic`, но обычное обращение к уничтоженному объекту из оставшейся части обработчика вызывает панику по разделу 7.4. Правила действуют для каждого компонента каскада Owner/Parent и сохраняют отсутствие повторного освобождения при пересечении деревьев. Порядок обхода и конкретный механизм освобождения не выбраны. Подробные примеры — в [контракте жизненного цикла](contracts/component-lifecycle.md).

### 8.3. Идентификаторы и callbacks

Предлагается различать постоянный ID узла формы, ID экземпляра в runtime и native handle. Реестр должен обнаруживать запоздалые события уничтоженного экземпляра, включая повторное использование слота.

Ограниченный набор native callback-dispatchers и реестр Go-обработчиков остаются предложением, учитывающим ограничения `purego.NewCallback`. [S1] При уничтожении предлагается отключать нативные соединения, очищать прикладные обработчики и записи реестра. Финализатор Go не предлагается как основной механизм своевременного уничтожения GUI. Конкретный механизм освобождения ресурсов ещё не выбран.

## 9. Layout и масштабирование

### 9.1. Собственный layout

Предлагается хранить правила раскладки в общем Go-ядре. Backend измеряет native control в текущем окружении и применяет результат размещения.

Начальные понятия:

- логические единицы измерения;
- минимальный и предпочтительный размер;
- ограничения ширины и высоты;
- отступы;
- строки и колонки;
- явные правила растяжения.

Align, Anchors, grid и ручное позиционирование добавляются с определёнными правилами взаимодействия. Один прямоугольник не должен одновременно назначаться независимыми конкурирующими алгоритмами.

### 9.2. Измерение

До появления peers и реального окружения точный размер native control может быть неизвестен. API не обещает точные метрики до готовности backend.

Смена DPI, шрифта, темы, текста или состава детей инвалидирует нужные измерения. Округление при переходе к физическим пикселям должно выполняться последовательно, чтобы соседние элементы не накапливали зазоры.

Проверка переносимости оценивает структуру формы, доступность содержимого и удобство взаимодействия. Пиксельное совпадение разных toolkit не является критерием готовности.

## 10. Нативные backend

### 10.1. Внутренний контракт

Общий peer имеет только применимые ко всем визуальным компонентам операции. Возможности отдельных controls выражаются отдельными интерфейсами.

~~~go
// Эскиз внутренних интерфейсов, а не готовая реализация.
type ControlPeer interface {
    Measure(Constraints) Size
    Arrange(Rect)

    SetVisible(bool)
    SetEnabled(bool)

    Destroy()
}

type EditPeer interface {
    ControlPeer

    SetText(string)
    SetReadOnly(bool)
}
~~~

Фабрики, ошибки операций и обратная передача событий здесь опущены. Перед реализацией этот эскиз должен быть дополнен минимальным полным контрактом.

Backend-specific операции не включаются в общее ядро только ради удобства первой платформы. Возможность, отсутствующая у одного backend, получает либо согласованную реализацию, либо явный статус неподдерживаемой.

### 10.2. Win32

Предлагается прямой backend на Go, использующий системные DLL. Пакет `golang.org/x/sys/windows` предоставляет необходимые механизмы загрузки библиотек и вызова процедур. Собственная дополнительная DLL не является обязательной частью этого пути. [S9]

Внутренние обязанности: цикл сообщений, привязка native handle к компоненту, нормализация уведомлений, управление ресурсами и нативными настройками внешнего вида.

### 10.3. GTK4

Предлагается прямой вызов GTK/GLib/GObject C API через заменяемый FFI-адаптер на основе purego. Выбранная версия FFI и комбинации Go/OS/CPU фиксируются и проверяются; отсутствие CGO не означает отсутствие GTK runtime. [S1]

Загрузка выполняется по этапам: поиск разрешённого runtime, загрузка библиотек, проверка обязательных symbols, контролируемая инициализация GUI. Для ошибки подключения к оконной системе используется механизм, допускающий возврат ошибки, например `gtk_init_check()`. [S3]

FFI не освобождает разработчиков backend от проверки сигнатур, layout структур и времени жизни памяти. Долгоживущие ссылки на Go-память не передаются в native code без отдельного доказанного механизма владения. [S1]

### 10.4. Qt

Qt Widgets предоставляет C++ API. [S4] Предлагается собственный предварительно собранный C++ bridge с C ABI.

Минимальные обязанности bridge:

- собственная версия ABI и проверка совместимости;
- непрозрачные handles;
- простые типы аргументов, явные длины и правила владения буферами;
- единая кодировка текстового интерфейса, предварительно UTF-8;
- перевод Qt signals и нужных virtual handlers в события фреймворка;
- обработка C++ exceptions внутри моста;
- корректное освобождение ресурсов на UI-потоке.

Наличие `extern "C"` само по себе не решает совместимость Qt, lifetime или обработку ошибок. Это части собственного контракта bridge.

Qt backend не объявляется готовым в первом прототипе. Его будущие требования учитываются при проектировании UI-потока и общего API.

## 11. Выбор backend и диагностика

### 11.1. Два разных уровня выбора

Go собирает отдельные executable для соответствующих GOOS/GOARCH; платформенные файлы включаются ограничениями сборки. Это отличается от выбора GTK или Qt при запуске Linux-приложения. [S10]

GTK и Qt рассматриваются как доступные toolkit, а не как взаимоисключающие операционные окружения. Оконная система X11/Wayland находится на другом уровне и обслуживается выбранным toolkit.

### 11.2. Предлагаемая политика

1. Явно заданный backend имеет приоритет.
2. Иначе используется политика комплекта поставки приложения.
3. В режиме Auto проверяются допустимые и совместимые кандидаты.
4. Рабочее окружение может влиять на предпочтение среди работоспособных кандидатов.
5. Выбор фиксируется до создания native UI и сохраняется до конца процесса.

В E1 режим Auto выбирает единственный поддерживаемый backend текущей платформы: Win32 или GTK4. Выбор между GTK и Qt внутри Linux и расширенные правила предпочтений появляются в E5. Поэтому использование BackendAuto в эскизе API не предполагает готовность Qt в первом прототипе.

Успешная загрузка файла библиотеки ещё не доказывает готовность backend. Проверяются обязательный API, транзитивные зависимости и возможность инициализации display.

Автоподбор не строится на предположении, что любую частично инициализированную GUI-систему можно безопасно откатить. Где инициализация не предоставляет контролируемой ошибки, нужен отдельный способ предварительной проверки или иной сценарий выбора.

### 11.3. Диагностика

Ошибка должна сообщать backend и стадию: поиск runtime, загрузка, обязательный symbol, display, создание компонента либо завершение. При возможности добавляются ID компонента и исходная платформенная ошибка.

Для диагностики нужен отчёт о выбранном backend и версиях фактически использованных библиотек. Он не должен требовать от обычного прикладного кода знания native API.

## 12. Сборка и поставка

### 12.1. Разделение ответственности

| Участник | Предлагаемый набор инструментов |
|---|---|
| Разработчик обычного приложения | Go toolchain; при использовании форм — генератор, написанный на Go |
| Команда фреймворка | Go и необходимые инструменты изготовления native artifacts, включая C++ toolchain для Qt bridge |
| Пользователь готового приложения | Executable и доступный согласованный runtime; компилятор не требуется |

Проверяемая техническая цель для базового пути — `CGO_ENABLED=0 go build`. Go module поставляется с исходниками и компилируется вместе с приложением. Нативные части, которым нужен другой toolchain, выпускаются заранее.

Обычный CGO workflow использует C/C++-компилятор; готовый .a или .lib сам по себе не доказывает возможность сборки приложения без этого workflow. [S8]

### 12.2. Варианты комплекта поставки

| Backend | Предлагаемый базовый состав |
|---|---|
| Win32 | EXE с Go-частью; системные DLL Windows |
| GTK, системный runtime | Go executable; явно поддерживаемая установленная версия GTK и зависимости |
| GTK, runtime в комплекте | Executable и подготовленный комплект библиотек, ресурсов и правил поиска |
| Qt | Executable, собственный bridge, необходимые Qt libraries/plugins и другие зависимости либо поддерживаемая системная установка |

Qt deployment требует учитывать runtime libraries и plugins. Размещение одной собственной .so рядом с приложением не гарантирует наличия остальных зависимостей и корректного поиска библиотек. [S7]

Для первого прототипа предлагается системный GTK runtime в зафиксированной среде. Выбор формата распространения Linux-приложения для конечных пользователей остаётся открытым.

### 12.3. Статическая компоновка

Go-часть включается в executable обычной сборкой. Полное статическое включение GTK/Qt и их зависимостей в Go executable не входит в доказанный базовый путь.

Такой вариант не объявляется принципиально невозможным, но требует отдельного исследования компоновки, зависимостей и условий распространения.

Встраивание готовой .so в ресурсы executable с последующим извлечением относится к упаковке. Во время работы библиотека остаётся динамической.

### 12.4. Версионирование и воспроизводимость

Предлагается фиксировать версии Go module, FFI, native bridge и поддерживаемого runtime baseline. Сборка приложения должна использовать совместимый заранее выбранный комплект; случайная подмена найденной библиотеки не считается допустимой политикой обновления.

Перед релизом документируются минимальные версии и проверенные комбинации. Поддержка новой CPU-архитектуры или другой libc требует собственной проверки ABI и runtime.

## 13. Описание форм и генерация Go

### 13.1. Предлагаемый формат

Предлагается начать с JSON, используя штатные средства Go. Это выбор для обсуждения; окончательная схема ещё не утверждена.

Фрагмент формы:

~~~json
{
  "schemaVersion": 1,
  "id": "main-form",
  "type": "Form",
  "name": "MainForm",
  "properties": {
    "title": "Пример"
  },
  "children": [
    {
      "id": "greet-button",
      "type": "Button",
      "name": "GreetButton",
      "properties": {
        "text": "Поздороваться"
      },
      "events": {
        "click": "Greet"
      }
    }
  ]
}
~~~

Это фрагмент, демонстрирующий идентичность, свойства и события. Полная схема должна дополнительно описать layout, ресурсы, типы значений и правила вложенности.

### 13.2. Метаданные компонентов

Единый каталог содержит имя типа, фабрику, свойства, defaults, ограничения, сериализацию, события и редакторы свойств.

Сохраняемые свойства отделяются от наблюдаемого runtime-состояния. Метаданные согласуются с типизированным Go API; инспектор не создаёт параллельную независимую систему поведения.

Проверка файла выявляет дубликаты ID, неизвестные типы, неподдерживаемую версию схемы, недопустимые значения и неверные связи. Ошибки содержат путь к узлу.

### 13.3. Разделение файлов приложения

| Файл | Назначение |
|---|---|
| `main.form.json` | Исходное описание интерфейса |
| `main_form_gen.go` | Сгенерированные поля, создание дерева и привязки |
| `main_form.go` | Пользовательская логика и методы |

Описание формы остаётся источником структуры интерфейса. Генератор не пытается восстановить форму из произвольной логики Go.

Привязка события превращается в обычный Go-вызов:

~~~go
f.GreetButton.SetOnClick(f.Greet)
~~~

Пользовательский обработчик хранится в отдельном файле:

~~~go
func (f *MainForm) Greet(e ui.ClickEvent) {
    f.ResultLabel.SetText("Привет!")
}
~~~

Генерация должна быть детерминированной, сохранять пользовательские файлы и давать обычные ошибки компиляции при несовпадении метода или сигнатуры. Генератор можно запускать из дизайнера либо через `go generate`; `go build` не выполняет `go generate` автоматически. [S10]

### 13.4. Загрузка во время исполнения

Загрузчик создаёт те же компоненты, что и сгенерированный код. Он получает явный реестр допустимых обработчиков или другой типизированный механизм связывания.

Файл формы не содержит исполняемый Go-текст. Runtime не предполагает динамическую компиляцию или выполнение произвольных функций по одному строковому имени.

Совместимость схемы, сохранение неизвестных свойств и правила миграций должны быть определены до выпуска формата для сторонних пользователей.

## 14. Визуальный редактор и расширения

### 14.1. Назначение редактора

Редактор пишется на Go поверх собственного фреймворка. Он работает с обычным Go-проектом и формирует файлы, которые можно хранить в Git.

Минимальный состав:

- палитра компонентов;
- дерево формы;
- инспектор свойств;
- выбор, перемещение и изменение размеров;
- настройка layout;
- привязка события к Go-методу;
- undo/redo;
- сохранение и загрузка формы;
- генерация и запуск предпросмотра.

### 14.2. Режим дизайна

Редактор имеет отдельный DesignHost. Клик выбирает компонент; рамки выделения и перетаскивание не зависят от прикладных обработчиков.

Пользовательская логика запускается в отдельном процессе предпросмотра. При падении или зависании приложения модель редактируемой формы должна оставаться доступной.

Полнота перехвата ввода над вложенными native controls проверяется отдельно: использование того же toolkit само по себе не создаёт дизайнер.

### 14.3. Собственные компоненты

Предлагаются три способа расширения:

| Способ | Обязанности автора |
|---|---|
| Составной компонент | Комбинация стандартных controls, собственные свойства и события |
| Рисуемый компонент | Контракт рисования, ввод, фокус, прокрутка и доступность |
| Специальный native component | Backend-адаптеры и явная матрица возможностей |

Первый способ нужен раньше остальных. Для подключения такого компонента к дизайнеру регистрируются его тип и метаданные.

Начальный вариант расширения дизайнера — пересборка с нужными Go-пакетами. Динамические Go plugins не принимаются как универсальная основа: стандартный plugin имеет ограничения платформ и совместимости toolchain/dependencies. [S11]

## 15. Первый прототип и критерии приёмки

### 15.1. Сценарий

Одна форма содержит поле ввода имени, кнопку и подпись. Прикладной обработчик читает текст и меняет подпись. Вторая операция запускает фоновую задачу и передаёт результат через Post.

Вспомогательный сценарий многократно создаёт и уничтожает группу контролов с обработчиками. Окно можно изменять в размерах, переключать фокус клавишей Tab и закрывать с возможностью отмены.

Один исходный код используется на Windows и Linux. Реализация узкого MVP создана; результаты её проверок приведены в [отчёте MVP](mvp-validation.md). Критерии полного E1 ниже не объявляются выполненными этим меньшим срезом.

### 15.2. Проверки

| ID | Проверка | Критерий готовности |
|---|---|---|
| T-01 | Сборка без C toolchain | Windows и Linux artifacts получаются с CGO_ENABLED=0 в окружении без GCC/Clang, GUI headers и pkg-config |
| T-02 | Общий Go API и native controls | Один исходный код; диагностика подтверждает Win32 controls и GTK widgets в соответствующих backend |
| T-03 | Текст и события | Кириллица вводится и читается; программное и пользовательское изменение соблюдают заданный контракт, без дубликатов |
| T-04 | Фокус и layout | Tab проходит элементы в определённом порядке; resizing не перекрывает и не обрезает содержимое вопреки ограничениям |
| T-05 | Потоки и Post | Фоновая работа не блокирует UI; native операции выполняются на правильном OS thread; Post из callback не создаёт deadlock |
| T-06 | Уничтожение | Повторные циклы создания/удаления не оставляют активные callbacks и записи объектов в реестре |
| T-07 | Ошибки запуска | Отсутствие GTK, обязательного symbol и доступного display различается и возвращается как понятная ошибка |
| T-08 | Отмена и завершение | Отмена закрытия сохраняет рабочую форму; успешное закрытие следует выбранной политике и освобождает ресурсы |
| T-09 | Сбой частичного создания | При запуске ошибка освобождает созданные peers и переводит приложение в Failed; при динамическом добавлении очищается только неуспешно добавляемое дерево, а остальной UI остаётся работоспособным |

Возврат RSS процесса строго к исходному значению не требуется: GUI runtime и Go могут сохранять кеши. Для T-06 проверяются управляемые фреймворком ресурсы и отсутствие устойчивого роста при повторяемом сценарии.

Проверка сборки и проверка запуска разделены. Система сборки не обязана иметь GTK runtime, если пример только компилируется; система запуска обязана соответствовать объявленному runtime baseline.

### 15.3. Уровни проверки

Логику событий, переходов состояний и layout можно проверять изолированно. Нативные smoke- и integration-сценарии выполняются на настоящих поддерживаемых платформах. Имитация backend не доказывает корректность FFI, native event loop или display initialization.

Файл формы и генератор добавляют отдельные критерии: корректная диагностика ошибочного документа, одинаковое построение из описания и кода, детерминированная генерация, сохранность пользовательских методов.
