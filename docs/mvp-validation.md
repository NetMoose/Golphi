# Проверка native UI MVP

Изменение: [implement-native-ui-mvp](../openspec/changes/archive/2026-10-28-implement-native-ui-mvp/proposal.md). Узкий MVP принят 28 октября 2026 года: автоматические native-проверки и ручные сценарии общего примера пройдены на Linux и Windows. Это не завершение E0 или полного E1; ограничения и открытые вопросы полной библиотеки сохранены.

## Матрица

| Платформа | Конфигурация | Источник |
|---|---|---|
| Linux | Mint 22.3 Zena, amd64, glibc 2.39, GTK 4.14.5, GLib 2.80.0, Cinnamon/X11, DISPLAY=:0 | Локальная проверка окружения |
| Windows | Windows 11 Pro, amd64, build 26100, 96 DPI / 100% | Журнал пользовательского native-прогона 28 октября 2026 года |
| Go | 1.26.5, CGO_ENABLED=0 для проверяемых сборок | go version локально; команды каждого прогона фиксируются ниже |

GTK runtime доступен; GTK development metadata (gtk4.pc) не установлен. Текущая системная настройка CGO_ENABLED=1 не используется для проверочных сборок.

## Технический этап

Подготовка Go-модуля, Linux и Windows FFI/bootstrap probes выполняется до фиксации backend-интерфейса. Probe проверяет узкий путь и не является пользовательским MVP.

Проверка Windows не заменяется успешной кросс-компиляцией. Получен успешный Windows-прогон технической пробы; задача 1.4 выполнена для уточнённой пользователем Windows 11. Последующий этап интерфейса backend учитывает результаты обеих платформ.

## Критерии MVP

| Критерий | Статус |
|---|---|
| M-01: сборки без C toolchain | Пройден: изолированные повторяемые сборки обеих целей, см. mvp-build.md |
| M-02: общий native-пример на двух ОС | Пройден: пользователь подтвердил все ручные сценарии Linux и Windows |
| M-03: события и текст | Пройден: ядро, GTK и Win32 native; ручная кириллица/кнопка на обеих ОС |
| M-04: Post и UI-поток | Пройден: ядро/race, обе native-интеграции, ручной worker и отзывчивость |
| M-05: проверки Run и одна попытка | Пройден: subprocess-сценарии на Linux и Windows |
| M-06: обычное закрытие и сбои очистки | Пройден: fault injection, GTK WM-close, ручное обычное и быстрое закрытие на обеих ОС |
| M-07: ошибки частичного запуска | Пройден: fault injection ядра на обеих ОС; реальное отсутствие runtime на целевой машине не имитировалось |
| M-08: аварийный путь и Destroy | Пройден: panic/Destroy subprocess-сценарии на обеих ОС и GTK/Win32 native-освобождение |

Все прежние открытые вопросы из дизайна изменения сохранены. Полные T-01–T-09 не объявляются пройденными; динамическое дерево, отменяемое закрытие, resizing и другие отложенные возможности не реализуются этим техническим этапом.

## Модуль: задача 1.2

Рабочий module path — github.com/NetMoose/Golphi; окончательный публичный path остаётся открытым. Закреплена github.com/ebitengine/purego v0.11.2 (её go.mod требует Go 1.25.0), сборки выполнялись Go 1.26.5.

Проверки прошли:

```sh
GOCACHE=/tmp/golphi-gocache GOMODCACHE=/tmp/golphi-gomodcache GOPROXY=off go mod verify
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 GOCACHE=/tmp/golphi-gocache GOMODCACHE=/tmp/golphi-gomodcache GOPROXY=off go build ./ui github.com/ebitengine/purego
CGO_ENABLED=0 GOOS=windows GOARCH=amd64 GOCACHE=/tmp/golphi-gocache GOMODCACHE=/tmp/golphi-gomodcache GOPROXY=off go build ./ui github.com/ebitengine/purego
```

Это проверка совместимости модулей и двух сборок, а не полный M-01 и не Windows native-прогон. Собственного C bridge нет. Review задачи 1.2: соответствие и качество — PASS.

## Linux: эксперимент 1.3

Импорт ui закрепляет startup thread без загрузки GTK. Subprocess-проверка подтверждает сохранение потока после переключений планировщика и отдельный поток фоновой goroutine. Реальный эксперимент создаёт GtkButton, подключает и синхронно испускает clicked, затем отключает callback и освобождает объект после его возврата.

```sh
CGO_ENABLED=0 GOCACHE=/tmp/golphi-gocache GOMODCACHE=/tmp/golphi-gomodcache GOLPHI_NATIVE_PROBE=1 DISPLAY=:0 GDK_BACKEND=x11 go test -count=1 -v ./cmd/probe-linux
```

Прогон 28 октября 2026 года с доступом к локальному X11:

```text
GTK=4.14.5 DISPLAY=:0 backend=X11 startup=216438 native=216438 callback=216438 callbacks=1 callback_same_thread=true
PASS
```

Без разрешения доступа к X11 из sandbox gtk_init_check возвращал ошибку. После предоставления доступа тот же тест прошёл. Проверки `CGO_ENABLED=0 go test -count=1 -v ./...` и `go vet ./...` прошли; native-тест без явного GOLPHI_NATIVE_PROBE=1 пропускается. Это не проверка message loop, видимой формы или полного жизненного цикла MVP.

## Windows: эксперимент 1.4

Пользователь 28 октября 2026 года уточнил ОС: Windows 11 вместо ранее ошибочно указанной Windows 10. Матрица MVP исправлена на Windows 11/amd64; совместимость с Windows 10 этим прогоном не подтверждается.

Источник: [исходный журнал пользователя](../artifacts/golphi-windows-probe.txt), сохранён без изменений в UTF-16LE. Программа собрана Go 1.26.5 для windows/amd64 с CGO_ENABLED=0; сборка и переносимые тесты прошли ранее. [Инструкция запуска](windows-probe.md).

Результаты:

- Windows 11 Pro, build 26100, архитектура CPU 9 (AMD64), ОС 64-разрядная.
- Системный масштаб 100%, DPI 96, system-aware.
- Startup/main/native/callback/cleanup: поток 10892; worker: 15524.
- EnumWindows: результат 1, 155 callback, все на потоке 10892, own-window-seen=true.
- DestroyWindow=1; PASS; код завершения 0.

Техническая задача 1.4 выполнена. Это подтверждает создание/освобождение нативного окна, синхронные callbacks и закрепление потока. Полный message loop, Form.Run, Post, прикладные события и критерии M-01–M-08 этим экспериментом не проверены.

## Внутренний контракт backend: задача 1.5

Добавлены `internal/backend.Driver`, общая очередь `Queue` и сохранение паники `Capture`. [Технический контракт](backend-contract.md) описывает владение строками, peers и callback, потоковые ограничения и порядок остановки перед освобождением wake-ресурсов. Это внутренние детали MVP, не публичный интерфейс расширения библиотеки.

Fake wake проверяет отсутствие inline-выполнения, FIFO и вложенный Post, отказ до готовности/после остановки, nil, отмену, исходную панику со стеком, отказ wake без принятия задачи, конкурентную доставку и ожидание завершения wake перед очисткой. Проверки `CGO_ENABLED=0 go test -count=1 ./...`, `go vet ./...` и `go build ./...` для linux/amd64 и windows/amd64 прошли. Дополнительно `CGO_ENABLED=1 go test -race -count=1 ./internal/backend` прошёл; CGO включён только для race detector, не для сборки MVP.

Общая Linux-сборка также исправлена для команды Windows-пробы: на неподдерживаемой платформе она явно возвращает ошибку. Нативные адаптеры и публичный ui.Post пока не реализованы; этот этап не подтверждает их работоспособность.

## Нативные адаптеры

GTK4 реализован через purego, с отложенной загрузкой runtime в Init. Опциональная проверка `GOLPHI_GTK_NATIVE=1 DISPLAY=:0 GDK_BACKEND=x11 CGO_ENABLED=0 go test ./internal/backend/gtk4 -run TestNative -count=1 -v` прошла при разрешённом доступе к X11. Проверены кириллица/emoji, clicked/changed/close-request, фиксированная клиентская область, запрет resizing, пробуждение из goroutine, перехват паники на FFI-границе и очистка registry/peers. `CGO_ENABLED=0 go run ./cmd/smoke-gtk` подтвердил startup-thread affinity и завершение очистки до сообщения об успехе. GTK-библиотека остаётся загруженной до выхода процесса; принадлежащие драйверу объекты, context refs и Go callback roots освобождаются.

Win32 реализован прямыми syscall-вызовами. Пробуждение использует manual-reset event, который не теряется во вложенном системном цикле; выполнение Go-очереди остаётся вне WndProc. Review исправил также очистку дочерних HWND и проверку переполнения при масштабировании/преобразовании размеров. Переносимые тесты и Windows/amd64 CGO-disabled сборка/vet прошли. На этом этапе Windows native-тесты backend были только скомпилированы; последующая успешная пользовательская приёмка нового backend зафиксирована ниже отдельно от startup-пробы.

## Ядро: этап 2

Реализованы логические Form/Edit/Button/Label, раздельные Owner/Parent, Destroy/Destroyed, геометрия, func()-события, нормализация текста и coalescing/nil/reset. Внутренние проверки не объявляют поддержку Panel или динамического native reparent.

Form.Run подключён к платформенным backend. Subprocess-тесты выполняются на startup thread через TestMain: неправильный первый Run, корректный последующий, повторный/вложенный Run, расход допуска при ошибке Init и приоритет panic уничтоженной формы до/после использованной попытки. Проверены тихая подготовка, порядок создания peers, подавление native echo и освобождение вне callback.

Пакетный ui.Post использует ту же очередь и атомарную публикацию после подготовки. Проверены отказ в Init/Create/Text/Show, первое событие до paint, 64 конкурентных вызова на границе готовности, FIFO/вложенность, nil, отмена при обычной остановке/панике. Свежие `CGO_ENABLED=0 go test -count=1 ./...` и `go vet ./...` прошли. `CGO_ENABLED=1 go test -race -count=1 ./ui ./internal/backend` также прошёл; это режим проверки гонок, не требование к сборке приложения.

Отдельные review компонентов, геометрии, событий, Run и Post завершились без открытых замечаний. На момент этого этапа fault-injection и нативная интеграция оставались отдельными задачами; их последующие результаты и итоговая приёмка приведены ниже.

## Интеграция и отказы: этап 4

Пройден итоговый локальный запуск:

```sh
DISPLAY=:0 GDK_BACKEND=x11 GOLPHI_GTK_NATIVE=1 GOLPHI_NATIVE_CORE=1 GOLPHI_NATIVE_WM_CLOSE=1 CGO_ENABLED=0 GOCACHE=/tmp/golphi-gocache GOMODCACHE=/tmp/golphi-gomodcache GOPROXY=off go test -count=1 -timeout=90s ./...
```

Все пакеты прошли, включая настоящие GTK native tests и ui integration. Последние выполняются отдельными процессами на startup thread; проверяют нормализацию текста (GTK: 70000 символов → 65534), подавление native echo, coalescing/nil/reset, worker Post и физическое освобождение после callback. Каждый peer получает ровно один вызов Destroy от runtime; очищены наблюдаемые карты peers и callback sinks. Отдельный GTK backend-тест проверяет глобальный callback registry.

Обычное закрытие проверено настоящим `wmctrl`-запросом к уникальному тестовому окну: один CloseRequest, Run возвращает nil, приём Post закрыт. Живые логические Go-компоненты после обычного закрытия сохраняются; их последующий Destroy проверен отдельно.

Fake Driver fault-injection покрывает ошибки загрузки библиотеки/символа/init, частичное создание, ошибки E1/E2 и panic W в независимых cleanup-операциях, первичную handler/Post panic и безопасное/ошибочное обращение к уничтоженному объекту. Исходные значения/стеки и все дополнительные ошибки сохраняются, следующие операции очистки предпринимаются. Это проверка ядра; она не подменяет реальное отсутствие DLL/GTK на целевой машине.

Общий code review ядра/backend и отдельные review сценариев не выявили открытых замечаний. go vet, openspec validate implement-native-ui-mvp --strict, openspec validate --specs --strict и git diff --check прошли. На этом этапе основные Requirements ещё не были синхронизированы; был подготовлен [исторический снимок Scope до sync](mvp-scope-sync.md).

Общий Linux-пример запущен из изолированной сборки: видны все native-контролы и кириллические подписи без обрезания в исходном состоянии, клиентская область 400×180; закрытие окна через WM завершило процесс с кодом 0. Попытка автоматического ввода через XTest не дала подтверждённого изменения интерфейса, поэтому ручной сценарий кнопки/ввода в общем примере этим не засчитывается. События и фоновые обновления отдельно подтверждены нативными интеграционными тестами.

## Итоговая приёмка 28 октября 2026 года

Пользователь подтвердил PASS **всех** ручных сценариев общего примера на Linux и Windows: исходный вид и кириллица, ввод и немедленный результат кнопки, фоновое обновление, отзывчивость во время worker, повторное нажатие с другим именем без устаревшего результата, фиксированный размер/расположение, обычное закрытие и быстрое закрытие до завершения worker, успешное завершение процессов.
