# Design

## Context

Мотивация и объём — в [proposal.md](proposal.md), проверяемый контракт — в [windows-native-appearance](specs/windows-native-appearance/spec.md).

Текущий Win32 `driver` в `internal/backend/win32/driver_windows.go` устанавливает system-aware DPI-контекст UI-потока, получает DPI запуска и масштабирует геометрию относительно 96 DPI. `CreateWindowExW` создаёт стандартные EDIT/BUTTON/STATIC; системный шрифт им явно не назначается. В проекте нет Windows manifest/`.syso`. `Close` уже пытается уничтожить оставшиеся peers, собирает ошибки и сохраняет нативную инфраструктуру, если уничтожение не удалось. Динамическое дерево может сохранять HWND либо пересоздавать peers; обе ветви должны получать корректное оформление.

Принятая матрица остаётся Windows 11/amd64 и существующий Linux Mint/GTK4/X11 для регрессий; Go 1.26.5, CGO_ENABLED=0. Базовые контракты [runtime](../../specs/native-ui-runtime/spec.md) и [failure](../../specs/application-failure/spec.md) не заменяются. Общие вопросы исходного дизайна и [архива дерева](../archive/2026-11-20-implement-dynamic-component-tree/design.md#open-questions) не закрываются.

## Goals / Non-Goals

**Goals:** стандартное нативное оформление Windows, явная ответственность приложения за манифест, системный шрифт с безопасным общим временем жизни, узкая и воспроизводимая приёмка на двух масштабах без C toolchain.

**Non-Goals:** тёмная или собственная тема, гарантированное оформление WinUI/Fluent, смена DPI/шрифта/темы во время работы, per-monitor transitions, новые контролы, публичный Font API, автоматическая раскладка/измерение содержимого, новая общая политика очистки, расширение Windows-матрицы и DOC-01. Windows 10 не выдаётся за фактически проверенную конфигурацию.

## Decisions

### 1. Приложение встраивает явный манифест

Согласован основной путь: XML с Common Controls v6 превращается в `.syso` в пакете `main`, затем включается обычной Go-сборкой. Имя ресурса учитывает Windows/amd64, чтобы он не участвовал в Linux-сборке. Для примеров использовать тот же публично описанный путь, без скрытого библиотечного манифеста. Если пользователь уже поставляет ресурс с манифестом, он дополняет исходный XML и регенерирует единый ресурс; автоматического объединения чужих `.syso` нет.

Альтернативы: внешний `app.exe.manifest` требует дополнительного файла поставки; runtime activation context внутри Golphi добавляет работу с контекстом UI-потока и его очисткой. Для WIN-01 они не являются основным способом и не реализуются как fallback. Запуск без манифеста разрешён, системный шрифт всё равно назначается; backend не отвергает приложение только из-за отсутствия v6.

Манифест примера должен соответствовать существующей system-aware модели: не включать автоматически per-monitor-v2 из шаблонов генератора. Подготовленный XML проверяется на сохранение настроек приложения и отсутствие новых требований прав администратора. Проверка styles для приёмки — диагностическая, без нового публичного API и без обязательного отказа Run при классическом оформлении.

### 2. go-winres — закреплённый инструмент подготовки

Согласован `github.com/tc-hib/go-winres`, работающий с готовым XML через конфигурацию `RT_MANIFEST`/`#1`. Конфигурация и XML — исходники приложения; генератор — build-time tool, не импорт backend. Не создавать собственный COFF/resource writer и не требовать windres/rc.exe/MinGW.

Конкретный release pin выбирается и фиксируется в задаче 1.2 после проверки на Go 1.26.5; на стадии proposal генерация ещё не выполнялась и версия не выдаётся за проверенную. Все команды генерации, включая `go:generate`, если он используется, должны ссылаться на тот же pin, без `@latest`. Зафиксировать источник/контрольные суммы зависимостей выбранного способа установки. Проверить подготовку ресурсов на Linux и Windows с CGO_ENABLED=0. Уже созданный `.syso` не должен требовать установленного генератора при обычной сборке потребителя; способ получения/регенерации ресурса описать явно.

Альтернатива `akavel/rsrc` проще для одного XML, но автор сообщает о low-priority maintenance и направляет к go-winres. Иконки, версии EXE и другие возможности генератора этим этапом не становятся требованиями.

### 3. Один системный шрифт на сессию backend

На UI-потоке после определения DPI и до начала приёма Post получить `NONCLIENTMETRICSW` через `SystemParametersInfoForDpi(SPI_GETNONCLIENTMETRICS, ..., dpi)`. Использовать `lfMessageFont` и `CreateFontIndirectW`. Не задавать имя/размер вручную и не применять дополнительное DPI-умножение к уже полученному LOGFONTW. Проверить ABI структур и Unicode-вызовов в существующем стиле Win32 ABI tests.

Один принадлежащий driver `HFONT` назначается через `WM_SETFONT` Button/Edit/Label после native-создания и до показа, в том числе в prepare/commit динамического дерева. Контролы не владеют шрифтом. Panel своего текста не имеет; заголовок окна рисует Windows. Прямой перенос HWND не требует переназначения шрифта; не трогать текст, фокус и выделение ради назначения шрифта. В частности, не вводить повторный `EM_SETSEL` для переноса сохраняемого Edit.

Альтернативы: жёстко заданная Segoe UI игнорирует системные настройки; отдельный HFONT каждому контролу увеличивает число ресурсов и усложняет уничтожение; публичное наследование шрифтов выходит за WIN-01. Обновление настроек Windows после запуска не обрабатывается этим этапом.

### 4. Шрифт — зависимость живых native-контролов

Нормальный порядок: выйти из callback, уничтожить использующие шрифт peers, закончить использование в DC, затем попытаться удалить HFONT через `DeleteObject`. Уничтожение отдельного компонента, detach, rollback либо замена peer не удаляют общий шрифт; новый peer использует тот же ресурс сессии. При ошибке запуска очищаются уже созданные ресурсы, Post не открывается. Неудача создания шрифта не заменяется молчаливым fallback.

Перехваченная panic handler/Post следует существующей остановке: шрифт участвует в последующей очистке. Ошибка либо перехваченная panic отдельной операции очистки дополняет исходную диагностику, включая значение/стек первичной panic; независимая очистка продолжается. При обычном закрытии cleanup failures дают ошибку Run без выдуманной первичной panic.

Если после попыток очистки ещё жив native-контрол, использующий шрифт, не вызывать `DeleteObject` для этого шрифта. Сохранить handle и диагностику; не объявлять ресурс освобождённым. Нельзя освобождать шрифт в `Destroy` одного компонента или до попыток очистить пользователей. Ошибка независимого ресурса сама по себе не блокирует освобождение шрифта, если его пользователи уже уничтожены. Эта конкретная зависимость не определяет общий граф очистки, retry или окончательную судьбу всех неосвобождённых ресурсов.

При окончательном завершении процесса Windows освобождает его GDI-ресурсы; это страховка ОС, а не замена штатной очистке и не гарантия выполнения Go cleanup при panic в чужой goroutine, os.Exit или принудительном завершении. Общие правила обработки таких сбоев здесь не расширяются.

### 5. Ручная геометрия без autosize по тексту

Сохраняется `SetBounds`: фиксированные координаты относительно Parent, минимальные размеры, допустимое увеличение native-темой, без исправления пересечений и расширения Parent. В Win32 используется уже существующее преобразование относительно 96 DPI: 100% = 96 DPI, 150% = 144 DPI, с единым существующим округлением. Шрифт из DPI-зависимых метрик второй раз не масштабируется. Если аудит выявит несовместимость существующего округления с этой границей, зафиксировать проблему, не менять публичную геометрию молча.

`WM_SETFONT` не увеличивает размер контрола. В этом этапе не добавляется подбор ширины по тексту либо одинаковое минимальное измерение для GTK и Win32. Размеры проверочного примера задать с запасом под системный шрифт, при необходимости поправить актуальные примеры и объяснить границу в документации. Для произвольного пользовательского текста автоматическое отсутствие обрезания не обещается.

Проверочный пример: Button/Edit/Label с обычным текстом и кириллицей с верхними/нижними элементами букв, достаточно широкие/высокие контролы, намеренно тесные границы, вложенные Panel для clipping и длинный Edit для горизонтальной прокрутки. При штатном размере текст полностью читаем, при намеренном выходе за границы рисование не выходит за соответствующий clip. Проверка динамического создания/пересоздания покрывает назначение шрифта, не вводя новую гарантию позиций пересозданного Edit.

### 6. Приёмка с отдельными запусками для масштабов

Windows 11/amd64, 100% и 150%; перед каждым прогоном завершить процесс, настроить системный масштаб и перезапустить. При system-aware модели логировать фактический DPI: ожидаются 96 и 144. Если окружение ещё выдаёт старое значение, сначала привести сессию Windows к новому DPI; такой прогон не считать проверкой нужного масштаба.

Для обоих масштабов: сохранить базовые снимки старого оформления до изменения и снимки новой сборки в сопоставимых условиях, ОС/build, Go, масштаб/DPI, команды, pin генератора, commit и SHA256 EXE. Не переписывать старые артефакты. Отдельно показать отсутствие обязательного sidecar-манифеста и запуск без встроенной v6-зависимости с системным шрифтом.

Не ограничиваться снимком: внутренний native test/readback подтверждает манифест в PE, активные visual styles и назначенный HFONT/его метрики; ручной прогон подтверждает видимость текста/clipping и взаимодействия. Проверить фокус, клавиатурный ввод, выделение и прямой перенос сохраняемого Edit; не повторять исследование позиций при пересоздании. Прогнать применимые существующие dynamic-tree/retained/aborted-cleanup suites и Linux-регрессии. Русская Windows-инструкция, русские `.ps1` в UTF-8+BOM. GUI-примеры `-H windowsgui`, native test EXE консольные.

## Risks / Trade-offs

- Генератор или его defaults меняют DPI/манифест → явный XML, pin и проверка фактически встроенного ресурса; пример с уже существующим манифестом.
- UI-шрифт меняет метрики и видимые размеры → тестовый пример на двух DPI, корректировка его Bounds, отдельные positive/negative clipping cases; без новой layout-системы.
- Общий HFONT удаляется при ещё живом peer → fault-injection и readback времени жизни; проверка завершения всех пользователей перед освобождением.
- Ошибка Win32 API маскирует первичную panic → отдельная операция очистки и существующая агрегация error/panic diagnostics.
- Создание peer в транзакции обходит шрифт → тесты initial/dynamic/recreated paths, фокус/выделение не менять.
- Снимок похож на тематизированный UI, но v6 не активна → native evidence активации, не только визуальное сравнение.
- Windows DPI не обновился после настройки → сверять DPI процесса при каждом отдельном запуске, не приписывать PASS масштабу только по настройке панели.

## Migration Plan

1. После review и отдельного запроса apply использовать ветку от актуальной `develop` без worktree. Текущая planning-ветка `codex/modernize-win32-appearance` основана на `5cfdcb256e12a589e42f5ad1e5605e3c6cc8bf85`; актуальность проверить перед apply. Subagent Driven Development, независимые ресурсы/документация и backend могут выполняться параллельно при раздельном владении; Git только координатор.
2. Получить baseline Windows, проверить и закрепить генератор, затем добавить подготовку примеров и ресурса. Не менять глобальные настройки DPI процесса скрытым default генератора.
3. Реализовать шрифт и тесты lifetime/failures, интегрировать все пути создания peers. Этапы завершаются review, commit/push с проверкой remote HEAD.
4. Провести сборки без C toolchain, регрессии и фактическую Windows-приёмку; отчёт и задачи отмечать только по полученным результатам. Нет Windows-evidence — соответствующий пункт остаётся незавершённым.
5. Обновить текущую документацию и WIN-01 в backlog по фактическому статусу, итоговый PR в `develop`. Sync/archive — отдельный запрос после завершения. Откат изменения не требует миграции пользовательских данных: вернуть backend и ресурсный шаг, сохранив evidence; чужие манифесты не перезаписывать.

## Open Questions

Сохраняются все ранее открытые вопросы [динамического дерева](../archive/2026-11-20-implement-dynamic-component-tree/design.md#open-questions) и остаток Q-01–Q-14 из [исходного дизайна](../../../docs/design.md), кроме уже согласованного узкого объёма WIN-01. В частности:

- Смена DPI между мониторами, системного шрифта/темы во время работы, тёмная и собственная тема, другие Windows-конфигурации и масштабы, новые платформы.
- Общий Font API, наследование/пользовательские шрифты, измерение содержимого, layout/resizing, изменение геометрии присоединённых контролов.
- Сохранение курсора/выделения при пересоздании Edit, публичный API позиций/выделения, IME/доступность/локализация.
- Несколько окон и перенос между формами, Owner, публичный Application, сторонние компоненты, остальные события и Program/User.
- Порядок Post/native/OnChange, fairness, перегрузка, ожидание и индивидуальная отмена Post.
- Общие зависимости очистки за пределами контролы→шрифт, retry и судьба неосвобождённых ресурсов, зависания/тайм-ауты, самостоятельный Destroy и прочие внутренние сбои, стабильный публичный тип/доступ/порядок диагностики; ранее отложенные сочетания fatal SetParent с дальнейшими операциями/паникой.
- Формы/дизайнер, поставка runtime и DOC-01 остаются отдельными задачами.

Выбор конкретного release go-winres и имён новых build/evidence файлов — технические задачи реализации, не новые продуктовые договорённости; они не могут менять принятый контракт.
