# Windows Native Appearance Spec Delta

## Purpose

Определить нативное оформление Windows-приложений Golphi: подключение visual styles, системный шрифт, безопасное время жизни его ресурсов и проверяемую геометрию при DPI запуска.

## ADDED Requirements

### Requirement: Application owns the embedded visual styles manifest
Документированный основной способ включения visual styles SHALL использовать явный XML-манифест пользовательского приложения с зависимостью Common Controls v6, встроенный в EXE. Golphi MUST NOT навязывать второй манифест приложению с собственным манифестом. При корректной подготовке и включённых стилях Windows контролы SHALL использовать visual styles на принятой Windows-матрице.

#### Scenario: Standalone themed executable
- **WHEN** приложение собрано по инструкции со встроенным манифестом и запущено на принятой Windows 11/amd64 с включёнными стилями
- **THEN** visual styles фактически активны и используются контролами; файл манифеста рядом с EXE для этого не требуется

#### Scenario: Existing application manifest
- **WHEN** приложение уже имеет XML-манифест с собственными настройками
- **THEN** инструкция показывает добавление зависимости Common Controls v6 в этот манифест, сохраняя остальные настройки, вместо добавления конкурирующего манифеста

### Requirement: Resource preparation needs no C toolchain
Подготовка ресурсов SHALL использовать закреплённую версию Go-инструмента и явный XML-манифест. Генерация Windows/amd64 ресурсов на Linux и Windows и последующая сборка приложения SHALL работать с CGO_ENABLED=0 без C compiler, resource compiler из Windows SDK и GUI headers. Windows-ресурс MUST NOT попадать в Linux-сборку того же примера.

#### Scenario: Generate and build on both hosts
- **WHEN** инструкции выполняют на Linux/amd64 и Windows 11/amd64 с согласованным Go toolchain и доступными Go-зависимостями
- **THEN** закреплённая версия генератора создаёт ресурс, Windows-приложение собирается без C toolchain и содержит нужный XML-манифест; Linux-сборка того же исходного примера остаётся доступной

### Requirement: Missing manifest does not reject startup
Отсутствие манифеста visual styles SHALL сохранять возможность запуска Golphi с классическим оформлением и системным UI-шрифтом. Само отсутствие зависимости Common Controls v6 MUST NOT становиться новой причиной ошибки Run; visual styles в таком приложении не гарантируются.

#### Scenario: Legacy application without manifest
- **WHEN** существующее приложение без манифеста успешно проходит прочие условия запуска
- **THEN** Run запускает приложение, Button/Edit/Label получают системный UI-шрифт, а отсутствие visual styles не вызывает ошибку запуска

### Requirement: Controls use the startup system UI font
Win32 Button/Edit/Label SHALL использовать системный шрифт сообщений из lfMessageFont, полученный для DPI запуска. Размер шрифта MUST NOT масштабироваться повторно после получения DPI-зависимых метрик. Выбор действует независимо от манифеста и сохраняется до завершения сессии; новый публичный API шрифтов этим требованием не вводится.

#### Scenario: Startup font at both accepted scales
- **WHEN** приложение отдельно запускают на 100% и 150%
- **THEN** шрифт соответствует системным метрикам соответственно для 96 и 144 DPI, без жёстко заданного имени гарнитуры и повторного увеличения размера

#### Scenario: Dynamic and recreated controls
- **WHEN** во время Run создают новый Button/Edit/Label или пересоздают его нативное представление
- **THEN** до показа он получает тот же системный шрифт сессии; прямой перенос существующего контрола сохраняет назначенный шрифт

### Requirement: Backend owns the shared font lifetime
Win32 backend SHALL владеть одним общим созданным шрифтом сессии и сохранять его, пока его используют нативные контролы. Уничтожение отдельного компонента или отсоединение поддерева MUST NOT освобождать общий шрифт. При очистке освобождение шрифта SHALL выполняться после уничтожения всех использующих его нативных контролов и прекращения его использования при рисовании.

#### Scenario: One component released while others remain
- **WHEN** компонент уничтожают либо поддерево отсоединяют, а другие контролы продолжают работать
- **THEN** общий шрифт остаётся действительным, и оставшиеся и последующие контролы могут его использовать

#### Scenario: Normal shutdown
- **WHEN** приложение обычно закрывается и все использующие шрифт нативные контролы успешно уничтожены
- **THEN** backend освобождает общий шрифт ровно один раз после этих контролов на UI-потоке; успешная очистка сохраняет возврат nil из Run

### Requirement: Font failures preserve startup and panic diagnostics
Ошибка получения системных метрик либо создания шрифта SHALL завершать запуск с ошибкой и попытками очистки созданных ресурсов, не открывая приём Post. При перехваченной панике handler/Post очистка SHALL учитывать общий шрифт после выхода из callback. Сбои очистки шрифта MUST дополнять исходную диагностику по application-failure, не заменяя её.

#### Scenario: Font initialization fails
- **WHEN** получение метрик либо создание шрифта завершается ошибкой
- **THEN** Run возвращает исходную ошибку со всеми сбоями очистки, Post не начинает приниматься, а созданные ресурсы проходят попытки очистки

#### Scenario: Callback panic and font cleanup failure
- **WHEN** handler либо функция Post паникует со значением V и стеком S, а после уничтожения использующих шрифт контролов его очистка даёт ошибку либо панику W
- **THEN** Run сохраняет V и S и сбой очистки, включая значение и стек W при панике; паника отдельной операции очистки не выбрасывается повторно, остальные независимые операции продолжаются

#### Scenario: Independent cleanup failure
- **WHEN** при остановке произошёл сбой независимого ресурса, но использующие шрифт контролы успешно уничтожены
- **THEN** сбой сохраняется для диагностики и не препятствует попытке освобождения шрифта

### Requirement: Failed control teardown does not invalidate its font
Если после попыток очистки нативный контрол ещё использует общий шрифт, backend MUST NOT преждевременно удалять этот шрифт. Run SHALL сохранять диагностику сбоя очистки. Эта зависимость контролов от шрифта MUST NOT трактоваться как выбор общей политики retry, зависимой очистки или гарантии освобождения ресурсов при произвольном завершении процесса.

#### Scenario: Font user survives cleanup attempts
- **WHEN** попытки уничтожения использующего шрифт нативного контрола не удались и он остаётся живым
- **THEN** шрифт сохраняется действительным, Run возвращает ошибку очистки и независимые операции всё равно получают свои попытки; успешное освобождение шрифта не утверждается

### Requirement: Startup scaling preserves manual geometry boundaries
SetBounds SHALL сохранять фиксированные координаты и минимальные размеры в logical units. Win32 SHALL масштабировать геометрию относительно 96 DPI с единым правилом округления. Допустимое увеличение нативной темой MUST NOT означать автоматическую раскладку, расширение родителя или подбор ширины по тексту. Содержимое MUST обрезаться по границам контрола и вложенных Panel.

#### Scenario: Adequately sized text at accepted scales
- **WHEN** проверочный пример с достаточными размерами Button/Edit/Label отдельно запускают при 96 и 144 DPI
- **THEN** обычный текст и кириллица, включая верхние и нижние элементы букв, отображаются без непреднамеренного обрезания; шрифт и геометрия соответствуют масштабу запуска

#### Scenario: Deliberate clipping and long input
- **WHEN** содержимое намеренно выводят за тесные границы контрола и вложенных Panel, а в Edit вводят длинную строку
- **THEN** рисование остаётся в соответствующих границах, Edit допускает горизонтальную прокрутку ввода, а соседи и родители автоматически не перемещаются и не увеличиваются

### Requirement: Windows appearance acceptance requires native evidence
WIN-01 SHALL подтверждаться реальными запусками на Windows 11/amd64 при 100% и 150%, с DPI запуска, доказательствами активации visual styles и назначения шрифта, снимками до/после и проверкой clipping и взаимодействий. GUI-примеры SHALL собираться с -ldflags="-H windowsgui", тестовые EXE SHALL оставаться консольными. Кросс-сборка MUST NOT заменять нативную приёмку.

#### Scenario: Appearance and interaction acceptance
- **WHEN** проверяют тематизированный пример на обоих масштабах после отдельного запуска для каждого масштаба
- **THEN** отчёт содержит окружение, DPI, идентичность сборки, снимки, результаты текста/clipping, фокуса, клавиатурного ввода, выделения и переноса сохраняемого native Edit; сохранение позиций при пересоздании Edit остаётся вне гарантии

#### Scenario: Build evidence alone
- **WHEN** имеются только успешная генерация ресурсов, статические проверки или кросс-сборка
- **THEN** фактическая Windows-приёмка остаётся ожидающей, без отметки PASS для непройденных нативных и ручных сценариев
