# Spec Delta

## Scope

Эта дельта расширяет прежнее ограничение на неизменный обработчик согласованными правилами отмены и перенаправления. Присоединённость по цепочке Parent и тихая подготовка сохраняются. Обычная остановка, Post, взаимные изменения компонентов и новое накопление после отсоединения/присоединения внутри одного callback остаются открытыми; правила ниже не задают политику этих случаев.

## MODIFIED Requirements

### Requirement: Single replaceable event handler
Событие в основном API Golphi SHALL иметь не более одного прикладного обработчика. `SetOnClick(handler)` SHALL заменять предыдущий обработчик, а `SetOnClick(nil)` SHALL отключать его. Такое же правило SHALL действовать для других событий.

#### Scenario: Replacing a handler
- **WHEN** после обработчика A установлен обработчик B и происходит следующее событие
- **THEN** вызывается только B

#### Scenario: Disabling a handler
- **WHEN** обработчик отключён через setter с nil и происходит событие
- **THEN** прикладной обработчик не вызывается

#### Scenario: Replacement during delivery
- **WHEN** уже выполняющийся обработчик заменён другим
- **THEN** текущий вызов продолжается как обычно; последующая доставка выбирает текущий обработчик

### Requirement: Deferred and coalesced repeated changes
Изменения текста внутри OnChange SHALL применяться сразу без рекурсии. Пока уведомление не отменено, итог SHALL сравниваться с текстом на входе в обработчик, либо с базой, установленной после сброса сравнения. Различие SHALL давать одно отложенное уведомление с итоговым текстом, равенство — ни одного. Доставка SHALL подчиняться правилам отмены и выбора текущего обработчика.

#### Scenario: Several changes inside a handler
- **GIVEN** обработчик не меняется, а компонент остаётся живым, работающим и присоединённым до повторной доставки
- **WHEN** обработчик, вызванный для текста «А», последовательно устанавливает «Б» и «В»
- **THEN** Text() отражает каждое изменение сразу
- **AND** после завершения текущего обработчика выполняется один повторный OnChange, видящий «В», без вложенного вызова

#### Scenario: Returning to the entry value
- **GIVEN** обработчик не меняется, а компонент остаётся живым, работающим и присоединённым
- **WHEN** обработчик, вызванный для текста «А», устанавливает «Б», затем возвращает «А»
- **THEN** повторное уведомление OnChange не вызывается

## ADDED Requirements

### Requirement: Destruction cancels unstarted component notifications
Логическое уничтожение компонента SHALL отменять все его ещё не начатые прикладные уведомления, включая ожидающий OnChange. Уже выполняющийся обработчик SHALL продолжать работу; обычные обращения к уничтоженному объекту вызывают panic. При каскаде правило SHALL применяться к каждому уничтоженному компоненту.

#### Scenario: Destroy with a repeated notification pending
- **WHEN** обработчик изменил текст и уничтожил компонент до повторной доставки
- **THEN** повторный OnChange не запускается, текущий обработчик продолжает работу без обычных обращений к уничтоженному объекту

#### Scenario: Cascaded cancellation
- **WHEN** уничтожение панели уничтожает её визуальных детей с ожидающими уведомлениями
- **THEN** все не начатые уведомления каждого уничтоженного ребёнка отменены

### Requirement: Detachment cancels pending text notifications
Успешное отсоединение компонента или его предка SHALL отменять ожидающие OnChange всего отсоединённого поддерева без восстановления при присоединении. Ошибка SetParent MUST сохранять уведомления вместе с прежним состоянием.

#### Scenario: Detach and reattach with a pending child notification
- **WHEN** у поля ожидается OnChange, его панель успешно отсоединяют и затем присоединяют снова
- **THEN** прежнее уведомление поля отменено и не воспроизводится

#### Scenario: Failed detachment preserves pending notification
- **WHEN** попытка SetParent(nil) завершается ошибкой при ожидающем OnChange
- **THEN** уведомление сохраняется и, при отсутствии последующей отмены, доставляется по обычным правилам

### Requirement: Pending text notification follows the current handler
Замена ненулевого обработчика OnChange другим ненулевым обработчиком SHALL сохранять ожидающее уведомление и доставлять его обработчику, установленному на момент доставки. Замена MUST NOT прерывать уже выполняющийся обработчик.

#### Scenario: Redirecting a queued notification
- **WHEN** OnChange ожидает доставки и обработчик A заменяется обработчиком B
- **THEN** при доставке вызывается B с итоговым текстом, а не сохранённый A

#### Scenario: Replacing the handler from its current invocation
- **WHEN** обработчик A меняет текст и назначает B без отключения через nil
- **THEN** A завершается как обычно; если итог отличается от текста на входе и отмены нет, один повторный OnChange получает B

### Requirement: Disabling cancels queued and accumulated text notifications
SetOnChange(nil) SHALL отменять ожидающее уведомление и накопленное изменение внутри текущего обработчика. Назначение нового обработчика MUST NOT восстанавливать отменённое уведомление. Текущий вызов SHALL продолжаться как обычно.

#### Scenario: Disabling a queued notification
- **WHEN** ожидающий OnChange отключают через nil, затем назначают новый обработчик без нового изменения текста
- **THEN** отменённое уведомление не доставляется

#### Scenario: Disabling accumulated changes before handler exit
- **WHEN** текущий обработчик меняет текст, вызывает SetOnChange(nil), назначает новый обработчик и выходит без дальнейших изменений текста
- **THEN** выход не создаёт повторное уведомление из отменённого накопления

### Requirement: Comparison restarts after disabling
После SetOnChange(nil) прежняя база сравнения SHALL сбрасываться. Первое реальное изменение после назначения нового обработчика SHALL снова создавать основание для уведомления; базой служит текст до этого изменения. При изменениях внутри текущего callback SHALL сохраняться отложенная доставка без рекурсии и объединение повторных изменений.

#### Scenario: Returning to the old handler entry after reset
- **WHEN** обработчик входит с «А», отключается через nil, устанавливает «Б», назначает нового обработчика и меняет текст на «А»
- **THEN** новая база — «Б»; после выхода один отложенный OnChange доставляется текущему обработчику с «А», несмотря на совпадение со входом в старый обработчик

#### Scenario: Assignment alone does not notify
- **WHEN** после отключения текст меняют без обработчика и затем назначают новый обработчик без нового изменения
- **THEN** одно назначение не создаёт OnChange
