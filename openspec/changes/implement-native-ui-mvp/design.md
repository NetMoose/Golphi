# Design

## Context

См. proposal.md, Why. В репозитории есть README, LICENSE (MIT), docs/design.md, четыре основные спецификации и четыре архивных изменения; Go-модуля, runtime, backend и тестов ещё нет. Контракты component-lifecycle/component-events/post-dispatch/application-failure задают целевую семантику, а не доказательство реализации.

Согласован узкий MVP перед полным E1. Linux-окружение проверено локально: Mint 22.3 Zena (Ubuntu Noble), amd64, glibc 2.39, Go 1.26.5, GTK 4.14.5, GLib 2.80.0, Cinnamon/X11, DISPLAY=:0. GTK runtime установлен, gtk4.pc отсутствует; текущий CGO_ENABLED=1 не подходит проверке, поэтому сборки явно используют 0. 28 октября 2026 года пользователь уточнил ранее ошибочно указанную Windows 10: фактическая машина — Windows 11 Pro/amd64, build 26100, масштаб 100% (96 DPI). Native-проба успешно выполнена; свидетельство — artifacts/golphi-windows-probe.txt и docs/mvp-validation.md. Проверочная Windows-матрица MVP уточнена до Windows 11; Windows 10 не проверена. Закреплена purego v0.11.2.

## Goals / Non-Goals

**Goals:** работающий одинаковый пример; проверка Go → native → Go callback, кириллицы, UI-thread affinity, Post, успешного/неуспешного запуска и завершения; минимальная экспериментальная поверхность, соответствующая принятым контрактам.

**Non-Goals:** полная библиотека или закрытие E0; публичный Application; динамическое создание/перенос/отсоединение контролов во время работы, Panel, несколько окон, модальность, отмена закрытия, Hide, повторный Run, resizing, layout engine, смена DPI, формы/дизайнер/Qt/Auto/runtime bundling. Прежние общие контракты не отменяются: неприменимые MVP сценарии помечаются непроверенными, а не успешно выполненными. Реализация не должна обещать полную поддержку всех основных specs.

## Decisions

### Принято: прямые native-вызовы без собственного bridge

Win32 и GTK4 вызываются напрямую; purego допустим как внутренняя зависимость. На Windows загрузка DLL/вызовы могут использовать Go Windows API, на Linux purego связывает нужные GTK/GLib/GObject-функции. Это технический backend, не типы публичного API. Собственный C bridge отклонён для MVP из-за лишней сборки/поставки; cgo не проверяет требуемую сборку без C toolchain.

Структура реализации (предложение, не новый публичный контракт): ui — компоненты и API, internal/runtime — состояния/очереди/диагностика, internal/backend — узкий интерфейс, win32/gtk4 — платформенные реализации, examples/hello — общий пример. Выбранные версии зависимостей закрепляются go.mod/go.sum. Для начальной сборки использовать временный module path, соответствующий текущему remote (github.com/NetMoose/Golphi), как рабочее допущение; окончательный публичный module path Q-01 не утверждается.

### Принято: startup thread и единственная попытка

UI-пакет закрепляет startup thread через runtime.LockOSThread в init, но не загружает GUI runtime и не обращается к display. main последовательно строит логическое дерево и вызывает Run (возможен обычный помощник). Run не запускает отдельную UI-goroutine; весь native lifecycle, события и Post выполняются на закреплённом потоке. Фоновые вычисления не обращаются напрямую к живым UI-компонентам.

Варианты явного init в приложении и отдельной UI-goroutine не выбраны. Цена выбранного удобства Form.Run — закрепление потока при импорте. Техническая проверка должна подтвердить получение/сравнение OS thread identity с CGO_ENABLED=0 на обеих платформах; горутинный ID или проверка имени main в стеке не нужны.

Состояния реализации предлагаются как NotStarted → Starting → Running → Stopping → Finished. После успешных предварительных проверок единственный process-wide допуск расходуется атомарно, до native-инициализации. Ошибка Startup также ведёт к завершённой попытке. Неправильный поток/повторный Run возвращает ошибку и не меняет текущий runtime; отклонение до допуска его не расходует. Эти правила возврата error относятся только к живой форме. Run сначала проверяет логическое уничтожение: уничтоженная форма вызывает panic до проверки потока и использованной попытки, без native-действий и изменения допуска. Приоритет действует и до первой попытки, и после её расходования; прежний контракт обычной операции уничтоженного объекта сохраняется. Повторный Run проверяется до обычного внутреннего освобождения peers, без необходимости превращать сам Go-объект формы в уничтоженный только ради закрытия окна.

### Принято: готовность и остановка

Starting остаётся закрытым для Post. Только после backend init, создания peers, применения свойств/геометрии и готовности очереди с пробуждением единый переход в Running открывает приём. Он предшествует обычной прикладной доставке и не ждёт первого paint. Сигналы native-подготовки не должны просачиваться как прикладные события. Отдельный OnReady не вводится; пример запускает фон из кнопки.

Запрос закрытия главной формы не отменяется. На его обработке закрывается приём Post, отменяются ещё не начатые задачи и уведомления, новые обработчики не запускаются; текущий вызов не прерывается принудительно. Гонка принятия имеет единую границу. После выхода из callback очищаем ресурсы на UI-потоке; Run возвращает nil или все сбои. Если текущий прикладной вызов сам паникует, действует уже принятый аварийный контракт, первичная паника не теряется.

Предлагаемый внутренний механизм: собственная очередь и платформенное пробуждение loop, без прямого вызова Post-функции из механизма уведомления. На GTK не полагаться на обещание «всегда отложено» у произвольного invoke helper; технический этап проверяет отсутствие inline-выполнения и рекурсии. Обработку native callback оборачивать перехватом panic до возврата через FFI. Конкретные wakeup primitives — детали реализации, порядок относительно native events/OnChange не выбирается.

### Принято: экспериментальная поверхность MVP

- ui.NewForm(); ui.NewEdit(owner), ui.NewButton(owner), ui.NewLabel(owner) создают логические объекты без автоматического Parent и без native-ошибки в конструкторе.
- form.SetTitle(string), control.Text() string, control.SetText(string), control.SetParent(parent) error; Destroy(), Destroyed() bool сохраняют прежние правила.
- button.SetOnClick(func()), edit.SetOnChange(func()); один заменяемый обработчик, nil отключает. Program/User и сигнатуры других событий не выбраны.
- ui.Post(func()) error и form.Run() error. Внутренний экземпляр приложения единственный; отсутствие публичного Application относится только к MVP.
- form.SetClientSize(width, height), control.SetBounds(x, y, width, height): целые логические единицы, клиентская область без декораций, Bounds: фиксированные координаты относительно внутренней области Parent, минимальные ширина/высота с возможным увеличением по нативным минимумам темы; SetClientSize задаёт точный размер клиентской области; только до Run. Размеры > 0, x/y >= 0, нарушение значений — panic. Автоисправления пересечений нет.

Пример явно задаёт все размеры: форма 400×180, Edit (16,16,368,28), Button (16,56,160,32), Label (16,104,368,32). Это точный клиентский размер формы и минимальные размеры контролов примера, которые проверяются на обеих ОС, а не обязательные размеры любых приложений. 28 октября 2026 года пользователь уточнил SetBounds: сохранять нативный вид и разрешать увеличение до минимума темы. На GTK4/X11 измерены Edit 368×29 при запросе 368×28 и Button 160×34 при запросе 160×32; Label 368×32 и клиентская область 400×180 совпадают с запросом. Координаты фиксированы; автоматическая перестановка/устранение пересечений не вводится. Windows переводит логические единицы в свою систему координат, GTK использует свою; одинаковые физические пиксели не обещаются. Масштаб фиксируется при запуске, пользовательское resizing запрещено. Точное значение проверенного масштаба записывается в отчёт для каждой машины.

Конкретные экспортируемые типы Owner/Parent и представление ошибок — минимальные детали реализации, без утверждения интерфейса расширения сторонними компонентами. В MVP используются форма-владелец и форма-контейнер. Ошибки конструктора для произвольных недопустимых Owner, использование геометрии после Run и неописанные сочетания не получают здесь новых обещаний. Рекомендуемые примеры используют только поддерживаемую поверхность; ограничения документируются явно.

### Принято: ошибки запуска и очистка

При отказе загрузки runtime/символа, backend init или создания peer остановить запуск и очистить уже созданное. Исходная ошибка и все дополнительные сбои возвращаются из Run; Post так и не открыт. При обычном закрытии первичной паники нет: nil при успехе либо ошибка со всеми сбоями очистки. В обоих случаях ошибки не прекращают независимую очистку, panic ловится на границе отдельной операции со значением/стеком и не выбрасывается повторно. Прикладная доставка не возобновляется.

Формат ошибки должен позволять сохранить исходные значения и стеки для диагностики и проверок; стабильный публичный тип и агрегатор не выбираются. Реализация освобождает конкретные ресурсы четырёх компонентов в безопасном порядке согласно backend; это не универсальный контракт порядка зависимостей, повторов или тайм-аутов. Fake-backend/fault injection проверяет редкие отказы, но не заменяет native-прогоны.

## Risks / Trade-offs

- FFI ABI, callbacks и GC → сначала технический проход на обеих ОС, проверка сигнатур, строк и владения; фиксированные callback trampolines с идентификаторами объектов вместо бесконечного создания FFI callbacks.
- Сборка прошла, GUI нет → отдельные реальные прогоны; Windows-проба и последующая native-приёмка общего примера подтверждены; свидетельства обеих ОС сохранены в docs/mvp-validation.md, кросс-компиляция не заменяет реальные прогоны.
- Native начальные сигналы/повторный SetText → ядро нормализует изменения и подавляет прикладную доставку до готовности; тесты coalescing/nil/reset сохраняются.
- Reentrancy или lost wakeup → тесты вложенного Post, конкурентной готовности/закрытия и пробуждения; callback не обслуживает очередь рекурсивно.
- Полные specs шире MVP → отчёт сопоставляет проверенное, неприменимое и отложенное; не менять старые требования ради удобства MVP.
- Фиксированная геометрия может обрезать native-текст → ручная проверка кириллицы/размеров при записанном масштабе каждой ОС; изменение размера окна и межмониторный DPI не обещаются.

## Migration Plan

1. Apply в feature-ветке от актуальной develop, без worktree. Сначала технический эксперимент FFI/bootstrap, затем общий контракт backend; только после этого независимые Windows/Linux реализации параллельно через Subagent Driven Development. Общие файлы и Git у координатора, review и commit/push каждого этапа, финальный PR.
2. Создать модуль, закрепить зависимости и результаты эксперимента. Сначала минимальные native вызовы, callbacks и OS-thread check; при невозможности сохранить принятые гарантии сообщить конкретный блокер, не заменять purego на cgo/bridge молча.
3. Реализовать ядро, backend, один пример и проверки из tasks.md. Прогоны Run разнести по отдельным процессам из-за единственной попытки. Ошибки запуска/очистки проверять управляемыми отказами; сборку без C toolchain — в воспроизводимом окружении с журналом команды/версий.
4. Обновить docs/design.md, текущие контракты и README: меньший MVP не закрывает E0 или полный E1/T-01–T-09. Сохранить исторические отчёты/архивы. В основных Scope application-failure, post-dispatch и component-events временно указать выбранные MVP-дополнения в change, не синхронизируя Requirements до отдельного workflow.
5. Отчёт docs/mvp-validation.md: фактическая матрица, результаты каждого критерия, ограничения, версии, логи/ручные проверки и точные финальные Scope для последующего sync/archive. Удалить общие «обычная остановка/запуск/сигнатуры полностью открыты» только в пределах принятого MVP; остальной контракт полной библиотеки открыт. Purpose существующих specs сохранять. Новая native-ui-runtime получает Purpose из дельты.
6. Отдельный sync/archive применяет пять дельт, сохраняет все прежние требования/сценарии, вручную обновляет Scope и ссылки. Откат реализации — обратный коммит; миграций пользовательских данных нет.

## MVP acceptance

- M-01: обе сборки Go 1.26.5/CGO_ENABLED=0 без GCC/Clang, GUI headers и pkg-config; purego закреплён.
- M-02: реальный запуск общего примера на обеих принятых ОС; native-контролы, кириллица, фиксированная геометрия без обрезания и resizing.
- M-03: native callback вызывает Go; SetText/OnChange соблюдают реальное изменение, тихую подготовку, объединение без рекурсии, замену/nil/reset; никакой доставки до готовности.
- M-04: Post из goroutine и UI, FIFO/вложенность/отказ nil, единые границы готовности и остановки; задачи выполняются на UI-потоке.
- M-05: Run уничтоженной формы вызывает panic раньше проверки потока/попытки, без изменения допуска; неверный/повторный Run живой формы отклонён без изменения работающего UI; невалидный первый вызов не расходует попытку, ошибка инициализации расходует.
- M-06: обычное закрытие отменяет ожидание и успешно возвращает nil; ошибки/паники очистки дают полный error без rethrow.
- M-07: отказ запуска после частичного создания очищает созданное, сохраняет исходную ошибку/все сбои, Post не открывается.
- M-08: паника обработчика/Post сохраняет прежнюю аварийную политику; Destroy/Destroyed, отмена уведомлений и освобождение callbacks/реестра проверены для доступных MVP объектов.

M-01 соответствует T-01, M-02/M-03 части T-02/T-03, M-04 части T-05, M-07 части T-07/T-09. Полные T-04/T-06/T-08/T-09 (resizing, динамические циклы, отмена закрытия и динамический rollback) не заявляются выполненными. Все M требуют свидетельств; документ с планом не является результатом испытаний.

## Open Questions

Публичный Application и окончательный получатель Post/стабильность API; окончательный module path, лицензии зависимостей; другие ОС/архитектуры/версии, Wayland и автоматический выбор backend; полноценные layout и DPI.

Остаются вопросы из предыдущих реестров, кроме явно принятой здесь MVP-части: ожидание/индивидуальная отмена Post, владелец задач, перегрузка и типы отказа; порядок относительно native events/OnChange, справедливость и взаимные изменения; Program/User/прочие сигнатуры; циклы/смена Owner, переносы, динамическое создание/отсоединение и повторное присоединение в callback, фокус/выделение/откат; расширенные ошибки конструкторов/setters, публичная диагностика и объединение, зависимая очистка/повторы/тайм-ауты, внутренние сбои вне отдельных cleanup операций и самостоятельный Destroy. Обычная остановка/повторный запуск полной библиотеки, Close/Hide, модальность, формы, дизайнер, Qt, поставка runtime, доступность/IME/локализация остаются открытыми. Q-01–Q-14 и ADR не объявляются целиком закрытыми.

В первом этапе реализации закреплена purego v0.11.2 и получен реальный Windows-прогон технической пробы: Windows 11 Pro build 26100, amd64, 100% (96 DPI). 28 октября 2026 года обе автоматические Windows suites и все ручные сценарии Linux/Windows пройдены; M-01–M-08 приняты в узкой поверхности MVP, свидетельства и ограничения сохранены в docs/mvp-validation.md. Это не закрывает E0, полный E1 или перечисленные выше открытые вопросы; sync/archive выполняются отдельно.
