# Proposal

## Why

Golphi пока содержит проектные контракты, но не исполняемый GUI. Нужен узкий MVP для проверки native-вызовов без C toolchain, общего Go API, callbacks и доставки Post на двух ОС без предварительного закрытия всего E0.

## What Changes

- Реализовать одну главную форму с Edit, Button и Label, прямыми Win32/GTK4-вызовами и внутренней зависимостью от purego, без собственного C bridge.
- Закрепить startup thread внутри Golphi через init; Form.Run вызывается из main и допускает одну прошедшую проверки попытку на процесс.
- Предоставить экспериментальный минимальный API с Owner/Parent, обработчиками func(), пакетным ui.Post, фиксированными координатами и минимальными размерами контролов через SetBounds, точным размером клиентской области через SetClientSize; пользовательское resizing отсутствует.
- Открывать Post после успешной подготовки формы, до прикладных событий, без ожидания первой отрисовки.
- Определить обычное закрытие без отмены, отмену ожидающей доставки, очистку и возврат nil либо всех сбоев; при ошибке запуска сохранять исходную ошибку и сбои очистки.
- Проверить одинаковый пример на Linux Mint 22.3/amd64/X11/GTK 4.14.5 и Windows 11/amd64, со сборкой Go 1.26.5 и CGO_ENABLED=0.

## Capabilities

### New Capabilities

- `native-ui-runtime`: нативный запуск, UI-поток, единственная попытка Run, обычное закрытие и проверяемая платформенная матрица MVP.

### Modified Capabilities

- `component-lifecycle`: минимальные конструкторы, свойства и фиксированная геометрия MVP; прежние правила Owner/Parent и Destroy сохраняются.
- `component-events`: сигнатуры func() для двух событий MVP и прекращение уведомлений при обычном закрытии.
- `post-dispatch`: пакетный API MVP, граница готовности и отмена/гонка принятия при обычном закрытии.
- `application-failure`: диагностика ошибок запуска и очистки без первичной паники при обычном закрытии MVP.

## Impact

Будущее apply создаёт Go-модуль, ui, внутреннее ядро и backend Win32/GTK4, пример, тесты и отчёт проверок. Версия purego выбирается и закрепляется после технического эксперимента; окончательный module path остаётся открытым. Native-типы не входят в публичный API.

Это меньший проверочный срез перед полным E1 из docs/design.md: динамическое добавление/перенос контролов, отмена закрытия, resizing, несколько окон и полная T-01–T-09 не входят. Принятые общие контракты не отменяются, их реализация проверяется в доступной MVP поверхности; недоступные сценарии не объявляются выполненными. Публичный Application и прочие открытые вопросы полной библиотеки сохраняются.

Разработка: ветка от актуальной develop, без worktree; Subagent Driven Development, независимые этапы параллельно при возможности, Git только у координатора; review, commit/push по этапам, итоговый PR в develop. Текущий propose создаёт только артефакты, реализация начинается отдельным apply.
