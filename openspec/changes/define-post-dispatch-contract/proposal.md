# Proposal

## Why

После согласования аварийной остановки судьба задач Post оставалась неопределённой. Новый контракт фиксирует передачу работы на UI-поток и её границу с остановкой, сохраняя различие между принятием и выполнением задачи.

## What Changes

- Post(fn) error безопасен из любой goroutine: nil означает принятие, ошибка — отказ без постановки и выполнения; Post(nil) сразу возвращает ошибку без аварийной остановки.
- Принимать задачи только во время работы приложения; до запуска Form.Run() отклонять с ошибкой.
- Всегда ставить функцию в очередь, включая вызовы с UI-потока; выполнять последовательно на UI-потоке после завершения текущего обработчика или задачи.
- Сохранять FIFO для последовательно принятых задач; вложенный Post добавлять в конец очереди без рекурсии. Не обещать порядок конкурентных отправителей и порядок относительно native events/OnChange.
- При аварийной остановке отменять все ещё не начатые задачи и отклонять новые. Гонка принятия и остановки имеет однозначный исход; принятие не гарантирует выполнение при последующей аварии.
- Применять к панике внутри Post ту же остановку, очистку и диагностику через Form.Run(), что и к панике обработчика.
- Обычный Post не связан с владельцем: уничтожение захваченного компонента задачу не отменяет; Destroyed() безопасен, обычное обращение к уничтоженному объекту вызывает панику и аварийную остановку.

## Capabilities

### New Capabilities

- `post-dispatch`: принятие, очередь, выполнение и отмена обычных задач Post на границе аварийной остановки.

### Modified Capabilities

- `application-failure`: включить панику функции Post в общую политику остановки и диагностики, запретить новые задачи и отменять ожидающие.

## Impact

Документальный этап E0: при apply обновить docs/design.md и контракты, добавить проектные трассировки Post. Runtime, очередь, backend и FFI не реализуются. Дельты синхронизируются отдельным workflow; исторические архивы не меняются.

Обычная остановка, ошибки очистки, порядок относительно native events/OnChange, ожидание результата, индивидуальная отмена, задачи с владельцем, точные типы ошибок, bootstrap UI-потока и остальные вопросы остаются открытыми. Q-04/Q-05/Q-06 и весь E0 не закрываются. Процесс применения — по docs/development.md: ветка от develop без worktree, Subagent Driven Development, независимые задачи параллельно, Git у координатора, commit/push по этапам и итоговый PR.
