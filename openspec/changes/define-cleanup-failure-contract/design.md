# Design

## Context

Application-failure уже задаёт остановку после паники обработчика или Post, отмену прикладной доставки и очистку после выхода из callback. Её Scope исключает сбои очистки, а Run returns panic diagnostics содержит два сценария успешной очистки. Post-dispatch повторяет исключение в Scope и Failure shutdown cancels unstarted tasks. Документы также объявляют ошибки очистки полностью открытыми. Runtime отсутствует; мотивация — proposal.md, Why.

## Goals / Non-Goals

**Goals:** описать наблюдаемую диагностику и продолжение независимых операций при сбоях очистки; расширить гарантию Run без потери первичной причины; сохранить прежние сценарии и границы остановки.

**Non-Goals:** реализация runtime/FFI, выбор типа ошибки, errors.Join или иного агрегатора, алгоритма обхода ресурсов, обычная остановка и закрытие всего E0.

## Decisions

### Принято: диагностика дополняется

Первоначальная паника обработчика или функции Post, её значение и стек остаются в результате. Ошибки очистки добавляются; для каждой перехваченной паники очистки сохраняются её значение и стек. Замена исходной причины последним сбоем или сохранение только первой ошибки очистки не соответствует решению. Способ представления и объединения не выбирается: полнота диагностики — наблюдаемый контракт, формат — открытый вопрос.

### Принято: продолжение независимых операций

Ошибка операции А не препятствует попыткам очистить независимые Б и В. Паника А перехватывается на границе отдельной операции и не препятствует тем же попыткам. Продолжение означает переход к остальным независимым операциям, а не возобновление тела упавшей операции. Успех освобождения всех ресурсов не гарантируется одним фактом попыток.

Трассировки используют ресурсы, независимость которых дана условием; порядок зависимых ресурсов, определение зависимостей и механизм безопасного обхода не назначаются этим изменением. Отмена остальных независимых операций при первом сбое отвергнута. Повторные попытки не добавляются как принятое решение.

### Принято: Run возвращает весь собранный результат

После выхода из callback и завершения попыток очистки Run возвращает ненулевую ошибку с первичной паникой и её стеком, всеми ошибками очистки и значениями/стеками её паник. Перехваченные паники очистки не выбрасываются наружу повторно. Это расширение прежней гарантии успешной очистки; оба прежних сценария остаются частными случаями.

Запрет запуска новых прикладных обработчиков и Post, отмена ожидающего и отказ новых Post действуют и во время очистки. Сбой очистки не возобновляет приложение. Случаи без первоначальной паники (обычная остановка, самостоятельный Destroy вне этой остановки) данным обсуждением не определены.

### Структура дельт и миграция оговорок

Application-failure получает три ADDED-требования и полный MODIFIED-блок Run returns panic diagnostics с обоими прежними сценариями. Остальные требования сохраняются. Post-dispatch получает полный MODIFIED Failure shutdown cancels unstarted tasks с обоими прежними сценариями: меняется только ссылка на расширенную политику очистки.

При apply Scope обеих основных спецификаций должен временно указывать: прежняя область действует до sync, согласованное расширение находится в change. Purpose и Requirements до sync не менять. В итоговом отчёте подготовить точные окончательные Scope: application-failure больше не исключает все сбои очистки и не ограничивает Run успешной очисткой; post-dispatch ссылается на расширенную application-failure. Оба сохраняют открытыми обычную остановку, порядок зависимых ресурсов, тип ошибки/способ объединения и прочие оставшиеся вопросы. Purpose менять не требуется. Автоматическое слияние Requirements не обновляет Scope.

## Risks / Trade-offs

- Последняя паника затрёт первоначальную → трассировка смешанных E1/E2/W с сохранением V и обоих стеков.
- Перехват вокруг всей очистки пропустит независимые ресурсы → сценарий паники одной операции и последующих попыток Б/В.
- «Очистка завершена» будет прочитана как гарантия освобождения → говорить о завершении попыток, сохраняя ошибки.
- Примеры зададут порядок зависимостей → независимость задаётся условием, относительный порядок Б/В не обещается.
- Старые оговорки исключат принятые правила → отдельные правки Scope и актуальных реестров, без переписывания исторических отчётов.

## Migration Plan

1. При apply создать ветку от актуальной develop без worktree; использовать Subagent Driven Development, независимые файлы распределять параллельно, Git оставить координатору; commit/push по этапам и PR в develop.
2. Обновить docs/contracts/application-failure.md: сохранить старые восемь сценариев и добавить трассировки всех новых, включая смешанные ошибки/паники, продолжение независимых операций и возврат Run после сбоя очистки. Обновить docs/contracts/post-dispatch.md, сохранив все 18 сценариев и правила очереди.
3. После контрактов обновить docs/design.md: описание остановки, Q-05, реестр решений и историю; согласовать актуальные реестры docs/contracts/component-events.md и component-lifecycle.md. Вместо полного исключения ошибок очистки перечислить конкретный остаток вопросов. Исторические отчёты и архивы не менять.
4. Подготовить переходные Scope основных application-failure/post-dispatch, не синхронизируя требования; сохранить окончательные Scope в docs/contracts/cleanup-failure-review.md. Провести отдельные и итоговое review, строгую валидацию, проверку ссылок и сохранения старых сценариев. Это документальные проверки, не T-01–T-09.
5. По отдельному запросу sync/archive применить обе дельты и вручную заменить Scope окончательными текстами отчёта, сохраняя Purpose и прочие разделы. При переносе change исправить ссылки актуальных документов.

Откат документационного этапа — обратное изменение ветки, без миграций данных.

## Open Questions

Эти вопросы не блокируют фиксацию выбранной части контракта, но требуют решения до соответствующей реализации:

- Публичный тип ошибки, API доступа, представление стеков, способ объединения и порядок представления собранных сбоев.
- Порядок очистки зависимых ресурсов и определение зависимостей; повторные попытки и судьба неосвобождённых ресурсов; зависшие операции, тайм-ауты и принудительное прерывание.
- Обычная остановка и очистка без первичной паники; самостоятельный Destroy, ошибки запуска, сбои внутренних механизмов вне отдельных операций очистки, повторный Run и состояние после возврата.
- Bootstrap/закрепление UI-потока, граница готовности Run и проверка потоковых правил; ожидание результата/индивидуальная отмена Post, API с владельцем, получатель, типы отказа и перегрузка.
- Порядок Post относительно native events/OnChange, справедливость, взаимные изменения; сигнатуры/Program/User и новое накопление после отсоединения/присоединения в одном callback.
- Ошибки конструкторов и setters живых компонентов; циклы/смена Owner, переносы между формами, native lifecycle, фокус и откат SetParent.
- Остаток Q-01–Q-14: module path, bridge/независимость, backend/baseline, Close/Hide/модальность, layout, формы, поставка runtime, Qt, дизайнер и доступность.
