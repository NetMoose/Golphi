# Design

## Context

Действующие component-lifecycle/component-events определяют уничтожение и отмену уведомлений; application-failure содержит 3 требования об аварийной остановке при панике обработчика и явно исключает Post. Раздел 6.4 docs/design.md пока предлагает Post и задачи, связанные с формой; runtime отсутствует. Мотивация — proposal.md, Why. Новый этап документирует выбранную часть Q-04/Q-05/Q-06.

## Goals / Non-Goals

**Goals:** отделить принятие от выполнения; задать проверяемые последовательности очереди и границу аварийной остановки; расширить единый контракт паники на Post, не менять правила компонентов.

**Non-Goals:** реализация диспетчера/FFI/backend, выбор блокировок и очереди, обычная остановка, ошибки очистки, окончательный Application API, ожидание результата и автоматическая отмена по владельцу. Весь E0 не закрывается.

## Decisions

### Принято: очередь, а не непосредственный вызов

Post(fn) error можно вызвать из любой goroutine. nil означает принятие, error — отказ без постановки и выполнения. Post(nil) сразу ошибочен, но не вызывает остановку. До запуска Form.Run() задачи отклоняются; принимаются только во время работы приложения. Точная граница завершения bootstrap остаётся открытой, её не следует подменять первым входом в тело Run.

Все принятые функции ставятся в очередь и исполняются последовательно на UI-потоке. Вызов с UI-потока не превращается в непосредственный вызов: отправленная из обработчика/задачи функция не начинается до завершения текущего вызова. Для фонового отправителя не обещается, что задача обязательно начнётся только после возврата самого Post; nil подтверждает принятие, не момент исполнения.

Альтернатива непосредственного исполнения с UI-потока отклонена ради отсутствия неожиданного повторного входа. Накопление до Run отклонено, чтобы не вводить судьбу незапущенной очереди. Механизм пробуждения и закрепления потока — будущая реализация.

### Принято: FIFO и вложенная отправка

Последовательно принятые задачи выполняются FIFO, если не отменены. Вложенный Post помещает задачу в конец: выполняется А, ожидает Б, А отправляет В — завершение А → Б → В. Порядок конкурентных отправителей заранее не обещается. Сценарий выполнения обеих конкурентно принятых задач предполагает отсутствие отмены: если первая выполняемая задача вызывает панику, ещё не начатая вторая отменяется по общей политике аварийной остановки. Это правило только между задачами Post: приоритет относительно native events/OnChange, квант обработки и справедливость не выбираются.

### Принято: единая аварийная остановка

Паника обработчика или функции Post закрывает приём задач, отменяет все ещё не начатые задачи и ожидающие прикладные уведомления; новые прикладные обработчики и задачи не запускаются. Внутренний выход и очистка продолжаются. При успешной очистке Form.Run() возвращает ошибку с исходным значением и стеком. Нет нового механизма повторного запуска или восстановления UI. Ошибки очистки не получают неявного приоритета или агрегации.

Гонка Post и аварийной остановки наблюдаемо однозначна: принятие до остановки даёт nil (ещё не начатая задача затем отменяется), либо отказ даёт error без очереди. Это требование согласованности, а не выбор mutex/atomic/канала. Не обещается принудительное прерывание произвольной выполняющейся функции.

### Принято: обычный Post без владельца

Захват компонента замыканием не создаёт связи владения. Уничтожение само не отменяет задачу: она может проверить Destroyed() и пропустить работу. Обычный метод уничтоженного компонента вызывает панику, которая при достижении границы функции Post запускает общую остановку. Автоматический анализ замыканий или скрытая привязка к форме отвергнуты; специальный API задач с владельцем остаётся открытым.

### Границы API и незакрытые вопросы

Обозначение Post(fn) error фиксирует функцию без аргументов/результата и отчёт о принятии; не выбирает получателя метода (app/form/package), конструктор Application, точные error-типы, ёмкость очереди или политику перегрузки. Последние вопросы не должны превращаться в дополнительные обещания принимаемости или задержки.

Новые требования принадлежат post-dispatch; application-failure обновляется полными MODIFIED-блоками с прежними именами и всеми 4 исходными сценариями. Правила Owner/Parent и событий не переписываются.

## Risks / Trade-offs

- nil может быть ошибочно прочитан как гарантия исполнения → явная трассировка «принятие, затем авария, отмена».
- Постановка из UI может вызвать скрытую рекурсию → отдельные сценарии обработчика и вложенной задачи.
- FIFO могут распространить на native events → явно ограничить область очередью Post.
- Захвачен уничтоженный компонент → показать обе трассировки: безопасный Destroyed() и panic обычного метода.
- Старые оговорки объявляют Post полностью открытым → обновить ненормативные Purpose/Scope отдельно от слияния Requirements.
- Сбой очистки может скрыть первоначальный → оставить отдельным вопросом, не обещать результат Run в этом случае.

## Migration Plan

1. При apply создать ветку от актуальной develop без worktree; использовать Subagent Driven Development, параллельно распределить непересекающиеся документы, Git оставить координатору. Commit/push после этапов, PR в develop.
2. Создать docs/contracts/post-dispatch.md с трассировками каждого сценария; обновить docs/contracts/application-failure.md под обе границы прикладного вызова. Общий docs/design.md обновлять после отдельных контрактов: разделы 6.3–6.4, 7.4, реестр решений, Q-04/Q-05/Q-06 и история. Остаток вопросов ниже сохранить.
3. При apply основной application-failure Scope временно обозначает, что прежняя область действует до sync, а расширение на Post описано этим change; оставить явные исключения ошибок очистки/обычной остановки. Purpose и Requirements на apply не менять. В component-events Scope заменить только общее «Post» среди открытых вопросов на «порядок относительно Post» и ссылку на change; Parent-абзац и Requirements сохранить. Согласовать актуальные docs/contracts/component-events.md и component-lifecycle.md, если их реестры всё ещё объявляют принятие/отмену Post полностью открытыми. Исторические отчёты и архивы не переписывать.
4. Сохранить docs/contracts/post-dispatch-review.md с покрытием, проверками, оставшимися блокерами и точным текстом будущей миграции Purpose/Scope. Проверки относятся к документации, не к runtime или T-01–T-09.
5. При отдельном sync/archive применить обе дельты. Новому post-dispatch перенести Purpose и Scope. В application-failure вручную расширить Purpose до паники «прикладного обработчика или функции Post»; Scope охватывает обе причины аварийной остановки и отмену Post, оставляет ошибки очистки, внутренние сбои и обычную остановку открытыми, возврат Run — при успешной очистке. Убрать переходную оговорку; в component-events заменить ссылку на change ссылкой на основную post-dispatch, оставив порядок относительно Post открытым. Автоматическое слияние Requirements этих абзацев не обновляет. Проверить ссылки после переноса change.

Откат документального этапа — обратное изменение ветки; миграции данных нет.

## Open Questions

Остаются за пределами этого документального изменения и требуют решения до соответствующей реализации:

- Обычная остановка: судьба уже принятых задач, момент закрытия приёма, Close/Hide и условия выхода; режим после возврата Run и возможность повторного Run.
- Ошибки/паники очистки, приоритет и объединение с первичной паникой; типы диагностики, доступ к значению/стеку.
- Порядок Post относительно native events/OnChange, взаимные изменения компонентов, справедливость и бесконечные последовательности.
- Ожидание результата и индивидуальная отмена; специальный API задач с владельцем; получатель Post и точные ошибки отказа; ёмкость/перегрузка очереди.
- Bootstrap и закрепление UI-потока, точная граница готовности во время запуска Run, ограничения Run и проверка нарушения потоковых правил.
- Ошибки конструкторов/setters живых компонентов; сигнатуры событий и Program/User; новое накопление после отсоединения/присоединения в одном callback.
- Циклы/смена Owner, переносы между формами/приложениями, присоединение к неотображаемому контейнеру, native lifecycle, фокус и откат SetParent.
- Остальные Q-01–Q-14: module path, независимость/bridge, backend/baseline, layout, формат форм, поставка runtime, Qt, дизайнер, доступность.
