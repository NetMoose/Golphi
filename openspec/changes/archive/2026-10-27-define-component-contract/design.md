# Design

## Context

См. `proposal.md` — Why. Исходная архитектура находится в `docs/design.md`, версия 0.1-draft. README уже называет проект Golphi. Реализованного публичного API в просмотренных файлах нет; проверенные платформенные возможности не заявляются. Настоящий change фиксирует согласованную часть E0, а не завершает весь E0.

## Goals / Non-Goals

**Goals:** отделить принятые решения от предложений; дать проверяемые сценарии lifecycle и событий; подготовить основу для согласования API на трёх примерах; сохранить список вопросов, блокирующих последующую реализацию.

**Non-Goals:** реализация библиотеки, выбор FFI и версий toolkit, дизайнер, генератор форм, утверждение всех ADR черновика. Наличие planning artifacts не означает готовность runtime к реализации без решения его блокирующих вопросов.

## Decisions

### Принято пользователем: название и ориентир API

Название — Golphi. Модель должна быть близка к VCL; другой API допустим при продемонстрированных удобстве и логичности. Полная совместимость с VCL не обещается. Альтернатива механического копирования API не выбрана; любые ещё не согласованные сигнатуры остаются эскизами.

### Принято пользователем: две связи компонента

Owner отвечает за владение, Parent — за визуальную иерархию. Это заменяет предложение единого дерева в разделе 8.1 исходного документа. Смена Parent сохраняет Owner. Можно создавать и настраивать компонент с Owner без Parent. Уничтожение проходит по обоим отношениям, поэтому при пересечении деревьев ресурс освобождается один раз.

Уничтожение панели уничтожает её визуальных потомков даже при Owner = форма. Альтернатива сохранения детей уничтоженного контейнера отвергнута. Отсоединение, напротив, сохраняет компонент и поддерево: для этого служит SetParent(nil).

### Принято пользователем: присоединение с откатом

`SetParent(parent) error` либо завершает перенос, либо сохраняет старого родителя и все настройки, обработчики и работоспособность компонента. Ошибка первого присоединения оставляет Parent = nil. Отсоединённое поддерево можно присоединить повторно.

Предложение реализации, не принятое техническое решение: подготовка нового представления до фиксации логической связи и очистка временных ресурсов при неуспехе. Backend должен доказать сохранение старого отображения; восстановить только поле Parent недостаточно. Сохранение или пересоздание native peers при отсоединении пока не выбрано.

### Принято пользователем: один обработчик

Основной API использует один обработчик на событие. SetOnClick заменяет его, nil отключает. Это заменяет предложение OnClick с несколькими подписками и Disconnect из раздела 7.2. Внутренние механизмы backend этим решением не определяются.

### Принято пользователем: нормализация OnChange

См. `specs/component-events/spec.md`. У работающего присоединённого компонента реальное изменение, включая SetText из кода, вызывает OnChange. Подготовка до запуска и изменение отсоединённого компонента проходят без уведомлений. Для событий присоединённость определяется цепочкой Parent до формы, а не только наличием непосредственного Parent: поле внутри отсоединённой панели тоже отсоединено. Owner и видимость это определение не меняют; работающий runtime — отдельное условие доставки.

Следующее правило действует при неизменном обработчике и компоненте, остающемся живым, работающим и присоединённым от входа в обработчик до повторной доставки. При изменениях внутри собственного OnChange текст обновляется сразу. После выхода сравниваются итоговый текст и текст на входе: различие порождает одно отложенное уведомление, равенство отменяет повторное. Альтернативы рекурсивного вызова и очереди всех промежуточных значений отвергнуты пользователем.

Предложение реализации: хранить признак доставки события и значение на входе; не создавать отдельную запись на каждое промежуточное изменение. Это не определяет очередность относительно Post, других компонентов и нативных событий. Замена/отключение обработчика, уничтожение, отсоединение (в том числе предка) или остановка до повторной доставки исключены из данного правила; политика ожидающего уведомления для этих случаев остаётся открытой.

### Принято пользователем: процесс разработки

- Не использовать git worktree. Для отдельных фич создавать ветки от `develop` в обычном checkout.
- После каждого этапа проверять результат, делать commit и push feature-ветки; по завершении создавать PR. Целевая ветка PR по предлагаемому рабочему правилу — `develop`; это допущение организации процесса, а не отдельное согласованное требование.
- Использовать навык Subagent Driven Development для отдельных этапов разработки. Независимые задачи запускать параллельно, если инструменты и зависимости позволяют.
- При общей рабочей директории назначать агентам непересекающиеся файлы. Переключение веток, интеграцию, commit и push выполняет один координатор последовательно. Зависимые задачи и правки общих файлов не запускать одновременно.
- Отсутствие сабагентов или невозможность безопасного параллелизма явно отмечать; выполнять этап последовательно без worktree.

Эти правила относятся к дальнейшей разработке. Текущий запрос — создание planning artifacts, не начало apply, публикация или реализация.

## Risks / Trade-offs

- Две иерархии и их пересечение → проверять каскады уничтожения и отсутствие повторного освобождения; правила допустимых циклов ещё определить.
- Перенос native controls может быть необратимым на отдельных платформах → проверить возможность выполнения контракта до реализации соответствующего backend.
- Отсрочка OnChange не исключает бесконечную последовательность изменений → отдельно определить справедливость диспетчера и диагностику; автоматический лимит пока не принят.
- Общий checkout нескольких агентов → разделять файлы и сериализовать операции Git, не создавать worktree.
- Конфликт с исходным черновиком → при применении синхронизировать только согласованные разделы, не переводить все Proposed в Accepted.

## Migration Plan

1. При применении уточнить реестр открытых вопросов и подготовить проектные примеры API.
2. Согласовать `docs/design.md` с данным контрактом: название, разделы 5–8, вопросы Q-01/Q-05/Q-06 и соответствующие записи решений. Не объявлять весь E0 завершённым.
3. Проверить соответствие каждого принятого решения сценарию, провести review и валидацию OpenSpec.
4. После этапов выполнять commit/push, по завершении открыть PR. Миграции данных нет; откат документации выполняется обычным обратным изменением в ветке.
