# Proposal

## Why

Golphi нужен проверяемый контракт компонентов до реализации платформенных backend. Черновик `docs/design.md` ещё предлагает единое дерево владения и несколько подписчиков, тогда как обсуждение установило отдельные Owner/Parent и один обработчик события.

## What Changes

- Зафиксировать название Golphi и ориентацию на VCL с допустимой адаптацией API к Go, если удобство показано на примерах.
- Определить отдельные Owner и Parent, каскадное уничтожение по обоим отношениям и создание без Parent.
- Определить `SetParent(parent) error` с сохранением прежнего состояния при ошибке и недеструктивное отсоединение через `SetParent(nil)`.
- Определить один заменяемый обработчик события и семантику OnChange: реальные изменения, подавление начальных уведомлений, отложенная доставка без рекурсии и объединение повторных изменений.
- Уточнить присоединённость через цепочку Parent до формы, включая потомков отсоединённой панели. Ограничить правило повторного OnChange неизменным обработчиком и живым, работающим, присоединённым компонентом.
- Сохранить нерешённые вопросы E0 явно открытыми, включая судьбу ожидающего уведомления при смене обработчика или жизненного состояния; специфицировать только согласованное поведение.
- Зафиксировать процесс разработки: отдельные feature-ветки от `develop`, без git worktree; commit и push после каждого этапа; PR по завершении. Применять Subagent Driven Development, параллельно выполнять независимые этапы при наличии такой возможности.

## Capabilities

### New Capabilities

- `component-lifecycle`: владение, визуальная иерархия, присоединение, отсоединение и уничтожение компонентов.
- `component-events`: один обработчик события и нормализованная доставка изменений текста.

### Modified Capabilities

Нет: существующих спецификаций OpenSpec пока нет.

## Impact

Это изменение этапа E0: результатом применения станут согласованный контракт, проектные примеры и согласование `docs/design.md` с принятыми решениями. Реализация runtime, backend, дизайнера и FFI остаётся за отдельными изменениями после закрытия соответствующих вопросов. Дельта-спецификации описывают целевое поведение, а не уже работающую библиотеку. Существующий код и зависимости этим предложением не изменяются.
