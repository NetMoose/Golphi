# post-dispatch Specification

## Purpose

Определить наблюдаемый контракт принятия и выполнения задач Post на UI-потоке Golphi и их отмены при аварийной остановке приложения.

## Scope

Контракт относится к обычному Post(fn), без владельца. Очистка и диагностика при аварийной остановке подчиняются [application-failure](../application-failure/spec.md): первоначальная паника сохраняется, сбои очистки добавляются к диагностике, попытки очистить остальные независимые ресурсы продолжаются, а Form.Run() возвращает всю собранную диагностику после завершения попыток.

Для узкого MVP пакетный ui.Post(func()) error, граница готовности и отмена при обычном закрытии определены требованиями ниже; bootstrap/закрепление UI-потока, ограничения Run и проверка потока — в [native-ui-runtime](../native-ui-runtime/spec.md); очистка без первичной паники — в [application-failure](../application-failure/spec.md).

Ожидание результата, индивидуальная отмена, задачи с владельцем, окончательный получатель Post полной библиотеки, стабильные типы отказа и перегрузка, порядок относительно native events/OnChange, справедливость и взаимные изменения остаются открытыми. Сохраняются открытые вопросы очистки из application-failure, а также bootstrap, готовность, потоковые правила и обычная остановка полной библиотеки вне выбранного MVP. Остальные вопросы E0 из [дизайна очистки](../../changes/archive/2026-10-27-define-cleanup-failure-contract/design.md) этим контрактом не разрешаются.

## Requirements

### Requirement: Post reports acceptance rather than completion
Post(fn) error SHALL возвращать nil при принятии функции в очередь и ошибку при отклонении. Отклонённая задача MUST NOT попадать в очередь или выполняться. Принятие MUST NOT означать завершение или гарантировать выполнение при последующей аварийной остановке либо обычном закрытии MVP.

#### Scenario: Accepted task
- **WHEN** работающий runtime принимает допустимую задачу Post
- **THEN** вызов возвращает nil как подтверждение принятия, а не завершения

#### Scenario: Rejected task
- **WHEN** Post отклоняет задачу
- **THEN** возвращается ошибка, задача не поставлена в очередь и не будет выполнена

#### Scenario: Acceptance followed by failure
- **WHEN** Post вернул nil, но аварийная остановка началась до выполнения задачи
- **THEN** задача отменяется; ранее возвращённый nil не является обещанием её выполнения

#### Scenario: Acceptance followed by normal closure
- **WHEN** Post вернул nil, но обычное закрытие MVP началось до выполнения задачи
- **THEN** задача отменяется; принятие не обещает её выполнения

### Requirement: Post rejects nil functions
Post(nil) SHALL сразу возвращать ошибку, не ставить задачу в очередь и не вызывать аварийную остановку приложения.

#### Scenario: Nil while running
- **WHEN** в работающем приложении вызывают Post(nil)
- **THEN** вызов возвращает ошибку без задачи в очереди и без аварийной остановки

### Requirement: Post accepts tasks only while running
Задачи Post SHALL приниматься только во время работы приложения. До запуска Form.Run() и во время подготовки MVP Post SHALL отклоняться с ошибкой. Для MVP приём SHALL открываться после успешной подготовки формы до прикладных событий, без ожидания первой отрисовки. После начала аварийной остановки или обычного закрытия MVP приём MUST быть закрыт.

#### Scenario: Before Run
- **WHEN** Post вызывают до запуска Form.Run()
- **THEN** возвращается ошибка, задача не накапливается для будущего запуска

#### Scenario: After failure shutdown begins
- **WHEN** Post вызывают после начала аварийной остановки
- **THEN** возвращается ошибка без постановки задачи в очередь

#### Scenario: Preparation is not readiness
- **WHEN** Run выполняет native-инициализацию, создание компонентов или начальное размещение
- **THEN** Post возвращает ошибку без накопления задачи

#### Scenario: Ready before first paint
- **WHEN** backend, native-компоненты, свойства, начальное размещение, очередь и пробуждение готовы, но первой отрисовки ещё нет
- **THEN** единый переход в Running открывает приём Post до начала обычной прикладной доставки

#### Scenario: Concurrent Post at readiness boundary
- **WHEN** Post конкурирует с переходом в Running
- **THEN** задача либо отклонена до готовности без очереди, либо принята после готовности; частично подготовленный UI ей недоступен

#### Scenario: Startup fails before readiness
- **WHEN** запуск завершился ошибкой до перехода в Running
- **THEN** приём Post не открывается, отклонённые задачи не выполняются

### Requirement: Post is safe across goroutines and executes on the UI thread
Post SHALL быть безопасным для вызова из любой goroutine. Принятые функции, дошедшие до выполнения, SHALL выполняться последовательно на UI-потоке и SHALL иметь возможность обращаться к живым компонентам по обычным правилам UI-кода. Механизм запуска и закрепления потока этим не определяется.

#### Scenario: Background caller updates a live component
- **WHEN** фоновая goroutine отправляет задачу, которая доходит до выполнения и обращается к живому компоненту
- **THEN** функция выполняется на UI-потоке без одновременного выполнения другой функции Post

### Requirement: Post always queues without recursive execution
Принятый Post SHALL всегда ставить функцию в очередь, включая вызов с UI-потока, и MUST NOT вызывать её непосредственно внутри Post. Задача, отправленная из текущего обработчика или функции Post, MUST NOT выполняться до завершения этого обработчика или функции.

#### Scenario: Posting from an event handler
- **WHEN** обработчик события вызывает Post с допустимой функцией
- **THEN** функция не вызывается вложенно и может начаться только после завершения текущего обработчика

#### Scenario: Posting from a running task
- **WHEN** выполняющаяся функция Post отправляет другую функцию
- **THEN** новая функция ставится в очередь и не вызывается рекурсивно до завершения текущей

### Requirement: Sequentially accepted tasks preserve FIFO
Последовательно принятые задачи Post SHALL выполняться в порядке принятия, если не отменены. Вложенный Post SHALL добавлять задачу в конец очереди, после уже ожидающих задач. Для конкурентных вызовов из разных goroutine заранее определённый порядок MUST NOT обещаться; порядок относительно native events и OnChange не определяется.

#### Scenario: Sequential submissions
- **WHEN** задачи А, Б и В приняты последовательно и не отменены
- **THEN** они выполняются в порядке А, Б, В

#### Scenario: Nested submission behind queued work
- **WHEN** выполняется А, в очереди ожидает Б, а А отправляет В и все задачи завершаются без отмены
- **THEN** В добавляется после Б, порядок завершения — А, Б, В, без рекурсии

#### Scenario: Concurrent submitters
- **WHEN** две goroutine конкурентно вызывают Post без дополнительного упорядочивания, обе задачи приняты и не отменены
- **THEN** обе принятые функции выполняются последовательно на UI-потоке, но контракт не обещает заранее, какая будет первой

### Requirement: Failure shutdown cancels unstarted tasks
При обнаружении паники прикладного обработчика или функции Post Golphi SHALL отменять все ещё не начатые задачи Post и MUST NOT запускать новые. Новые вызовы Post SHALL отклоняться с ошибкой. Очистка и диагностика, включая сбои отдельных операций очистки после первичной паники, подчиняются application-failure.

#### Scenario: Handler panic with queued tasks
- **WHEN** обработчик события вызывает panic при ожидающих задачах Post
- **THEN** все ещё не начатые задачи отменены и больше не запускаются, новые Post отклоняются

#### Scenario: Task panic with queued tasks
- **WHEN** выполняющаяся функция Post вызывает panic при ожидающих задачах
- **THEN** ожидающие задачи отменены, новые Post отклоняются и применяется остановка по application-failure

### Requirement: Acceptance has an unambiguous boundary with failure shutdown
Гонка Post с аварийной остановкой SHALL иметь один из двух исходов: задача принята до остановки с результатом nil и может быть отменена, либо отклонена с ошибкой без постановки. После начала остановки новые задачи MUST NOT приниматься.

#### Scenario: Acceptance wins the race
- **WHEN** Post принят до начала аварийной остановки, но его функция ещё не началась
- **THEN** Post возвращает nil, а остановка отменяет эту задачу

#### Scenario: Shutdown wins the race
- **WHEN** аварийная остановка началась раньше принятия конкурентного Post
- **THEN** Post возвращает ошибку и не ставит задачу в очередь

### Requirement: Ordinary Post has no component owner
Обычный Post(fn) SHALL быть не связан с владельцем. Уничтожение захваченного компонента MUST NOT само по себе отменять задачу. Функция SHALL иметь возможность проверить Destroyed(); обычное обращение к уничтоженному объекту SHALL вызывать panic и аварийную остановку по application-failure.

#### Scenario: Guarded access after destruction
- **WHEN** компонент уничтожен до выполнения принятой задачи, а задача проверяет Destroyed() и пропускает обычные обращения
- **THEN** само уничтожение не отменяет задачу; проверка безопасно возвращает true без аварийной остановки

#### Scenario: Unguarded access after destruction
- **WHEN** функция Post обращается обычным методом к уже уничтоженному захваченному компоненту
- **THEN** обращение вызывает panic и ту же аварийную остановку, что паника обработчика события

### Requirement: Package Post for MVP
MVP SHALL предоставлять ui.Post(func()) error без публичного Application. API SHALL сохранять прежние гарантии goroutine safety, UI-выполнения, FIFO, отсутствия рекурсии, отказа nil и отсутствия владельца. Это экспериментальная поверхность MVP; наличие публичного Application и окончательный получатель Post полной библиотеки не определяются.

#### Scenario: Worker posts through package API
- **WHEN** после готовности фоновая goroutine вызывает ui.Post с допустимой функцией
- **THEN** функция принимается и выполняется по существующему контракту Post, если не отменена

### Requirement: Normal MVP shutdown cancels queued tasks
Начало обычной остановки MVP SHALL закрывать приём Post и отменять все ещё не начатые задачи без восстановления. Новые вызовы SHALL возвращать ошибку без очереди. Уже выполняющаяся функция MUST NOT прерываться принудительно. Гонка с остановкой SHALL иметь однозначный исход: принятие до границы с возможной отменой либо отказ без постановки.

#### Scenario: Normal shutdown wins acceptance race
- **WHEN** обычная остановка началась до принятия конкурентного Post
- **THEN** Post возвращает ошибку, задача не попадает в очередь

#### Scenario: Post accepted before normal shutdown
- **WHEN** задача принята до начала обычной остановки, но ещё не выполняется
- **THEN** Post возвращает nil, остановка отменяет задачу, очистка её не восстанавливает
